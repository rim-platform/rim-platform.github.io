Deploying a public relay

compose.relay.yml turns compose.yml into a public relay: rim-server with RIM_ROLE=relay, the public relay's quotas and proof-of-work signups, PostgreSQL 17 and Caddy terminating TLS, and no web client. The relay holds its users' accounts, devices and cards, queues what other servers send them and forwards their requests; it hosts no workspaces. This page brings a relay up for the first time. The operator's runbook (docs/operations/relay-public.md) covers running it: keys, backups, quotas, monitoring, incidents, the abuse policy and every command. docs/relay.md explains what a relay does, and docs/specs/server-to-server-v1.md is the protocol.

A server that hosts workspaces uses compose.yml alone: docs/self-hosting.md covers it, and its sections on updates, backups and monitoring apply to the relay too.

The project's public relay is relay.rim-platform.org; yours uses your own domain. RIM_DOMAIN is the relay's host name, such as a relay. subdomain: Caddy answers for that name only, so the apex of the domain can serve a website from elsewhere.

Before the first start #

  1. A host with Docker (Compose v2.20 or later), ports 80 and 443 open, and DNS A/AAAA records of your domain pointing at it. Caddy gets the certificate from Let's Encrypt on the first request.

  2. Create deploy/.env (Git ignores it; deploy/.env.example lists every setting):

    cat > deploy/.env <<EOF
POSTGRES_PASSWORD=$(openssl rand -base64 32 | tr -d '/+=')
RIM_DOMAIN=relay.example.org
RIM_VERSION=0.0.1
EOF
chmod 600 deploy/.env

    RIM_VERSION is the release you run, the tag this checkout is at without its v. RIM_PUBLIC_BASE_URL follows RIM_DOMAIN. Every other setting has the public relay's value in the compose files; set it in .env to change it (the quotas are listed in the runbook). Without POSTGRES_PASSWORD or RIM_DOMAIN every compose command stops and names it.

  3. Check the configuration. The commands on this page and in the runbook use this alias, from the repository root:

    alias dc='docker compose -f deploy/compose.yml -f deploy/compose.relay.yml'
dc config --services          # postgres, migrate, rim, caddy: no web client

    The relay runs only ghcr.io/rim-platform/rim-server:<RIM_VERSION> (or RIM_SERVER_IMAGE). Verify it as docs/self-hosting.md, "Verify the images", says. To build it from this checkout instead, add -f deploy/compose.dev.yml to the alias and use up --build; the relay needs no rim-ui checkout either way.

Start #

dc up -d
dc logs -f rim

The migrate service applies the migrations and exits; the server starts after it. On its first start the server creates its key, writes /data/server-recovery-key.txt and logs a warning about it at every start until the file is gone. Move it offline now, as the runbook's "The server recovery key" says:

dc exec rim cat /data/server-recovery-key.txt
# copy the line to the offline places the runbook names, then:
dc exec rim rm /data/server-recovery-key.txt

Check it answers:

curl -s https://relay.example.org/.well-known/rim-server | head -c 300; echo
dc exec rim /app/rim-server server-key show

The descriptor in the discovery document says "registration":{"mode":"pow","powBits":24}.

Health, updates and operation #

The probes (/healthz, /readyz) and their checks are the same as on any server: docs/self-hosting.md, "Monitoring". Caddy does not proxy them, so they are reachable from inside the compose network only:

dc ps rim          # healthy once /readyz passes
dc exec rim curl -s http://localhost:8080/readyz

Update as docs/self-hosting.md, "Updates", says, with the relay's files named for the backup:

COMPOSE_FILE=deploy/compose.yml:deploy/compose.relay.yml deploy/backup.sh
git fetch --tags && git checkout v<version>
$EDITOR deploy/.env          # RIM_VERSION=<version>
dc pull && dc up -d

The operator's commands (/app/rim-server inside the rim container: invites that skip the proof-of-work, principal and peer blocks, abuse reports, key rotation) are listed in the runbook, "Command reference".

Another proxy #

Caddy is an example. Any TLS proxy works if it:

  • passes /api (with /api/ws as a WebSocket upgrade, and /api/remote/…), /s2s/v1/… and /.well-known/rim-server to rim:8080 unchanged: no path rewriting, no compression, no body changes, since server-to-server requests and answers are signed over method, URL and body;
  • accepts request bodies up to 32 MiB;
  • sets X-Forwarded-For to the client's address itself, replacing what the client sent, because the server trusts it (RIM_TRUST_FORWARDED_HEADERS=true) for its per-IP limits, signups included; and sets X-Forwarded-Proto;
  • is the only way in: port 8080 is never published.

With nginx:

server {
    listen 443 ssl;
    http2 on;
    server_name relay.example.org;
    client_max_body_size 32m;
    gzip off;

    location ~ ^/(api(/|$)|s2s/v1/|\.well-known/rim-server$) {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 1h;
    }
}

($connection_upgrade is the usual map $http_upgrade $connection_upgrade { default upgrade; '' close; } in the http block.)
