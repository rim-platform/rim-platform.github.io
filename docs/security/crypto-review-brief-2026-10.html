1.3 Out of scope #

  • TLS, HTTP framing, cookies and CORS (the review may assume a correct TLS channel to the server, and should say where a design depends on more than that).
  • PostgreSQL itself, the database's access control, backups and disk encryption.
  • The plaintext product: channels, search, pipelines, the agent's server side, email, alerts.
  • OpenMLS, libcrux and RustCrypto internals as libraries. Their use is in scope: configuration, suite choice, storage, which checks we skip, and what we assume they enforce.
  • Stage 5 (relays and server-to-server, specs/server-to-server-v1.md), except where Stage 4 defers a risk to it.

1.4 What we want answered #

  1. Can a malicious server (full database and code) read, inject into or silently downgrade an encrypted DM or group, or make clients trust a device it controls? Section 6 lists the paths we found; we want the ones we missed.
  2. Are the signed statement formats unambiguous and non-malleable: contexts, exact-text payloads, version 1 and 2 spellings, duplicate and unknown fields, key and signature canonicality, the 256-entry log?
  3. Is the device-linking channel sound as specified (a 256-bit symmetric secret, HKDF per direction, AES-256-GCM, AAD, one message per key, a 40-bit fingerprint the person compares)?
  4. Are the key derivations separated (HKDF salts and infos, one secret per purpose), and is any seed used in two roles in a way that matters?
  5. Is our use of OpenMLS correct: suite 0x004F, pure-ciphertext policy, the credential chain, the authenticated-data cross-checks, the decrypt-once transaction, Welcome handling with skip_lifetime_validation and replace_old_group, last-resort key packages, re-adds and incarnations?
  6. Is franking binding enough for a moderator to rely on, and who can forge a "verified" report?
  7. What does local state rollback (backups, a second tab, a restored browser profile) do to MLS, the vault and the archive?
  8. What is agile for the planned hybrid post-quantum signatures, and what would have to change?

2.3 Trust boundaries #

  1. Client and server. Everything the server returns is data. Signed statements are verified by the client against key logs it replays itself. Membership, revocation status, the conversation's encryptedAt, the author of a row, pending adds and removes, Welcomes and Commits are server assertions; section 6 lists where clients act on them unchecked.
  2. Rust and the webview (desktop). Private keys never cross into the webview, which asks the Tauri side for signed statements (key_identity/commands.rs, e2ee/commands.rs). The webview chooses what to ask for and supplies the endpoint, logs and device lists the Rust side checks.
  3. The page and IndexedDB (web). Any script in the page can use the device key handle and read the MLS keys and plaintext.
  4. Devices and the drive. The archive is encrypted under keys the drive provider never sees; it can delete, withhold or roll back files.
  5. The app and plugins. Sandboxed web plugins see only host messages; local-process plugins run as the user.

2.4 Statement formats #

Every statement travels as { payload, signature }; the payload is the exact signed text and is never re-serialized; the signature covers context ‖ payload; unknown and duplicate fields are refused (key-identity-v1.md "Signed statements"). Version 2 spells keys and signatures <algorithm>:<base64url>; version 1 spells bare Ed25519. A key log never goes from version 2 back to 1; other statements may be either version (mls-key, mls-readd and plugin-manifest exist only in version 2).

3. Review guide per area #

Each area gives the claim, the design in brief, the code, the vectors and tests that pin it, our questions, and what we suspect or deferred. Section 6 collects the findings across areas.

(a) Signed statements and key logs #

Claim. One meaning per statement; a principal id commits to its inception; only the current identity key extends a log, except a recovery key replacing a lost one; nothing is re-serialized.

Design. Exact-text payloads; per-purpose context bytes; strict unpadded base64url (canonical trailing bits); Ed25519 verify_strict; weak and non-canonical public keys refused on the server; deny_unknown_fields plus serde's duplicate-field refusal; version 2 tags with an algorithm name, a signature's algorithm must be its key's; logs up to 256 entries at enrollment; prev chaining by SHA-256 of the previous payload; plugin manifest statements stay valid across identity rotations and fail after a later recovery rotation.

(g) MLS #

Claim. A server with full access cannot read content, add a device, forge a message or force a last-resort re-add; one Commit per epoch; post-compromise security from update paths at least weekly; key agreement is hybrid.

Design summary. Suite 0x004F (X-Wing KEM 0x647a, AES-128-GCM, SHA-256, Ed25519), OpenMLS 0.9.1 with openmls_libcrux_crypto 0.4.0 on clients and openmls_rust_crypto 0.6.0 on the server. Group id rim1 ‖ conversation UUID ‖ u32 incarnation. Pure-ciphertext wire format (Commits are PrivateMessages), ratchet tree in the Welcome, padding 256, out-of-order tolerance 32, forward distance 10,000, max_past_epochs(2), Welcome leaf lifetimes not validated. Members are devices. Leaves carry an mls-key statement; clients verify each leaf against the key log, the certificate, revocation and membership. The server validates every key package against the uploading session's own device key. Twenty one-time packages plus one last-resort package per device, 90-day lifetime, never handed out within 14 days of expiry. The server sequences one Commit per epoch under a row lock and a unique index (STALE_EPOCH otherwise) and refuses application messages while removals are pending (MLS_COMMIT_REQUIRED). Re-add requests are signed by the device and served only from one-time packages uploaded after the request. Incarnations restart the group for suite migration, recovery, or when no device is left.

6. Known gaps and open questions #

Numbered for reference from sections 3 and 4. Each names where it lives at the commits in 1.1. "Ask" is what we want the reviewer's view on. The first eleven are what we would fix first.

Server substitution and client trust in server-provided data #

  1. The client takes "encrypted" from the server on every render. encrypted: Boolean(encryptedAt) from the server's Conversation.encryptedAt (ui src/features/e2ee/hooks/useE2eeConversation.ts:183) decides whether the composer uses the encrypted path (ui src/features/messages/components/MessageTimeline.tsx:295, Composer.tsx:233). A server that answers null for a conversation this device holds group state for gets the next messages through sendMessage in plaintext. The spec's "never cleared" is a server promise only. Ask: confirm, and whether a local pin (any conversation with local group state or an e2ee_conversation row is encrypted for good) is enough.
  2. Revocation status is the server's word. Leaf verification treats a device as revoked only if principalDevices lists revokedAt or a revocation (ui/tauri src/e2ee/directory.rs:94; ui src/features/e2ee/web/directory.ts:61). A server that omits them keeps a revoked (stolen) device a verified leaf; it also stops listing it as a pending remove, so no client commits its removal. The signed revocation is never verified either (presence alone counts). Ask: is a client-side revocation list or a signed device-set statement (the profile card already lists active devices) the right fix?
  3. Certificates from before a recovery stay valid on clients. certified_device (ui/tauri src/key_identity/statement.rs:645; ui browser/statements.ts:462) accepts a certificate signed by the identity key at its keySeq, with no check that a recovery rotation followed that entry, unlike plugin manifests (server rim_identity/src/plugin_manifest.rs:86 recovery_after). A thief of the pre-recovery identity key, with a server that lists the new device, gets a device every member's client verifies and adds. A retired key after an ordinary identity rotation has the same power. The server's own addDeviceKey refuses such certificates (device.rs:52), so this needs a malicious or compromised server. Ask: should clients refuse certificates whose keySeq precedes a recovery, and should certificates carry something that stops a retired key from minting new ones?
  4. Membership is server-owned; clients add whatever the server lists. Pending adds come from Conversation.mlsGroup and are committed after the rank delay (ui src/features/e2ee/runtime/groups.ts:287, membership.ts:67); is_member comes from the server's member list (ui/tauri src/e2ee/directory.rs:147). A malicious server can add a member it controls (an account with its own key identity) to a DM or group and every client commits its devices. Nothing pins a DM to two principals or asks the person. Ask: what is the minimum (DM pinning, a visible "X was added by Y" that a member signs, refusing adds not initiated by a member device)?
  5. Sender binding depends on a server field. The author check in decrypt runs only when DecryptExpectations.author_principal_id is Some (ui/tauri crates/rim_mls/src/group.rs:144, :854-861), and the app fills it from the server's author.principalId (ui/tauri src/e2ee/feed.rs:339; ui src/features/e2ee/web/feed.ts:529). A server that returns no principal id for the author can show member A's message as member B's: the row's author_id is what the timeline shows. The server's senderDeviceId is never compared with the decrypted sender device. Ask: make a missing principal id invalid, and show the MLS sender rather than the row's author?
  6. A replayed Welcome can roll a device's group state back. join builds with replace_old_group() and skip_lifetime_validation() (ui/tauri crates/rim_mls/src/group.rs:691-692); the app refuses only an older incarnation, not an older epoch of the same incarnation (ui/tauri src/e2ee/group.rs:466). The server keeps Welcomes for 30 days; a Welcome to a last-resort key package whose private key the device still holds can be delivered again through myMlsWelcomes, replacing the current state with the old epoch. Effects we see: messages of that epoch decrypt again (breaking decrypt-once), the device falls out of step and asks for a re-add. Ask: refuse a Welcome whose epoch is not above the held state's, and are there worse effects?

Franking #

  1. Whoever reads the database can forge "verified" reports. The receipt key K is one franking_key row created on first use, stored in plaintext, never rotated (server rim_infra_db/src/sea_orm_impl/e2ee.rs:1297). Verification checks only the receipt over a reporter-supplied commitment; it does not compare with the row's stored franking_commitment (server rim_infra_services/src/e2ee/mod.rs:1832-1851). With K from a backup, a member can report any text against any real message id of any sender and the server marks it verified. The moderator trusts the server's verdict by design. Ask: move K out of the database (configuration or KMS), rotate it with key ids, and require the reported commitment to equal the row's?

Rollback and reuse #

  1. State rollback replays MLS secrets. Restoring the desktop's SQLCipher cache (Time Machine, a disk image) together with the vault, restoring a browser profile, or two tabs running without the Web Lock (ui src/features/e2ee/web/webSession.ts:24-25) restart the sender ratchet at generations already used. Only OpenMLS's random 4-byte reuse guard then separates two encryptions under one AES-128-GCM key from nonce reuse. Neither the vault (ui/tauri src/secret_store.rs) nor the cache has rollback detection. Ask: how bad is this in practice, and should a device self-update (or request a re-add) when it detects it restarted from an older state (for example a monotonic counter in the OS credential store)?
  2. Re-add requests have no freshness. The server checks only the signature, the incarnation and lastEpoch ≤ epoch (server e2ee/mod.rs:1597-1690); committers check only the signature and their own 24-hour limit (ui/tauri crates/rim_mls/src/readd.rs:78, :119). The nonce is never checked for reuse and issuedAt is ignored. A server can store a genuine request and replay it later in the same incarnation, forcing a Remove and Add of that device once a day and, after 10 minutes without a Commit, opening the recovery path to a new incarnation (server e2ee/mod.rs:494 incarnation_ground). Ask: bind requests to the epoch they were made in (lastEpoch must equal the device's last known epoch) and record nonces?

Clock skew #

  1. Any client clock ahead of the server stops key package uploads. The client sets not_after = client_now + 90 days exactly (ui/tauri crates/rim_mls/src/device.rs:224); the server refuses not_after > server_now + 90 days (server e2ee/mod.rs:1113). A device whose clock runs ahead by more than the upload latency never becomes MLS-active. Receivers also validate an added key package's lifetime with their own clock against a one-hour not_before slack; a receiver more than an hour behind cannot process the Commit and asks for a re-add. Server-side windows (challenge expiry, claim validity of one hour, 14-day claim margin, 60-day activity) use the application node's clock while the database stores the times; nodes with skewed clocks disagree. Ask: margins, and which checks should use database time.
  2. No pinning of key-log heads. Clients replay whatever log the server serves. A server can serve an older prefix (hiding a rotation or a recovery), or, with a stolen old identity key, a fork for a principal it has never seen. The post-quantum decision names head pinning as the planned mitigation; nothing implements it (no store of seen heads in ui/tauri src/e2ee/directory.rs or src/key_identity/). Ask: is pinning per contact on first use enough until Stage 5's multi-relay cards?

The desktop's webview and local plugins #

  1. The webview drives signing and sees two secrets. The desktop webview sees the recovery kit text at enrollment and signup, the phrase typed at recovery and takeover, and the full link code with its secret. It chooses the endpoint the Rust side derives a login audience from (ui/tauri src/key_identity/mod.rs:662 sign_login, called from commands.rs:137) and supplies the inputs to revocations, profile cards and plugin manifests signed with the identity key (mod.rs:778, :840, :876). An XSS in the desktop app (DOMPurify is the backstop) gets login proofs for any audience and identity-key signatures on attacker-chosen manifests. Ask: which commands should require a Rust-side confirmation or pin their inputs?
  2. Local-process plugins can read every secret. They run as the user; the credential store hands an unlocked item to any process of the session and the vault file is readable by the user. chat.read.encrypted constrains sandboxed web plugins and honest local ones only (ui docs/plugin-chat-methods.md, web-plugins-v1.md "Security"). Plugin secret settings, specified on 2026-10-18 after the commits in 1.1 (plugin-protocol-v1.md, section 15), are kept in the same vault and handed to the plugin that declares them in plain form, so they are kept from other plugins and web pages, not from that plugin. Ask: is the consent wording enough, or should encrypted grants be refused to local-process plugins?

Login and errors #

  1. Revocation is disclosed before the challenge is checked. verify_login answers FORBIDDEN for a valid signature from a revoked device before the audience and challenge checks (server rim_infra_services/src/key_auth.rs:441-453). The spec says "a valid proof". Any proof from that device, however old or for whatever server, reveals revocation here.
  2. The audience defaults to localhost. With neither RIM_KEY_LOGIN_AUDIENCES nor RIM_PUBLIC_BASE_URL set, a server accepts localhost:PORT and 127.0.0.1:PORT (server rim_server/src/config.rs:370) and logs the list. A deployment behind a proxy that forgets both accepts proofs meant for any other misconfigured server on the same port.

Key separation and lifetimes #

  1. The identity seed doubles as HKDF input. The Ed25519 identity seed derives the archive wrap key (ui/tauri src/key_identity/backup.rs:48, salt rim.history-archive.v1, info archive key wrap). The HKDF salt and info separate the outputs, but the seed now has two roles. Ask: acceptable, or derive both the signing seed and the wrap key from a root?
  2. The archive key never rotates. An identity rotation replaces this device's identity-v1 wrap entry, but a drive provider can keep the old key-wraps.json; with a retired identity key the archive key opens. Likewise a passphrase change cannot revoke old manifest copies. Ask: should a rotation or recovery re-key the archive?
  3. One bad vault record discards the vault. load verifies every record and moves the file aside if any fails (ui/tauri src/secret_store.rs:290-331, :448), losing device and identity keys on that computer; "v": 2 makes every call fail. Ask: fail per record?
  4. The MLS signature key never rotates. One per device; issuedAt in mls-key is not checked anywhere. A leaked MLS key signs as that device until a lost-state re-add. Ask: rotate with self-updates?

MLS details #

  1. Lying Commits are merged before they are flagged. check_summary (ui/tauri crates/rim_mls/src/group.rs:617) marks a mismatch, then process_commit merges anyway (:573). Proposals other than Add and Remove (GroupContextExtensions, PSK, ReInit) inside a Commit only make the summary fail. Ask: which should cause a refusal and a re-add instead?
  2. Last-resort key packages are shared across claims. A last-resort package is handed out whenever a device has no one-time package left (server e2ee/mod.rs:1215), up to more than 5 claims or 7 days before expiry before the device replaces it, and its private key stays up to 7 days after. Ask: the forward-secrecy cost, given that item 6 also relies on it.
  3. Verifiers disagree on what a valid Ed25519 key is. The server refuses non-canonical point encodings (server rim_identity/src/encoding.rs:144); the desktop's verify and usable_device_key (ui/tauri src/key_identity/statement.rs:187, :218) and rim_mls's parse_tagged_key (crates/rim_mls/src/identity.rs:114) check only is_weak; the browser checks canonicality itself (statements.ts:79). The desktop's log replay also skips the identityKey != recoveryKey rule and accepts unknown fields. Ask: does any split matter?
  4. Zeroization gaps. rim_identity has no zeroize: LinkSecret, derived link keys and test signing keys stay in memory (server rim_identity/src/device_link.rs:140-170, :304); the server's franking key is a plain Vec (message.rs:631). The webview's strings (phrase, code) cannot be wiped. The web keeps MLS keys and plaintext unencrypted in IndexedDB (e2ee-web.md "Limits"). DecryptedMessage.content_bytes is a plain Vec (ui/tauri crates/rim_mls/src/group.rs:168). The desktop's Rust side otherwise wraps secrets in Zeroizing. Ask: which of these matter given the threat model?
  5. The link fingerprint is 40 bits and the race is UX-dependent. See area (c), question 1.
  6. Edits share one receipt time. See area (i), question 2.

Spec against code, and dependencies #

  1. What the specs promise and the code does not do yet.
    • The franking moderator view and the report-scoped attachment download (e2ee-mls-v1.md "Franking" step 5) are not on master in either repository; no GraphQL field exposes franked_content.
    • A report "needs no message row" (e2ee-mls-v1.md "Franking" step 4); the code requires the row (server e2ee/mod.rs:1814-1820).
    • "A valid proof from a revoked device" answers FORBIDDEN (key-identity-v1.md "Challenge login" rule 5); the code does not check the challenge or audience first (item 14).
    • encrypted_at is "never cleared" (e2ee-mls-v1.md "Scope"); clients do not hold the server to it (item 1).
    • The cache key "is re-wrapped under the device key in Stage 3" (ui/tauri src/message_cache/key.rs:4); it is not.
    • The library decision lists the IETF mls-implementations vectors for suite 0x0001 as re-run in RIM's CI; crates/rim_mls/src/tests/vectors.rs runs primitive vectors only.
    • The decision names libcrux-ml-kem 0.0.11 (2026-10-07) among the sources; the lock files link 0.0.10, which the ACVP test pins (=0.0.10 in crates/rim_mls/Cargo.toml).
  2. Errors that disclose. Anonymous rotateIdentityKey refusals other than "unknown principal" carry the validation reason (documented: they show a principal is enrolled); serde parser messages reach clients as VALIDATION text; principalDevices answers empty for principals outside the caller's workspaces. Ask: anything here worth closing?
