Strategic Thesis — 2026-10-04 #

RIM is not trying to replace Discord, Slack, or Matrix. It is a programmable communication workspace: a place where chat is the medium and the product is what the user can build on top of it. Developer teams can live in it, open-source communities can live in it, people who want a self-hosted private place to talk can live in it, and gamers can once a voice bridge plugin exists; each of them shapes it differently without RIM shipping a feature for each of them.

Five bets define the product. Everything on this roadmap either serves one of them or is the minimum support needed so people can use the app daily.

  1. The workspace is programmable by its users. A command palette over every action, keybinds for anything, macros that chain commands, pipelines that react to events, a workspace key-value store. This is how the app works, not a workflow builder bolted on.
  2. Plugins extend the application, not just the channel. A plugin adds panels, commands, context actions and keybinds, and runs next to the user with the user's own credentials. The canonical example: a panel that shows the running pods in your Kubernetes cluster, inside your chat. Slack and Discord bots can only post messages.
  3. An AI agent that operates, not summarizes. The agent uses the same command registry a keybind uses, with capability checks and a human confirmation for anything that mutates. With plugins, the agent can operate whatever a community has plugged in.
  4. Keyboard-first, modal, fast. Vim-style modes, spatial navigation, zen mode, a non-Electron desktop. For the people who choose Neovim and Obsidian.
  5. Self-hosted, private and decentralized. Your box, your model, your audit log today. The decentralization model was decided on 2026-10-08: a person is a key pair, history lives on their own drive and comes back on any device, servers are interchangeable relays, and each workspace is hosted on one server that enforces its roles. No domain or home server per user and no central RIM server anyone depends on. End-to-end encryption (MLS) covers DMs and private groups; channels stay plaintext so server search, pipelines and AI grounding keep working there. Stages 2 to 5 below delivered this.

What this rules out: chasing Discord or Slack feature parity, building first-party verticals (the incident and on-call layer is gone from the core; it returns as a plugin), and building voice.

One sentence: RIM is the communication workspace you program: commands, keybinds, macros, pipelines, plugins and an AI operator on top of chat, where you are a key, your history lives on your own drive, and no server is central.

The two pillars that carry the value are the plugin workspace (bets 1 to 3) and decentralization (bet 5). Keyboard-first, Vim-style navigation (bet 4) runs through both as the way the app is used, not as a separate pillar.

Principles for sequencing #

  • Enough chat, not parity chat. Each chat item must be justified as "people cannot live here daily without it". The bar is comfort, not Discord.
  • Platform over features. When a request can be met by a plugin, a bot, a pipeline or a macro, build the primitive and the example, not the feature.
  • Do not foreclose Stages 2 to 5. Every new server-side feature answers two questions: what does it look like when message content is encrypted, and what does it look like when there is more than one server. See the guardrails section.
  • Prove the platform on ourselves. Every platform milestone ships with one real thing built on it, starting with the Kubernetes pods panel.

Track 7 — Decentralization (XL total, Stages 1 to 5) #

Rewritten 2026-10-08. The model is decided (the contracts are docs/specs/key-identity-v1.md and docs/specs/server-to-server-v1.md), so the old research spike is dropped and the track is renumbered 7.0 to 7.4 to match the stages. Local history and keys come first because both encryption and relays depend on them.

  1. Done. Identity shape in the plugin SDK (S, Stage 1, with 2.1): plugins see users as { principalId, displayName }, never a local UUID or name@domain; principalId is opaque and stable across key changes; mentions are <@principalId>; chat methods go through one client message service. Ids minted before Stage 3 are provisional (rimp0_), and the host sends rim.principal.changed plus an old-to-new mapping notification when Stage 3 replaces them (docs/specs/plugin-protocol-v1.md, docs/specs/key-identity-v1.md).

  2. Done. Local history and drive archive (L, Stage 2): an encrypted local message store, local search marked "on this device", and an encrypted archive written to a folder, Google Drive or Dropbox. Each device writes its own archive segments, so two devices never overwrite one file; segments are encrypted under one random archive key that Stage 3 rewraps instead of re-encrypting every file. Drive providers are built-in Rust modules behind one trait in the Tauri app, not SDK plugins. One server PR adds a message change feed (change_seq bumped on edit, delete, reaction and pin, plus conversationChanges(since)) so edits and deletes reach the cache.

  3. Done. Keys, devices and challenge login (L, Stage 3, absorbs 6.1): inception and device keys with a signed rotation log, a signed profile card, QR device linking, a 12-word recovery phrase, and challenge login that issues today's session cookie. The identity key stays off day-to-day devices, which hold only device keys it signed. Keys are nullable columns on the existing user row with a kind of local or remote, so none of the dozens of tables that reference the user id move. Bots, ingest tokens and the CLI keep host-local credentials and host-scoped ids. The web app becomes a linked device of the desktop app. Shipped 2026-10-09: the rim_identity crate, enrollment, devices, rotation and recovery, profile cards, challenge login, algorithm-agile statements, key-only signup, device linking by code (desktop and web), the 12-word recovery phrase, the identity-key backup on the drive, and sign-out of other sessions (docs/specs/key-identity-v1.md, docs/specs/device-linking-v1.md). Web plugins and workspace plugin registries with signed manifests (Tracks 2.3 and 2.4) shipped with it (docs/specs/web-plugins-v1.md, docs/specs/workspace-plugins-v1.md).

  4. Done (docs/specs/e2ee-mls-v1.md; the outside review is open). E2EE v1 with MLS (XL, Stage 4): OpenMLS on the Tauri side for DMs and private groups; channels stay plaintext. Every server feature that reads text gets a client replacement in encrypted conversations; plugins read messages only through the client message service under their grant. The client sends mentioned principal ids beside the ciphertext so mentions still notify, attachments are encrypted on the client, and the server accepts one MLS commit per epoch so racing commits cannot fork a group. MLS group state is never backed up: a new device joins each group fresh and reads older history from the 7.1 archive. Message franking for reports is designed at the start of this stage. Key agreement uses a hybrid X25519 + ML-KEM-768 suite.

  5. Done. Relays and workspace hosts (XL, Stage 5, three steps): rim-server gains relay and workspace-host roles and a signed server-to-server HTTP API (HTTP Message Signatures with replay protection and rotatable server keys); GraphQL stays the client contract.

    • 7.4a Cross-server DMs and the request inbox.
    • 7.4b Remote workspace members: the user's relay subscribes to each workspace host with a delegation the user's device signed and forwards traffic both ways, so the client keeps one endpoint.
    • 7.4c The public relay relay.rim-platform.org with its runbook and abuse policy, where registering a key needs proof-of-work or an invite.

    The client keeps one GraphQL endpoint and one WebSocket, to its own relay; the relay is an untrusted courier for all its users' traffic, workspace traffic included. Every write carries the user's device signature and is forwarded unchanged, the host signs its events and the client verifies them against the host key pinned from the invite, and the host stays the only authority and sequencer. Hosts accept any relay by default, with an optional allow-list. A direct connection to a host is the fallback when the relay is unreachable. Stage 5 ships after Stage 4, so DMs and private groups are ciphertext on relays; plaintext channels are readable by the relay while queued. The contract is docs/specs/server-to-server-v1.md.

Architecture guardrails (apply from today) #

These keep Tracks 1–6 from making Stages 2 to 5 a rewrite. They cost little now.

  • Message identity is global, not server-local. Keep UUIDv7 ids, never expose row ids, and do not key anything on "the server". Design new tables with an origin/home column in mind even if it is a constant today.
  • Content and metadata are separable. New message features store rendered or derived data (search vectors, link previews, mention rows) in a way that can be absent for an encrypted message without breaking the row. No new server feature may require reading message text; it may benefit from it.
  • Keep the client capable. Commands, macros, keybinds, lenses and plugin logic stay evaluable on the client. Prefer server features that operate on metadata (membership, timing, structure) over content.
  • Identity and devices are first-class. The seeded system user, bot principals and the coming device list all go through one principal model, so keys and remote users (7.2, 7.4) add a kind and a key to a principal rather than a new concept. Plugins and new APIs see an opaque principalId, never a local UUID or name@domain.
  • GraphQL stays the client contract. Server-to-server traffic (Stage 5) is a small signed HTTP API, a non-GraphQL transport in the file_handlers.rs pattern, not federation over GraphQL.
  • Migrations are additive. Expand, then contract a release later, so a host can roll back the binary.
  • Single-node stores stay behind traits. Broadcaster, confirmation store, rate limiters, presence and typing are in memory behind interfaces today; keep it that way and never let a new feature depend on their single-node semantics.
  • No new server-only vertical features. The incident layer was removed from the core; anything comparable goes through plugins, bots or pipelines.

Risks #

  • Scope. Two XL pillars on one small team; Stages 4 and 5 are each XL. Every stage ships alone, and the plugin pillar reaches its showcase first.
  • Freezing the SDK too early or too late. v1 carries only what is implemented plus what a panel plugin needs; pre-Stage 3 ids are provisional and migrate once via rim.principal.changed plus a mapping notification.
  • Plugins and encrypted messages. A local plugin runs with the user's rights; decryption for plugins only through the client message service, per plugin and per grant, shown in the consent prompt.
  • Key loss. Recovery phrase and backup are mandatory at first run with a banner until done; the recovery key in the rotation log restores identity even without the drive.
  • Crypto correctness. Stages 3 and 4 use OpenMLS rather than hand-rolled primitives, and need an outside review before RIM is called 1.0 or production ready; 0.1.0 already waits for it. The 0.0.x releases come out before that review and are explicitly pre-review: nobody outside the project has checked their cryptography yet. docs/security/crypto-review-brief-2026-10.md says what the review covers.
  • Keys in the web app. A browser has no OS keyring; non-extractable WebCrypto keys in IndexedDB are weaker than desktop, and the UI should say so.
  • Spam without domain reputation. Request inbox and rate limits per IP, key and server first; proof-of-work on first contact is reserved in the send API from v1.
  • Server features that read text. Search, keyword notifications, lenses, link previews and pipelines need client replacements in encrypted conversations; Stage 2's local index is the first, so Stage 4 does not start without it.

Anti-Roadmap — explicitly not building #

  • Feature parity with Discord or Slack. Not the goal; Track 1 is bounded on purpose.
  • Voice and video. Discord's job; if a community needs calls, a bridge plugin to a self-hosted media server is the path, and it is not scheduled.
  • First-party verticals. No gaming pack, no developer pack, no second incident-style core module. Showcase plugins instead.
  • A native media stack, integration-directory breadth, enterprise agent platform.
  • Marketplace monetization before there is a network of plugins.
  • Domain federation (name@domain as identity), Matrix-style room replication, or peer-to-peer. Rejected for the key-identity model; a domain may return later only as an optional alias on top of a key. See docs/specs/key-identity-v1.md.
  • Encrypted channels. Channels stay plaintext so server search, pipelines and the agent keep working there; E2EE covers DMs and private groups.
