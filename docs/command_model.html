Command Model

This document defines the command model for RIM.

The command system is one of the core differentiators of the product. Commands are the backbone for:

  • built-in workflows
  • user-defined workflows
  • keybinds
  • plugin-provided actions
  • context actions
  • automations

Purpose #

A command is a named, invokable action with:

  • a stable id
  • declared arguments
  • declared context requirements
  • declared capabilities
  • a defined execution target
  • a structured result

Commands should be the common execution unit across the product.

This means:

  • the command palette invokes commands
  • keybinds invoke commands
  • context actions invoke commands
  • plugins register commands
  • automations may invoke commands
  • user commands are commands too; a macro runs commands but is not one

Current Backend State #

The current backend/contracts implementation already provides:

  • built-in command definitions
  • command listing and single-command lookup
  • backend command execution
  • persisted user commands and macros
  • user-defined command create/update/delete flows
  • command context-aware filtering for palette/context-menu/keybind use cases

Current v1 constraint:

  • persisted user-defined commands may only compose backend-executable commands
  • desktop-local command composition belongs to a later client/runtime slice

Product Requirements #

The command system must be:

  • easy to understand for end users
  • easy to extend for plugin authors
  • easy to wire into keybinds and context actions
  • safe by default
  • explicit about dangerous local behavior

Command Identity #

Every command must have a stable, namespaced id.

Examples:

  • chat.post_message
  • chat.open_thread
  • workspace.open_panel
  • integration.youtrack.create_issue
  • plugin.k8s.restart_pod
  • user.clone_repo_and_open

Namespacing rules:

  • built-in commands should use product namespaces like chat.*, workspace.*, call.*
  • integration commands should use integration.<name>.*
  • plugin commands should use plugin.<plugin_id>.*
  • user-defined commands should use user.*

Command Kinds #

RIM should support the following command sources.

Built-in Commands #

  • Shipped by RIM.
  • Stable and documented.
  • Usually available in the command palette.

Channel builtins (docs/messaging.md, Channel Visibility And Membership). Apart from the read-only chat.list_channels (Safe, chat.read), all are Backend, Mutating, chat.write, palette- and keybind-visible. conversation_id falls back to the focused conversation (context.conversation_id). Authorization (membership, private-channel visibility, Owner/Moderator) lives in ConversationService, so the agent can never do more than the user it acts for.

chat.create_channel server_id, name, description?, is_private? (default false), member_ids? yes no Members are added right after creation; privacy cannot change later
chat.join_channel server_id, conversation_id yes no Public, unarchived channels only; idempotent
chat.leave_conversation server_id, conversation_id yes no Channels and groups, not DMs
chat.invite_to_conversation server_id, conversation_id, user_ids yes no Caller must be a member

chat.unarchive_channel server_id, conversation_id yes no Owner/Moderator

Moderation builtins. All are Backend and Mutating; the admin.* ones require admin.manage_members, the chat.* ones chat.write. They call ModerationService, which enforces the roles (Owner/Moderator, who may target whom) and writes the moderation audit row (docs/messaging.md, Roles And Moderation), so a command execution is audited twice: the generic command row plus the moderation row. chat.delete_message (context menu, selected message) goes through MessageService as before, which now lets an Owner/Moderator delete other people's messages.

Notification builtins (docs/messaging.md, Notification Rules). All are Backend, Mutating, palette- and keybind-visible, AI-callable, in category Notifications, and need no capability: like chat.mark_as_read they change only the caller's own state. They call NotificationService, which requires workspace membership (and, for the level, read access to the conversation). Being Mutating, they are refused while the caller is timed out (T1); the GraphQL mutations are not.

Id Args AI-callable Dangerous Notes
notifications.set_level server_id, conversation_id, level (all/mentions/none/default) yes no default clears the override; conversation_id falls back to the focused conversation. Payload {conversation_id, level, effective_level}
notifications.dnd server_id, mode (on/off/until), until? (RFC 3339), minutes? (1..=10080) yes no The manual do-not-disturb pause (separate from the daily window); until mode needs until or minutes. Payload {paused, until}
notifications.mark_all_read server_id yes no Marks every notification of the workspace read (not the conversations' unread counts). Payload {marked}

General builtins the agent may call. None declares a new capability. The navigation commands are DesktopLocal: the server refuses to execute them, so the desktop agent runs them through the client's local handlers, and only when they are Safe and not dangerous (anything stricter goes to executeCommand, which refuses it). The five writes were raised from Safe to Mutating, which has three effects beyond the agent's confirmation gate: a timed-out member can no longer run them through the command path (T1; the GraphQL markAsRead mutation is not affected), server-side pipelines (initiator Plugin) can no longer run them because nobody is there to confirm, and they count towards the agent's per-turn mutating-call cap. Palette and keybind still run them in one step.

state.get server_id, key, scope? Safe no Read
state.list server_id, prefix?, scope?, limit? Safe no Read
state.set server_id, key, value, scope?, ttl? Mutating yes
state.incr server_id, key, delta?, scope? Mutating yes
state.delete server_id, key, scope? Mutating yes
chat.mark_as_read server_id, conversation_id Mutating yes
chat.create_group server_id, member_ids, title? Mutating yes member_ids is a JSON array or one comma-separated string

The state.* commands and the GraphQL roots workspaceState, workspaceStateList, setWorkspaceState and deleteWorkspaceState follow the same rules. Every member reads the workspace scope (scope: server) and reads and writes their own user scope. Writing the workspace scope takes a Member, Moderator or Owner who is not timed out and whose account is out of probation; a guest gets FORBIDDEN. A Member overwrites and deletes only the keys they created and increments any numeric key, so a shared counter takes everyone's count; Owners and Moderators change every key. A key whose entry expired is written as a new entry of its writer, even before the expired row is purged. A Member creates at most 100 workspace-scoped entries per workspace, holding at most 1 MiB of values; a workspace holds at most 10,000, a user scope 1,000, and a value at most 64 KiB. Each user makes at most 60 writes (sets, increments and deletes, either scope) a minute in bursts of up to 30, however they reach the service (GraphQL, a command, a macro or pipe step, a pipeline); past that a write answers RATE_LIMITED with retryAfterSeconds. WorkspaceStateChanged names the key, scope and version but not the value, which a client reads again.

Data the agent sends to its model provider grows with this set: state.get and state.list return stored values, including the caller's own scope: user entries, and nothing redacts secrets kept in workspace state. Kept off the AI surface on purpose: chat.edit_message, chat.delete_message, chat.reply_to_selected_message and chat.copy_message_text (they act on the user's selected message, which the agent cannot supply), admin.invite_member (its result is an invite token that would pass through the model provider), and chat.mark_all_as_read (duplicates notifications.mark_all_read).

List arguments such as user_ids and member_ids accept a JSON array of ids or one comma-separated string, because the agent's tool schema types every argument as a scalar.

AI-callable builtins: 41. They are seventeen chat, channel and navigation builtins (chat.post_message, chat.open_thread, workspace.open_settings, workspace.navigate_to_channel, workspace.switch_workspace, chat.list_channels, chat.create_channel, chat.list_members, chat.search_messages, chat.get_recent_messages, chat.pin_message, chat.toggle_reaction and the five channel membership builtins above), admin.timeout, chat.set_slow_mode and chat.report_message, the three notifications.* builtins, and the eighteen general builtins above. The set is pinned by collect_ai_callable_inventory_matches_reviewed_set (registry/mod.rs) and list_commands_ai_surface_returns_forty_one_commands_with_caps (command_tests.rs). The capability union the AI surface checks is admin.manage_members, chat.read and chat.write; the notification and general builtins declare none.

Plugin-Provided Commands #

  • Registered by plugins.
  • May be local-runtime or plugin-runtime specific.
  • Must declare required capabilities.

Integration-Provided Commands #

  • Registered by integrations such as bots, webhooks, or external tool connectors.
  • Usually remote or backend-oriented.

User-Defined Commands #

  • Created by the user.
  • May wrap built-in, plugin, or integration commands.
  • May compose multiple commands into a single workflow.

Current v1 backend constraint:

  • persisted user-defined commands may only compose backend-executable commands
  • desktop-local command composition belongs to a later client/runtime slice

A user command belongs to the user who created it and nobody else sees it. commands lists it as a Command while it is enabled, without its steps. userCommand(id) returns one of the caller's user commands as a UserCommand, enabled or not, with its title, description, steps in the order they run (each a commandId and its args) and isEnabled: the fields updateUserCommand takes, so an edit form loads the saved steps instead of asking for them again. It answers null for an id that is not one of the caller's user commands: a built-in id, another user's command and an unknown one alike. userCommands lists the caller's user commands in the same shape, enabled or not, sorted by id.

User Commands And Macros #

Two things compose commands, and only one of them is a command:

  • a user command (createUserCommand, id user.<key>) is a command: it is listed with the others, so it shows in the palette and a keybind can name it; its steps run in order, each with its own arguments, in the context the user command runs in
  • a macro (createMacro, MacroDef) is a list of up to 20 steps, each a builtin command id with its own arguments; a step may not name another macro or a user command, so one run performs at most 20 builtin steps. It is not in the command registry, so the palette does not list it and no keybind names it. It runs through executeMacro (from Settings or /macro in the client), its steps in order, each with its own arguments, in the context of the run. commands on the AI surface and commandDiscover offer an ai_callable macro to the agent as macro.<id>

A user holds at most 50 macros (and 50 pipelines) in a workspace, and one who is neither Owner nor Moderator at most a fifth of RIM_LIMIT_MACROS_PER_WORKSPACE (RIM_LIMIT_PIPELINES_PER_WORKSPACE) when it is set. In the server's default workspace, which every account joins, that share is the only bound: the per-workspace caps do not apply there, since macros and pipelines belong to their author and no account may fill a cap for everyone, and an account in probation creates none (VALIDATION saying when it can).

Neither pipes: each step's payload is collected under its command id in the result, and no step receives another step's result. Only executeCommand with isPipe (the palette's |) passes one command's result to the next stage.

A user command has limits that keep one run, and one lookup of its definition, bounded:

  • it lists at most 20 steps, and a user keeps at most 100 user commands
  • a chain of user commands naming user commands holds at most eight
  • one run performs at most 100 built-in steps: a nested user command counts its own steps each time a step names it, and the stages of a pipe count together

createUserCommand and updateUserCommand refuse a command over a limit with a VALIDATION error that names it: "a user command may have at most 20 steps", "a user may have at most 100 user commands", "user command recursion depth exceeded" or "a user command expands to more than 100 steps". An update is refused the same way when it would take a stored command that names the updated one past 100 steps. A stored user command that nests deeper than eight or expands past 100 steps, saved before these limits, is refused when it runs, before any of its steps runs; a pipe over 100 steps is refused with "a pipe expands to more than 100 steps". commands leaves out a user command whose definition cannot be resolved (one past 100 steps, or with a step naming an unknown or disabled command, or a cycle) and lists the rest. A disabled user command does not run: executeCommand answers NOT_FOUND for it, as for an id that names no command.

createMacro and updateMacro refuse a step naming a user command with a VALIDATION error, "macro steps must not reference user commands"; executeMacro refuses a stored macro with such a step the same way, before any of its steps runs.

A macro run asks for one confirmation up front when the macro's own sensitivity is Restricted or when any step needs one under the confirmation gate below, judged with the run's initiator: a dangerous step, a Restricted one, or a Mutating one the agent or a plugin started. Without a proof executeMacro runs no step and answers CONFIRMATION_REQUIRED with a challenge for the macro, and its message names the reason: the sensitivity tier, the steps, or both. The call made again with that proof runs the steps, and the one confirmation covers every step of the run that needs one. A macro with no such step runs without a confirmation.

Size Limits #

Each call and each stored definition has a size limit, so one request costs a bounded amount of work, storage and audit log. A request over a limit is refused with a VALIDATION error that names it, such as "command arguments may be at most 65536 bytes".

What Limit
executeCommand args, serialized as JSON 65,536 bytes, room for the longest message chat.post_message takes
executeCommand commandId 256 bytes; a pipe expression (isPipe) 4,096 bytes
User command (createUserCommand, updateUserCommand) id 256 bytes, title 128 characters, description 1,000 characters, each step's id 256 bytes and args 4,096 bytes
Macro (createMacro, updateMacro) description and nlDescription 1,000 characters each, up to 10 intentSamples of 200 characters, each step's id 256 bytes and args 4,096 bytes
Pipeline (createPipeline, updatePipeline) description 1,000 characters, up to 5 filter conditions, a MessageContains pattern of 256 characters, up to 10 actions, each action's id 256 bytes and args 4,096 bytes

Too large calls are refused before they run, so they write no audit row. The audit log keeps a call's redacted arguments when they serialize to 4,096 bytes or less; larger arguments are kept as {"truncated": true, "bytes": <size>, "prefix": <the first 1,024 bytes of the redacted JSON>}.

A pipeline action may not name a user command or a macro: each action runs as its own command call with its own budget of 100 builtin steps, and a pipeline fires on events other people cause. createPipeline and updatePipeline refuse such an action with "pipeline actions must not reference user commands or macros". A pipeline saved before these limits runs at most its first 10 actions and skips an action naming a user command or a macro.

The server keeps at most 32 unanswered confirmation challenges per user; issuing one more drops that user's challenge closest to expiry, which then answers CONFIRMATION_STALE. A pipeline's action that needs a confirmation issues a challenge nobody answers, and this keeps such challenges from piling up.

Command Contract #

Each command should expose the following metadata.

Required Fields #

  • id
  • title
  • description
  • source_kind
  • execution_target
  • arguments
  • required_context
  • required_capabilities

Recommended Fields #

  • visible_in_palette
  • visible_in_context_menus
  • visible_in_keybind_picker
  • dangerous
  • supports_preview
  • supports_dry_run

Confirmation gate (H1) #

A call needs a confirmation when the command is dangerous or Restricted, or when it is Mutating and the agent or a plugin started it. Without a proof, executeCommand answers with status CONFIRMATION_REQUIRED and the challenge confirmationRequired { token, argsHash, expiresAt }. The client asks the person to confirm and calls again with confirmation: { inBandToken: { token, argsHash } } before expiresAt, which is 60 seconds after the challenge was issued. The proof is good once, for the same caller, command, arguments and context; one that expired or was used answers CONFIRMATION_STALE, and one made for something else CONFIRMATION_FAILED.

Timeout gate (T1) #

After the capability and confirmation gates, execute_command refuses any command whose sensitivity is Mutating or Restricted with ServiceError::TimedOut { until } (GraphQL TIMED_OUT, extension until) when the actor is timed out in the context's workspace (ModerationService::active_timeout). Safe and Sensitive commands still run. The gate also runs on nested dispatch (user-command steps, pipe stages), before the rate limiter, inside the audit wrapper. Without a workspace context it has nothing to check; the services behind the command apply their own write gates anyway. Gate order: C1 capability → H1 confirmation → T1 timeout → R1 rate limit.

Arguments #

Arguments should be typed from day one.

Initial recommended argument kinds:

  • string
  • integer
  • float
  • boolean
  • enum
  • user_id
  • conversation_id
  • message_id
  • thread_id
  • workspace_id
  • selection_text

Each argument definition should include:

  • name
  • title
  • description
  • type
  • required
  • default_value if applicable
  • allowed_values for enums

Arguments should be usable by:

  • command palette forms
  • plugin-provided UIs
  • the steps of user commands and macros
  • API surfaces later

Context Model For Commands #

Commands should explicitly declare required context.

Examples of context sources:

  • selected text
  • selected message
  • selected thread
  • current conversation
  • current workspace
  • active call/session
  • current user/principal

This is important for:

  • discoverability
  • context menu filtering
  • keybind eligibility
  • plugin action registration

If required context is missing, the command must not be silently invoked.

Invocation Sources #

Commands should be invokable from multiple surfaces.

Command Palette #

  • Main discovery surface.
  • Should show only commands valid for the current context unless the user explicitly asks for all.

Keybinds #

  • Keybinds should point to commands, not to custom one-off handlers.
  • A keybind may provide fixed arguments or derive arguments from current context.

Context Actions #

  • Text selection, message menus, thread actions, channel actions, etc.
  • A context action should usually map to a command invocation.

Plugin UI #

  • Buttons, panels, modals, or toolbars can invoke commands.

Automations #

  • Event-driven or scheduled workflows may invoke commands later.

Execution Targets #

Every command should declare where it runs.

Initial execution targets:

  • backend
  • desktop_local
  • plugin_runtime
  • integration_runtime

Why this matters:

  • security and capabilities differ per target
  • availability differs by platform
  • result handling and latency expectations differ

Command Results #

Every command should return a structured result envelope.

Decision:

  • commands should not be modeled as only success/failure
  • even simple commands should return a consistent result shape

Minimum result envelope should include:

  • status
  • message or summary
  • optional structured payload
  • optional follow-up actions

This supports:

  • command palette feedback
  • automation chaining
  • plugin UI responses
  • audit/event recording later

Dangerous Local Commands #

User-defined commands may run local OS processes on desktop.

Decision:

  • allowed, but only with an explicit dangerous capability

Additional rule:

  • local process execution should show a confirmation dialog by default
  • the user may disable the confirmation later
  • the safe default is confirmation enabled

This applies especially to commands such as:

  • running shell commands
  • launching local tools
  • opening paths or files
  • interacting with local system automation

The confirmation UX should clearly show:

  • what command will run
  • what runtime/capability is involved
  • whether the command came from:
    • built-in logic
    • a plugin
    • an integration
    • a user-defined command

Security Rules #

Commands must inherit the security model of their provider.

Examples:

  • built-in commands use built-in permissions
  • plugin commands use plugin-declared capabilities
  • integration commands use integration capabilities and tokens
  • user-defined commands cannot exceed the capabilities of the commands they compose plus any local execution permissions explicitly granted by the user

Security rules:

  • no implicit privilege escalation
  • no hidden local process execution
  • no hidden remote side effects
  • dangerous commands must be marked clearly

Availability Rules #

A command may be:

  • globally available
  • available only in certain contexts
  • available only on certain platforms
  • available only when a required capability is granted
  • available only when the workspace has the command's optional module (feature) turned on

Visibility: the commands and commandDiscover queries list only the commands the caller could run in the given context, so the palette and the AI agent never offer one that executeCommand refuses for who the caller is. A command the server runs (backend) is listed only when the context names a workspace the caller is a member of, their role there may run it, and each of its required capabilities passes the capability gate; a user command needs the role every step needs. The role a builtin needs is the one the service behind it enforces: the Owner for admin.invite_member; an Owner or Moderator for admin.kick, admin.ban, admin.unban, admin.timeout, admin.set_role, chat.set_slow_mode, chat.archive_channel and chat.unarchive_channel; a member (not a guest) for chat.create_channel, chat.create_group and chat.invite_to_conversation; a member, or a guest in the direct space, for chat.join_channel; any member, guests included, for the rest. In the direct space, where everyone is a guest, a group is started and people are invited through createConversation and addConversationMembers, which apply the DM-request checks (the daily cap on requests to strangers and the probation of new accounts) that the commands do not. The commands the client runs itself (desktop_local) need no workspace and are listed to every signed-in caller, with a workspace or without. Naming the direct space makes the caller a guest of it, as other reads there do. A listed command can still be refused for its arguments, a confirmation it needs, or a timeout in force.

Examples:

  • chat.post_message may require conversation context or explicit arguments
  • plugin.k8s.restart_pod may require desktop runtime and plugin capability approval
  • integration.youtrack.create_issue may require integration installation and auth

Example Command Shapes #

Built-in Command #

  • id: chat.post_message
  • target: backend
  • context: current conversation optional
  • capabilities: chat.write

Integration Command #

  • id: integration.youtrack.create_issue
  • target: integration_runtime
  • context: selected text or selected message optional
  • capabilities: action.invoke, integration-specific external access

Plugin Command #

  • id: plugin.k8s.restart_pod
  • target: plugin_runtime
  • context: selected pod or active panel context
  • capabilities: plugin-declared runtime permissions

User-Defined Command #

  • id: user.clone_repo_and_open
  • target: desktop_local
  • composed from:
    • workspace.prompt_input
    • local process execution
    • workspace.open_folder
  • dangerous capability required because it runs a local process

Non-Goals #

The command model does not define:

  • a scripting language: a pipe passes one command's result to the next stage, macros and user commands run fixed steps, and anything beyond that belongs in a plugin
  • dataflow beyond a linear pipe
  • distributed workflow execution
  • a typed payload schema per command result: results share one envelope
  • the UI for editing commands, which is the client's concern

Summary Of Decisions #

  • Commands are the common execution unit across palette, keybinds, context actions, plugins, and automations.
  • Command ids are namespaced.
  • User-defined commands may compose other commands.
  • User commands are composed commands; macros are lists of steps with arguments, not commands.
  • Commands use typed arguments.
  • Commands declare required context.
  • Commands declare execution target.
  • Commands return structured result envelopes.
  • User-defined local process execution is allowed on desktop only behind an explicit dangerous capability.
  • Dangerous local commands should show a confirmation dialog by default, with an option to disable it later.

Default-workspace unbans #

admin.unban restores a local account to the current default workspace as Member with public channels, atomically with lifting the ban. The audit action records restored_default_workspace; reasons remain flags rather than free text. Other workspaces still need a fresh invite after unban.
