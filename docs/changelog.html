Changelog

What changes between rim-server releases, for the people who run a server and the people who write a client. The format is Keep a Changelog and the versions follow Semantic Versioning; a release is the tag v<version>, the version every crate in the workspace carries.

How entries are written #

  • A pull request that changes what an operator, a user or a client author sees adds its line under Unreleased in the same pull request. Refactors, tests and internal documentation do not.
  • Each line goes under one heading: Added, Changed, Deprecated, Removed, Fixed or Security. It says what changed for the reader, not how it was built.
  • A change the operator has to act on (a new required setting, a migration that rewrites a large table, a contract migration, a changed default) starts with Upgrade: and says what to do. docs/operations/upgrade.md is how an upgrade runs.
  • A change to the GraphQL schema or a spec in docs/specs/ names the type, field or spec.
  • At release time Unreleased becomes ## [<version>] - <YYYY-MM-DD> and a new empty Unreleased starts above it (docs/operations/release-checklist.md).

Unreleased #

Changed #

  • The web client is versioned and deployed on its own: RIM_WEB_VERSION picks the rim-ui release (unset: RIM_VERSION), rim-deploy also follows rim-ui releases and deploys the web container alone, and upgrade.sh no longer needs a rim-web image at the server's version.

0.0.4 - 2026-10-26 #

Added #

  • Message.threadReplyCount: the number of replies, deleted ones not counted, in the thread a timeline message is the root of; null on other messages.

Changed #

  • serverInfo.features gives email's unavailable reason as "no mail server is set up" instead of naming the server's settings; the boot warning still names RIM_SMTP_HOST and RIM_SMTP_FROM.

Fixed #

  • At RUST_LOG=info the server no longer logs every SQL statement, such as the server-to-server outbox poll each second; statements log at debug and those slower than one second at warn.

0.0.3 - 2026-10-26 #

Added #

  • An operator can clear the display name, picture, status and bio of the account holding a principal and optionally lock them for 1 to 365 days: rim_server principal clear-profile <principal-id> --reason <text> [--lock-days <n>], and in the app the mutation instanceClearProfile returning InstanceProfileClearOutcome. User.profileLockedUntil tells the account on me until when its profile is locked; while it is, setting any of the four answers FORBIDDEN and picture uploads 403. Audited as relay.profile_cleared.

Security #

  • Profile pictures are re-encoded by the server: POST /api/files/avatar decodes the upload as its declared type and stores the first frame, centre-cropped, as a 256×256 PNG without metadata. The upload limit drops from 2 MiB to 1 MiB, images past 4096 pixels a side answer 413, and bytes that do not decode 415.
  • During RIM_PROBATION_HOURS a new account cannot set a profile picture, status or bio; its display name it still can.
  • Profile picture uploads are limited per account by RIM_AVATAR_UPLOADS_PER_HOUR (default 5) and RIM_AVATAR_UPLOADS_PER_DAY (default 20); past either the upload answers 429 with Retry-After. 0 turns either off; instance operators are exempt.
  • Upgrade: every uploaded profile picture is scored for sexual content, gore and violence by a new service, imagecheck (ghcr.io/rim-platform/rim-imagecheck), which deploy/compose.yml now runs. At RIM_AVATAR_CHECK_BLOCK (default 0.85) POST /api/files/avatar answers 422 and stores nothing; at RIM_AVATAR_CHECK_REPORT (default 0.60) the picture is stored and an abuse report with the reason "automatic profile picture check …" is filed for the operators; while the service is down the upload answers 503. Take the new compose file with the release; a deployment that runs without the service sets RIM_AVATAR_CHECK_URL= empty, and pictures are stored unchecked.

0.0.2 - 2026-10-26 #

Added #

  • Channels can be set so only the workspace's Owner and Moderators post in them, with a switch for whether everyone else may still react and reply in threads: setChannelPosting, the PostingPolicy enum and Conversation.postingPolicy / Conversation.postingAllowsThreads, the command chat.set_channel_posting, and posting / postingAllowsThreads per channel in the default workspace's definition file (the committed file makes announcements moderators only).

0.0.1 - 2026-10-25 #

Added #

  • While rim-server or the web client cannot be reached, as during an upgrade's restart, Caddy answers 503 with Retry-After: 30: JSON for /api, /s2s/ and /.well-known/, and a self-reloading "RIM is being updated" page for browsers, instead of a bare 502 (deploy/Caddyfile, deploy/Caddyfile.relay).

  • Upgrade: account passwords, checked with OPAQUE (docs/specs/key-identity-v1.md, "Account password (OPAQUE)"). signupWithKey requires passwordRegistration (from the new passwordRegistrationStart) and answers serverShare; an account of this server with a password signs in only with loginWithKey(proof, passwordTicket), the ticket coming from the new passwordLoginStart and passwordLoginFinish (which also answers the sealed server share and the rewraps). Clients older than this release can no longer sign up, and cannot sign in to accounts that have a password. Every login start counts as a try: three are free, then waits from one minute to twelve hours (RATE_LIMITED), and the 10th locks the password (PASSWORD_LOCKED, a new error code) until a reset with the recovery key (passwordResetChallenge, passwordResetStart, passwordResetFinish, and a new password-reset statement). New roots passwordChangeStart and passwordChangeFinish; an account of this server without a password does not sign in. People from other servers sign in at a host with the key alone. The OPAQUE setup and the key the server shares are sealed under live in the new password key file, RIM_PASSWORD_KEY_FILE (default <RIM_DATA_DIR>/password-key.json), created at the first start and checked by /readyz (passwordKey); back it up with the database, which the backup scripts do with the data directory. docs/api.md ("Account password").

  • Upgrade: "Keep me signed in". loginWithKey and signupWithKey require keepSignedIn: Boolean! and keepKeyHeld: Boolean!, and LoginPayload and SignupWithKeyPayload gain sessionSecret and keepKey. A kept session gets persistent cookies and, for a web client, a keep key, read again with the new query sessionKeepKey. An unkept session gets browser-session cookies and a session secret that every request carries in the new X-RIM-Session-Secret header and the WebSocket in its connection_init payload (sessionSecret; otherwise closed with 4401), except plain file downloads, logout and the new reloadSession. reloadSession and setReloadKey (new, with the type ReloadSessionPayload) let a reloaded tab take back its data within 60 seconds of its WebSocket closing, once. Clients older than this release cannot sign in with a key or sign up. docs/api.md ("Keep me signed in").

  • Public join links: a workspace's Owner can turn on one permanent link, <server>/join/<token> with a rim_pjl_ token (off by default), that lets existing accounts of this server join (DIRECT) or ask to join (REQUESTS) as Member or Guest; it never creates an account. New GraphQL roots publicJoinLink, updatePublicJoinLink, reissuePublicJoinLink, publicJoinLinkPreview (no sign-in), joinByPublicLink, joinRequests, myJoinRequests, acceptJoinRequest, declineJoinRequest and withdrawJoinRequest, the types PublicJoinLink, PublicJoinLinkPreview, JoinRequest, JoinRequestPage and JoinByPublicLinkPayload, and the events JoinRequestCreated and JoinRequestDecided; MemberJoined gains an optional source (public_link). Every invalid link answers NOT_FOUND, and 20 misses from an address in ten minutes answer RATE_LIMITED for an hour. The tokens are sealed under the new link key file, RIM_LINK_KEY_FILE (default <RIM_DATA_DIR>/link-key.json), created at the first start and checked by /readyz (linkKey); back it up with the rest of the data directory. docs/messaging.md ("Public join link and join requests") and docs/api.md.

  • Accounts of other servers join through a workspace's public link, or ask to join, through their own server, unless the Owner turns allowRemote off (FORBIDDEN); a blocked peer is refused as for every request. remoteJoinChallenge gains the argument publicLinkToken, RemoteJoinChallenge the fields workspaceName and publicLinkMode, JoinRemoteWorkspaceInput the fields publicLinkToken and message, and RemoteJoinResult the fields outcome, joinRequestId and joinRequestExpiresAt. A request from another server is filed and decided like a local one, and the decision reaches the person's server as a JoinRequestDecided host event. On the server-to-server path, POST /s2s/v1/join/challenge and POST /s2s/v1/join take publicLinkToken (and message), and a join answers joinRequest when a request was filed. Misses a relay makes count against its server id. docs/specs/server-to-server-v1.md ("Joining"), docs/messaging.md, docs/relay.md and docs/api.md.

  • POST /api/plugin-bundles/fetch fetches and validates pinned bundles for browser installs without CORS-dependent external requests. Its plugin_link_fetch feature is enabled by default, independent of workspace plugins; public HTTPS, hash, size and rate checks apply.

  • Handles, @<username>:<domain>: GraphQL User.handle gives a local account its username at this server's handle domain and a person from another server their username at their home server and its handle domain, never the internal r_… name; null while unknown and for deleted accounts. The domain is the new RIM_HANDLE_DOMAIN, by default the host of RIM_PUBLIC_BASE_URL (the server refuses to start when it is not a DNS name, so a server whose public URL has an IPv6 host sets it). The signed descriptor declares it as the optional handleDomain; a domain that is not the server's host delegates with {"delegate": "<origin>"} at its /.well-known/rim-server, followed once and accepted only when the server's descriptor names that domain. Identity documents and joins carry the person's username at their relay. searchMessages takes from:@name:domain. docs/server-identity.md ("Handles and delegation") and docs/specs/server-to-server-v1.md ("Handles") describe it; a client that refuses unknown descriptor fields must accept handleDomain.

  • RIM_DEFAULT_WORKSPACE_FILE: the default workspace described in a JSON file (its name, DM policy and channels with topics), checked at every start. While nobody has claimed it, each start writes a single-use owner claim link to <RIM_DATA_DIR>/owner-claim.txt; the account that signs up through it creates the workspace as its Owner, optionally becomes an instance operator (claimGrantsOperator), and every existing local account joins as a Member. Later starts add new channels, topics, the name and the DM policy from the file and delete nothing. deploy/default-workspace.json is the public relay's workspace; compose.yml mounts it at /config/default-workspace.json, and RIM_DEFAULT_WORKSPACE_FILE in deploy/.env turns it on. The signup through the claim link answers the new workspace as serverId, and serverInfo.defaultWorkspace names it from then on. "A default workspace" in docs/self-hosting.md describes it.

  • RIM_TERMS_FILE: the terms of service as a Markdown file the server serves as a page at /api/terms?v=<hash>, which is then serverInfo.termsUrl and the URL every signup accepts. A missing, empty or oversized file, a FILL: placeholder in it, or RIM_TERMS_URL set too stops the server at boot. deploy/terms.md holds the public RIM server's terms and an example for self-hosters; compose.yml mounts it read-only at /config/terms.md.

  • RIM_ABUSE_CONTACT: where to report abuse, an email address or an https URL, published as abuseContact in the signed server descriptor (docs/specs/server-to-server-v1.md) and as serverInfo.abuseContact.

  • RIM_MINIMUM_AGE (13 to 21): every signup confirms the person has reached that age. serverInfo.minimumAge names it and signupWithKey takes confirmedMinimumAge; a signup without it answers VALIDATION. The account records only the age confirmed. The migration adds a nullable user.minimum_age_confirmed column.

  • "Legal duties of an operator" in docs/self-hosting.md.

  • RIM_WEB_DOMAIN in deploy/.env serves the web client on a domain of its own with deploy/Caddyfile, such as chat.example.org next to RIM_DOMAIN. The client calls the API on that origin; RIM_DOMAIN stays the server's name for apps, other servers and the discovery document, and redirects browsers to the web domain with the path kept, so invite links still open the client. The compose file sets RIM_CORS_ALLOWED_ORIGIN to the web domain's origin and RIM_KEY_LOGIN_AUDIENCES to both domains unless they are set. Unset, nothing changes. "The web client on its own domain" in docs/self-hosting.md describes it.

  • deploy/upgrade.sh <version>, the upgrade of docs/operations/upgrade.md in one script: it checks that the version's images are published (exit 2 when one is not), verifies their signatures against the release workflows, takes a backup, sets RIM_VERSION in deploy/.env, pulls, migrates and starts, waits for /readyz and the public discovery document, and rolls back to the version before when they do not answer. --dry-run checks the images and prints the rest.

  • deploy/rim-deploy.sh with deploy/systemd/rim-deploy.service and rim-deploy.timer, the unattended upgrade for a host that runs published images: every five minutes it installs the latest published rim-server release that is not a pre-release from the tag's deploy/ files and its upgrade.sh, once the version's signed rim-server image proves an approved release run. A HOLD file stops it, a failed version is held back in FAILED, and rim-deploy <version> deploys or rolls back by hand. "Unattended upgrades from releases" in deploy/README.md describes it.

  • The backup and upgrade scripts read COMPOSE_FILE from deploy/.env too, so a relay can name its compose files there once.

  • deploy/compose.monitoring-containers.yml, an opt-in overlay on top of compose.monitoring.yml that adds cAdvisor, so Alloy also sends each compose service's CPU and memory use (job cadvisor). cAdvisor reaches the Docker and containerd sockets only through proxies that allow it read-only calls alone; it needs the new DOCKER_GID in deploy/.env, and a host on the overlay2 storage driver also adds compose.monitoring-containers-overlay2.yml. "Container metrics" in docs/operations/metrics.md describes it.

  • deploy/compose.monitoring.yml, an opt-in overlay that turns on the metrics listener and adds a Grafana Alloy collector: every 15 seconds it scrapes rim-server's metrics, probes /readyz and reads the host's metrics, and remote-writes them to Grafana Cloud with the new GRAFANA_CLOUD_METRICS_URL, GRAFANA_CLOUD_METRICS_USER and GRAFANA_CLOUD_METRICS_TOKEN in deploy/.env. "Collecting them with Grafana Alloy" in docs/operations/metrics.md describes what it sends.

  • Production monitoring metrics for local accounts and activity, committed plaintext and encrypted messages, GraphQL operations, WebSocket connections and pending device delivery. Relay delivery metrics distinguish device acknowledgements from human read receipts and stored queue rows. Adds user_activity for persistent, throttled activity tracking. docs/operations/metrics.md describes their scope and sampling.

  • Who may start a DM, in three layers where each only tightens the one above ("Who May Start A DM" in docs/messaging.md). The operator sets RIM_DM_INBOUND (open, requests by default, partners, none), RIM_DM_OUTBOUND (allowed by default, partners, none) and RIM_DM_PARTNERS, shown in the new ServerInfo.dmInbound, dmOutbound and dmPartners; a workspace's Owner sets a floor for DMs from outside and a default for members' DMs with the new setWorkspaceDmPolicy (Server.dmOutsideFloor, Server.dmMemberDefault); each person chooses with the new setMyDmSettings and setMyWorkspaceDmSetting, read with myDmSettings (effectiveOutside, outsideFloorFrom). New enums DmInbound, DmOutbound, DmOutsideFloor, DmMembers, DmOutside, DmFloorSourceKind. A workspace DM a member takes as a request now goes through their request inbox. docs/operations/closed-company-server.md is the recipe for a server closed to DMs from outside or open to partners only.

  • GraphQL Conversation.dmRequestPending: for a DM, true while the other member's DM request for it is pending, so the sender can show that their messages wait for acceptance; null for groups and channels.

  • GraphQL userCommand(id) and userCommands return the caller's own user commands as the new UserCommand type (UserCommandStep), enabled or not, with their saved steps in order, so a client can edit a user command without asking for its steps again. userCommand answers null for a built-in id or a command that is not the caller's.

  • Invitations to encrypted conversations: an encrypted DM or group may now include members who have no device ready for encryption. They are listed in the new Conversation.pendingMemberIds, see the conversation but cannot read, send or be notified, and join with the new acceptConversationInvite once a device is ready, or decline with declineConversationInvite. Invitations expire after 30 days, and RIM_LIMIT_PENDING_INVITES_PER_USER (serverInfo.limits.pendingInvitesPerUser, default 50) caps how many one user holds. Before, the server refused such members; it still refuses a creator who is not ready (e2ee-mls-v1.md).

  • Instance moderation in the app: rim_server operator grant | revoke | list makes an account an instance operator, me.instanceOperator says whether the caller is one, and the queries instanceReports, instancePrincipalBlocks, instanceIpBlocks and the mutations instanceBlockPrincipal, instanceUnblockPrincipal, instanceResolveReport, instanceBlockIp, instanceUnblockIp do what the abuse-reports, principal and ip commands do; anyone else gets FORBIDDEN. Their audit lines now carry actor_id.

  • LoginPayload.csrfToken and SignupWithKeyPayload.csrfToken: loginWithKey and signupWithKey return the session's CSRF token, the value of the rim_csrf cookie, so a client that cannot read that cookie (a packaged desktop app talking to a server on another host) can send it in X-CSRF-Token.

  • docs/operations/upgrade.md: how to move a server to a new release and back.

  • Release images: every release tag publishes ghcr.io/rim-platform/rim-server:<version> (also <major>.<minor>, sha-<short sha> and latest), signed with cosign keyless by the release workflow and with an SPDX SBOM attested to it and attached to the GitHub release. docs/self-hosting.md, "Verify the images", checks the signature.

  • GraphQL ServerInfo.auditRetentionDays: the days command audit rows are kept before they are exported and deleted, null when they are kept forever. Readable without a session, like the rest of serverInfo.

  • Request limits, each off unless set: RIM_RATE_REQUESTS_PER_MIN_PER_IP (requests to /api routes per client address, answered 429 with Retry-After), RIM_RATE_MUTATIONS_PER_MIN_PER_SESSION, RIM_RATE_MESSAGES_PER_MIN_PER_USER with RIM_RATE_MESSAGES_BURST (both answered RATE_LIMITED), RIM_RATE_WS_CONNECTIONS_PER_USER and RIM_RATE_SUBSCRIPTIONS_PER_CONNECTION (the new GraphQL error code TOO_MANY_SUBSCRIPTIONS). Refusals are counted in rim_rate_limit_rejections_total, and browsers may read Retry-After. docs/api.md ("Limits") describes them.

  • An IP deny list: rim_server ip block <cidr> --reason <text> [--expires-in-days <1-365>], ip unblock <cidr> and ip list. A blocked address or range, IPv4 or IPv6, is answered 403 with {"error":"blocked"} on every route but /healthz, server-to-server routes included. A running server picks up changes within 30 seconds; blocks are audited as ip.block and ip.unblock and refusals counted in rim_ip_blocked_requests_total. Adds the ip_block table.

  • RIM_INSTANCE_NOTICE and RIM_TERMS_URL: a short operator notice and the terms of service URL, served as GraphQL ServerInfo.instanceNotice and ServerInfo.termsUrl. With terms set, signupWithKey requires acceptedTermsUrl (a new optional field of SignupWithKeyInput) equal to the terms URL and answers VALIDATION otherwise; the acceptance is stored on the account.

  • Instance limits, each off unless set: RIM_LIMIT_WORKSPACES_PER_USER, RIM_LIMIT_MEMBERS_PER_WORKSPACE, RIM_LIMIT_CHANNELS_PER_WORKSPACE, RIM_LIMIT_DEVICES_PER_USER, RIM_LIMIT_DM_REQUESTS_PER_DAY, RIM_LIMIT_MACROS_PER_WORKSPACE, RIM_LIMIT_PIPELINES_PER_WORKSPACE, RIM_LIMIT_PLUGINS_PER_WORKSPACE, RIM_LIMIT_INVITES_PER_USER_PER_DAY, RIM_LIMIT_INVITE_MAX_USES and RIM_LIMIT_MESSAGE_BYTES. Creating one more past a cap answers VALIDATION naming it. GraphQL ServerInfo.limits (type ServerLimits, one nullable Int per cap) reports them; for devices and DM requests it reports the stricter of the cap and the relay quota, which is what applies. docs/api.md ("Limits") lists them.

  • Probation for new accounts: RIM_PROBATION_HOURS (off unless set) keeps an account younger than that from creating a workspace or sending a DM request to a stranger, answered VALIDATION naming the minutes left, and RIM_RATE_PROBATION_MESSAGES_PER_MIN gives it a lower message rate. A DM in a workspace meets probation as one in the direct space does, and sharing only the server's default workspace does not make someone known to the account; an instance operator is never on probation. GraphQL ServerLimits.probationHours reports the setting and User.probationEndsAt, read on me, says when the caller's probation ends.

  • GraphQL transferWorkspaceOwnership(input: { serverId, userId }) hands a workspace to another member, who becomes its one owner while the caller becomes a moderator, and deleteWorkspace(input: { serverId, confirmName }) (answers DeleteWorkspacePayload { deleted }) deletes a workspace with everything in it once its owner types its name.

  • Self-service account deletion: GraphQL requestAccountDeletion(input: { confirmUsername }) (answers AccountDeletionSchedule { scheduledFor }), cancelAccountDeletion and User.deletionScheduledFor, set on me while a deletion is pending. After a grace period (RIM_ACCOUNT_DELETION_GRACE_DAYS, default 14, 0 to 30) an hourly job purges the account and leaves a tombstone ("Deleted account") as the author of its encrypted messages; rim_server account purge [--dry-run] runs the purge on demand. The only owner of a workspace with other members is refused until they transfer or delete it. The tombstone keeps the key identity id, so signupWithKey with a deleted account's identity answers VALIDATION. Signups may no longer take usernames starting with deleted-. Adds user.deletion_requested_at, deletion_scheduled_for and deleted_at.

  • The invite chain and the complete ban. Every account records the invite it signed up with and that invite's creator (new nullable user.created_by_invite_id and user.invited_by_user_id). rim_server principal block now also revokes the account's invites that have uses left, blocks its email (the new blocked_email table: a signup with it answers VALIDATION "this email cannot sign up here"), records the reason as a resolved abuse report, and lists the accounts its invites created; --cascade blocks those too, recursively, in the same transaction. principal unblock also lifts the email block; sessions and invites stay ended. The new principal show <principal-id> prints the account, its inviter, its invite tree, its invites, its open reports and its block.

  • RIM_RESERVED_NAMES: comma-separated usernames and display names that signupWithKey and updateMyProfile refuse with VALIDATION "this name is reserved", compared after trimming, Unicode NFKC normalisation and lowercasing, and also followed by -, _, . or a space (rim reserves rim-admin, not rimmer). An account whose own username is reserved may still take a reserved display name. An empty entry stops the server at boot.

  • Reaction notifications: a reaction on someone's message tells its author with the new NotificationReason.REACTION, one entry per message that each later reaction re-surfaces unread. Notification.reactionEmoji, Notification.reactedBy, the setting NotificationSettings.reactions / UpdateNotificationSettingsInput.reactions (default on), and reaction_emoji / reaction_by on the NotificationDue event.

  • RIM_DEFAULT_WORKSPACE: the id of a workspace on this server that every new account joins as a Member, with its public channels, whichever way it signs up, so people land where others already are. GraphQL ServerInfo.defaultWorkspace names it, null when unset. A workspace that does not exist here, or the direct space, stops the server at boot.

  • Plugin settings in docs/specs/plugin-protocol-v1.md, section 15, for plugin and client host authors: the rules of a manifest's settings_schema (value_type string, boolean, integer, path or enum, is_secret, and the optional default, min, max, options and placeholder), and rim.settings.get and rim.settings.changed, added within protocol v1 for both plugin kinds, with the panel bridge's rim.settings.open, which opens the plugin's settings form over the current view, leaving the panel in place. Values stay on the device and never reach the server, so the server does not change. Sections 15 to 20 of that spec are now 16 to 21.

  • Workspace invites can be listed and revoked. The new workspaceInvites(serverId, dir, cursor, limit) gives a workspace's Owner its invites newest first as a WorkspaceInvitePage of WorkspaceInvite (role, uses, expiry, creator, revocation and a WorkspaceInviteState of ACTIVE, EXPIRED, USED_UP or REVOKED), paged with WorkspaceInviteCursorInput and WorkspaceInviteCursorOutput, never with their tokens; the new revokeInvite(inviteId) stops an invite admitting anyone, while members who joined with it stay ("Workspace invites" in docs/messaging.md).

  • RIM_LIMIT_ACCOUNTS caps the local accounts a server holds, those waiting out their deletion grace period included; people from other servers and purged accounts do not count. Off when unset or 0. At the cap every signup, password or key, with an invite, open or with a proof-of-work, is refused with the new GraphQL error code REGISTRATION_FULL and a message that the server is full and points to running a server or signing up on another one. The new ServerInfo.registrationFull and ServerLimits.accounts, and registration.full in the discovery document beside the descriptor (server-to-server-v1.md), say so before anyone tries. docs/operations/relay-public.md says the public relay is a first test run with no guarantee against data loss, and what happens if it shuts down.

  • An hourly purge deletes the sessions that sign nobody in any more, revoked or past their expiry, and counts them in rim_sessions_purged_total; until now their rows stayed forever.

  • RIM_AUDIT_EXPORT_RETENTION_DAYS (1 to 3650): the server deletes the audit export files in <RIM_DATA_DIR>/audit-exports/ written more than that many days ago, a minute after boot and daily, and counts them in rim_audit_exports_deleted_total. Unset keeps every export. deploy/compose.relay.yml sets it to 90, so on a public relay a command audit row is gone completely after about 180 days.

  • RIM_BACKUP_KEEP_DAYS for deploy/backup.sh: after a backup that succeeded, the deployment's archives in RIM_BACKUP_DIR older than that many days are deleted. Unset keeps every archive.

  • RIM_BACKUP_HEARTBEAT_URL for deploy/backup.sh: an https URL it fetches after each backup that succeeded, for a monitor such as healthchecks.io that alerts when a night is missed. A failed ping is a warning, not a failed backup.

  • The avatars feature for RIM_FEATURES_DISABLED: while it is off, POST /api/files/avatar and GET /api/files/{path} (also when forwarded) answer 403 FEATURE_DISABLED, updateMyProfile with an avatarUrl answers FEATURE_DISABLED, and GraphQL User.avatarUrl and ServerMember.avatarUrl read as null. Stored avatars are kept. serverInfo.features and the discovery document list avatars; a client hides the profile picture upload while it is not enabled.

Changed #

  • The recipient of a DM request posts nothing into its conversation before accepting it: sendMessage, replyToMessage, forwardMessage into it, sendEncryptedMessage and toggleReaction answer FORBIDDEN ("accept the message request before posting here") while their request is pending or ignored, or they blocked its starter, and startTyping answers false. Reading it first stays possible. Before, a reply from "Read first" reached the sender while the request stayed pending.

  • In the server's default workspace a group is started and grown like a DM with each newcomer: createConversation and addConversationMembers (and the chat.create_group and chat.invite_to_conversation commands) follow each newcomer's DM settings, the request limits and probation, and a newcomer who takes it as a request holds it in their request inbox until they accept it. One call names at most 50 people and a plaintext group holds at most 50 members (VALIDATION). There only an Owner or Moderator, or a private channel's creator, adds people to a channel (FORBIDDEN), and @channel and @here notify everyone only from an Owner or Moderator; from anyone else they are plain text.

  • Upgrade: the committed deploy/default-workspace.json sets "memberDefault": "REQUESTS": a fellow member's first DM or group in the default workspace waits in the recipient's request inbox until they accept it. A server running the committed file applies it at its next start; set DIRECT in your copy to keep members' DMs direct.

  • Starting a DM or group, or adding someone to a group, is refused (FORBIDDEN) when the recipient blocked the caller or the operator blocked the caller's principal, as when their DM settings refuse it. A member added to a group gets its invite from whoever added them, so their blocks and DM settings judge that person rather than the group's creator. A plaintext group holds at most 100 members, like an encrypted one (VALIDATION).

  • In the default workspace macros and pipelines meet each member's share of RIM_LIMIT_MACROS_PER_WORKSPACE and RIM_LIMIT_PIPELINES_PER_WORKSPACE but not the per-workspace caps, which a handful of accounts could otherwise fill for everyone, and an account in probation creates none there (VALIDATION).

A Member creates at most 100 such entries per workspace, holding at most 1 MiB of values (VALIDATION). Each user makes at most 60 workspace state writes a minute in bursts of up to 30, through GraphQL, commands, macros and pipelines alike (RATE_LIMITED). Security #

  • POST /api answers a multipart/* body 415 with {"error":"unsupported_media_type"} before reading it, and reads every other body as JSON. Before, it parsed the GraphQL multipart upload format, which the schema has no use for, and one body of many empty file parts opened a temporary file for each, enough to run the server out of file descriptors (docs/api.md).
  • A workspace holds at most five times RIM_LIMIT_CHANNELS_PER_WORKSPACE channels, archived ones included; creating one past that answers VALIDATION saying archived channels still count. Before, creating and archiving channels in turn added channels without end. The ceiling is off when the cap is.
  • Adding someone as a contact no longer lets a user skip their own limits on DMs to strangers. The daily invites to people on other servers (RIM_RELAY_DM_REQUESTS_PER_DAY) and a new account's probation (RIM_PROBATION_HOURS) now pass only for people the user knows: a contact who lists the user as a contact too, or someone either of them accepted a DM request from on this server. A user holds at most 1,000 contacts; addContact for someone new past that answers VALIDATION. "Who May Start A DM" in docs/messaging.md and "Public relay" in docs/specs/server-to-server-v1.md describe both.
  • A device holds at most 256 pending MLS Welcomes and 64 MiB of them. A Commit whose Welcome would take an added device past either is refused (VALIDATION), and claimMlsKeyPackages leaves out a device without room for one more, so clients do not add it until it has read and acknowledged its Welcomes. Before, Welcomes for one device piled up for 30 days without limit. myMlsWelcomes answers a page at a time: the new optional after: MlsWelcomeCursorInput and limit (1 to 100, 100 by default) arguments, and the new MlsWelcome.createdAt that with id makes the cursor. A client that asks with no arguments gets the oldest 100 (docs/specs/e2ee-mls-v1.md, "Welcome delivery and joining").
  • Upgrade: RIM_LIMIT_INVITES_PER_USER_PER_DAY is on by default, at 50, and also caps the invite emails (createInvite with recipientEmail) one user sends in 24 hours. Emails are counted apart from the invites, so deleting a workspace does not give them back. Past either count createInvite is VALIDATION and creates nothing. Before, the cap was off unless set, and any workspace owner could have the server email any number of addresses. Set a higher number if your owners invite more people a day, or 0 to turn the cap off (docs/email.md).
  • Accepting, ignoring or reporting a DM request whose expiry has passed is NOT_FOUND, as for an unknown request; the decision checks the expiry in the same update that records it. Before, an expired request not yet purged could still be accepted.
  • The outbox a host keeps for each relay is bounded: at most 100,000 rows and 2 GiB that the relay has not acknowledged. Past either, new events are not queued for that relay; they are counted in rim_outbox_not_queued_rows_total and logged at warn once a minute. A relay every delivery to has failed for RIM_S2S_PEER_DEAD_AFTER_HOURS (default 24) is dead: nothing new is queued for it, it is tried once every 5 minutes, and its first success resumes queueing. The write itself and every other recipient are unaffected, and the relay's apps reconcile what they missed from the host's streams. Before, rows for an unreachable relay piled up for 7 days at whatever rate events were written. New gauges rim_outbox_pending_rows, rim_outbox_pending_bytes, rim_outbox_peer_max_pending_rows, rim_outbox_peer_max_pending_bytes and rim_outbox_dead_peers (docs/specs/server-to-server-v1.md, "Outbox and deliver"; docs/operations/metrics.md).
  • A relay files a DM invite another server delivers only when that server speaks for the sender it names: the sender's card must be signed by their key, and their newest card must list the delivering server (or the sender is a local user subscribed there). Anything else is refused invalid_invite and reaches no inbox; a sender whose identity neither server can produce is taken as a stranger, a request at most. Before, a peer could name anyone, including the recipient's contacts or fellow workspace members, to skip the request inbox, or invent a new sender for each request to get past the daily limit. A delivering server now also files at most 1,000 DM requests per day on a relay, whichever senders it names (docs/specs/server-to-server-v1.md, "The request inbox").
  • rustls 0.23.46: the TLS library behind outgoing HTTPS requests picks up the fixes for RUSTSEC-2026-0346, -0347, -0348 and -0349 (TLS secrets in Debug output, buffered data after an ECH rejection, certificate decompression memory, key-exchange downgrade).
  • rustls-webpki 0.103.16 and webpki-roots 1.0.10: outgoing HTTPS requests no longer trust the distrusted emSign intermediates or accept other distrusted intermediates (RUSTSEC-2026-0381, RUSTSEC-2026-0382).
  • A member removed from a workspace (kicked, banned) or from a conversation (left, removed) loses their notifications for it, and the email digest leaves out anything its recipient can no longer read. Before, a kicked member's pending notification was still emailed in the next digest, carrying the message's current text, edits made after the kick included.
  • A mutation whose protected field sits in nested fragments, named or inline, needs the CSRF header. Before, a request that showed only an exempt field such as logout at its top level skipped the check while a fragment two levels down ran updateMyProfile. The server reads the operation operationName selects through fragments at any depth, and requires the header whenever it cannot account for every root field. The refusal of account mutations for people from another server reads operations the same way.
  • RIM_RATE_MUTATIONS_PER_MIN_PER_SESSION charges every mutation field a request runs: fields in nested fragments count, and a fragment spread twice counts twice. Before, fields more than one fragment deep were not charged.
  • /api/ws runs subscriptions only. A query or a mutation sent on it answers one VALIDATION error, "only subscriptions over the WebSocket", and runs nothing. Before, a mutation sent there ran without the CSRF check, the mutation budget or the refusal of account mutations for people from another server. Clients send queries and mutations to POST /api.
  • Link previews stop reading a page at 1 MiB as it arrives, where a page sent without a length used to be read whole before the cap applied. At most RIM_LINK_PREVIEW_CONCURRENCY fetches (default 8, 1 to 64) run at once; a fetch that waits five seconds for a slot is dropped.
  • Link previews and server-to-server requests share one address policy that also refuses reserved IPv4 (240.0.0.0/4), benchmarking and protocol-assignment ranges, and IPv6 addresses that embed a private IPv4 address through NAT64 (64:ff9b::/96) or 6to4 (2002::/16). Server-to-server requests now ignore proxy environment variables, as link previews did. docs/specs/server-to-server-v1.md lists the refused ranges.
  • A WebSocket connection on /api/ws no longer outlives its session. When the session is signed out (logout, logoutOtherSessions), reset, revoked with its device, ended by an identity recovery, a requested account deletion, a block or the purge, or reaches its expiry, the server ends the connection's streams and closes it with code 4401 ("session ended"). Every operation on a connection checks the session first. A session ended in another server process or from the command line closes its connections within RIM_WS_SESSION_RECHECK_SECS (default 30, 0 turns the recheck off). docs/api.md ("Subscriptions") describes it; a client that sees 4401 signs in again before reconnecting.
  • A message on /api/ws is at most 256 KiB, whole or in fragments; a larger one closes the connection with code 1009 ("message too large"), refused at the frame header where it can be. Before, fragments were reassembled without a limit and queued for the server unbounded.
  • Pipelines react only to events their creator may see: a message, edit, deletion or reaction in a private channel, DM or group the creator is not in (for a guest, any conversation they are not in) no longer fires their pipeline or counts towards its cooldown or suspension, and a creator who has left the workspace has no pipeline firing. Only the creator is told when a pipeline fires or is suspended, and PipelineGql.lastFiredAt reads null for everyone else. Before, any member could build a pipeline with a text or author filter and learn from its firing when a private conversation they were not in received a matching message.
  • GraphQL a relay forwards for one of its users keeps this server's RIM_API_MAX_BATCH and RIM_RATE_MUTATIONS_PER_MIN_PER_SESSION, the mutation budget counted per device of the remote user, with the same refusals as /api. Before, a forwarded batch ran with no batch cap and no mutation budget.
  • A workspace state key with non-ASCII characters, given to setWorkspaceState or to the state.incr command, is refused with a VALIDATION error. Before, a key with a non-ASCII character across its 64th byte made the request fail instead.
  • A message's reactions, reactedByMe included, are read for the user who asked. Before, when several users' requests loaded reactions at the same moment, one of them could be shown another user's reaction state.
  • A workspaceEvents subscription that falls behind and misses events checks the subscriber's membership and role again before it delivers the next event, and ends when they are no longer a member of the workspace. Before, a member whose removal or demotion to guest was among the missed events went on receiving the workspace's events as before.
  • An identity recovered with the recovery phrase reaches other servers again. The identity document a relay serves and pushes (GET /s2s/v1/principals/<id>) leaves out the devices the recovery revoked, so hosts accept it, apply the recovery and revoke those devices; before, hosts refused the whole document and kept trusting the old devices, and the person could not be looked up or join a workspace on another server. A receiver ignores such a device instead of refusing the document, and a document past 64 devices keeps the current ones. Identity key rotations and recoveries are now pushed to hosts like device and card changes (server-to-server-v1.md "Profile cards and contacts", key-identity-v1.md "Rotation and recovery").
  • A host applies an identity pushed for someone from another server (POST /s2s/v1/identity) only from a relay that speaks for them: one their profile card lists (or a newer pushed card lists), their home relay while they have no card, or one holding a delegation of one of their devices. Any other server gets 403 not_delegated and nothing changes. Before, any peer could push a copy of someone's public identity and switch their devices' encryption activity on or off or become the relay the host refreshed them from. The relay a local user names, or one presenting a delegation or revocation for an unknown device, likewise only updates a known person when it speaks for them; refreshes go to the relays the person's card lists and then their home relay. RIM_HOST_ALLOWED_RELAYS now covers identity pushes too. docs/specs/server-to-server-v1.md ("Profile cards and contacts (7.4a)", "Remote users on a host", the threat model) states the rule.
  • User commands have limits: at most 20 steps each, at most 100 per user, at most eight nested, and at most 100 built-in steps in one run, nested user commands and pipe stages included. createUserCommand and updateUserCommand refuse a command over a limit with a VALIDATION error naming it. A stored user command nested deeper than eight or expanding past 100 built-in steps is refused when it runs, before any step runs, and commands leaves out a user command that does not resolve instead of failing. A disabled user command no longer runs (NOT_FOUND). Before, a few small user commands naming each other many times made one lookup or run do work that grew exponentially ("User Commands And Macros" in docs/command_model.md).
  • When a host applies a recovery or a device revocation that arrives in someone's identity (pushed by their relay or fetched from it), it ends their direct sign-in sessions and the delegations of the revoked devices, as it does for a revocation sent to /s2s/v1/revocations, and closes those sessions' live connections. Before, a device lost and recovered from kept its direct session at the host and stayed listed as delegated there. A direct sign-in of someone from another server is now refused (UNAUTHENTICATED) when their relay answers with an identity the host refuses; it still falls back to the stored copy when no relay answers (server-to-server-v1.md "Profile cards and contacts", "Direct connection").
  • A relay bounds the items DM requests hold apart from each user's queue: at most 1 MiB per request and 16 MiB per user, the invites of ignored requests included, past which a new invite is refused limited and a later item is dropped. Held items no longer count toward RIM_RELAY_QUEUE_BYTES_PER_USER. Before, they counted toward it but could not be dropped, so requests from strangers could make the relay drop every item queued for that user's devices (server-to-server-v1.md "Relay queues", "The request inbox", "Limits and audit").
  • A host keeps the challenges it issues for joining a workspace apart from login challenges. A join challenge is bound to the relay that asked for it and is accepted only by that relay's join; loginWithKey and signupWithKey refuse it, and the join refuses a login challenge. Before, a relay could present the proof a person's device signed for joining to the host's loginWithKey and get a session there as that person. Clients and relays change nothing: the proof keeps its format (server-to-server-v1.md §Joining, key-identity-v1.md).
  • Workspace invites expire: createInvite without expiresAt gives an invite that expires in seven days, and CreateInviteInput.expiresAt must be in the future and at most 30 days away (VALIDATION otherwise), as for instance invites. Invites created before keep their expiry, or none; revokeInvite ends them. Redeeming a workspace invite now checks its revocation and expiry in the same update that counts the use, so an invite revoked or expiring while a join or signup runs admits nobody.
  • The request inbox's limits hold for DMs started on this server. A conversation that would file a DM request past them is refused when it is started (createConversation, addConversationMembers): RATE_LIMITED with retryAfterSeconds once the sender would file more than RIM_RELAY_DM_REQUESTS_PER_DAY requests in 24 hours, FORBIDDEN ("their request inbox is full") while the recipient holds 100 pending requests. Before, a DM past either limit from someone on this server, or from someone elsewhere through the forward path, skipped the request inbox and reached the recipient's conversations and notifications directly. Workspace DMs a member takes as requests meet the same limits.
  • Cached identities of people on other servers, stored by remoteIdentity and by a host refreshing its remote members, are deleted 30 days after they were fetched unless the person is a remote user here. A pin of another server is forgotten after 90 days without a fetch or a request when nothing here refers to it and the configuration does not name it; its key-log head is kept, so its next contact pins it again only with a log that extends the one seen before (another history is pinned forked, a shorter one is not pinned). One origin holds at most 4 pins: a fifth server id there is refused until rim_server peer reset removes one. Before, any signed-in user could grow both tables without bound by looking up principals and servers. The hourly job, its s2s.peer_forgotten audit line and the rim_remote_identities_purged_total and rim_peer_pins_forgotten_total counters are in docs/operations/background-jobs.md (docs/specs/server-to-server-v1.md, "Pinning a peer").
  • A relay queues a host's items that name no conversation (workspace events, presence, directory events) only for recipients subscribed to that workspace, or, for presence and a recipient's own directory events from a host's direct space, for recipients who accepted a conversation that host homes; it refuses the rest not_subscribed. It also queues at most 2 GiB of items from one host a day across all its users, items of subscribed workspaces not counted, and refuses that host's further items limited (metric limiter relay_peer_bytes). Before, any server could queue such items for every user of the relay, for any workspace, up to each user's queue cap, and keep them there for the retention period (server-to-server-v1.md "Outbox and deliver", "Limits and audit").

  • Upgrade: the migration shortens the expiry of every accepted conversation a relay holds to 400 days from the upgrade, and drops the stored sender card of conversations accepted on arrival; nothing is to be done, and the previous release keeps working on the result. A relay no longer keeps a person's accepted conversations forever. The record of an accepted conversation is deleted when they leave it or are removed from it, and otherwise expires 400 days after the last item delivered for it; a person holds at most 5,000 from one host, past which a new conversation their settings would deliver is refused limited. A conversation accepted as it arrived no longer stores its sender's card. When a relay refuses an item of a direct-space conversation not_subscribed for someone still in it, the host sends them its invite again, at most once a day, so a conversation that wakes up after its record expired, or whose invite was written while that relay was unreachable for a day and never delivered, is filed again. Before, each accepted conversation was kept for a hundred years with a card of up to 128 KiB, so a host could fill a relay's database by inventing conversations (server-to-server-v1.md "Outbox and deliver", "The request inbox", "Storage", "Limits and audit").
  • Every service of deploy/compose.yml drops its capabilities, cannot gain privileges and has a read-only root filesystem, as the monitoring overlays' services already did. PostgreSQL runs as postgres from the start, and Caddy, the only container on the public ports, as nobody instead of root, keeping only NET_BIND_SERVICE, which its binary needs to start. A new one-shot service, caddy-init, gives Caddy's volumes to that user before each start, so volumes a root Caddy wrote keep working. docker compose cp into a container now fails; docs/self-hosting.md shows how to pass a file in instead.
