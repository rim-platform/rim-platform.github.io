Server-to-server v1

Server-to-server v1version 1status: implemented, normativerim-server/docs/specs/server-to-server-v1.mdcommit c2a30ae

Status: implemented, normative. Read key-identity-v1.md, device-linking-v1.md and e2ee-mls-v1.md first. This document is the contract between servers and between a server and its clients: server identity, the signed HTTP API between servers, relays, hosts, and what the client verifies. Labels of the form S5-n below name the change that introduced an item.

Summary #

  1. Every rim-server has an Ed25519 server key in a signed key log whose inception fixes a rims1_ server id, published with a signed descriptor at GET /.well-known/rim-server.
  2. Servers talk over HTTPS with HTTP Message Signatures (RFC 9421) over a fixed component list with Content-Digest (RFC 9530), a 5-minute window and a nonce store. Responses are signed too. A minimal, vector-tested profile lives in a new rim_s2s crate; no published crate fits.
  3. RIM_ROLE=relay|host|both, default both: with no new configuration a server behaves as today, and server-to-server traffic stays off until RIM_PUBLIC_BASE_URL is an https URL.
  4. Each relay has one direct space, a server row of kind direct holding the DMs and groups its users start with anyone. The relay hosts them: sequencer, MLS delivery service, change feed. A DM's home is its creator's relay.
  5. Hosts know people from elsewhere as user rows of kind remote, keyed by principal id, with key log, devices and card copied from the person's relays and kept current.
  6. A client talks only to its relay. Requests for a space hosted elsewhere go to /api/remote/<host server id>/… with a device-signed request statement; the relay forwards them unchanged; the host answers with a host-signed response the client checks.
  7. Hosts sign every event they send to relays (host-event, per-stream sequence numbers). Relays queue events per user with per-device cursors (30 days at most) and push them over the client's existing WebSocket; the client verifies them against the host key pinned from the invite.
  8. Workspace traffic reaches a relay only under a delegation a device signed (relay, host, workspace, at most 24 hours); direct-space traffic goes to the relays the person's card lists.
  9. A device revocation fans out from the relay to every host with a signed acknowledgement; the app sends it directly to a host that has not acknowledged within 2 minutes.
  10. When the relay is down the desktop app logs in to a host directly with its device key. A public relay gates registration with proof-of-work or an invite.

Server identity #

Server key log #

The rules of a person's key log apply (key-identity-v1.md, "Signed statements": exact signed text, unknown and duplicate fields refused, at most 256 entries), in version 2 only. Context bytes rim.server-key.v1\0, payload at most 16 KiB.

{"v":2,"type":"server-inception","seq":0,"serverKey":"ed25519:…","recoveryKey":"ed25519:…","createdAt":"2026-10-09T00:00:00Z"}
{"v":2,"type":"server-rotate","serverId":"rims1_…","seq":1,"prev":"…","serverKey":"ed25519:…","recoveryKey":"ed25519:…","signer":"server","createdAt":"…"}
serverId = "rims1_" + base64url(SHA-256("rim.server.v1\0" || inception payload bytes))
keyHash  = base64url(SHA-256(tagged key text))          (as device_key.key_hash)
  • The inception is signed by its serverKey. "signer": "server": signed by the current server key, recovery key unchanged. "signer": "recovery": signed by the current recovery key, which may change. seq, prev and "the key must change" are as for a person's log.
  • Private keys never touch the database: the server key's 32-byte seed is in RIM_SERVER_KEY_FILE (default <RIM_DATA_DIR>/server-key.json, {"v":1,"seed":"<base64url>"}); the server refuses to start if the file is readable by group or others, or if file and log head disagree. The log is in server_key_log_entry.
  • First boot (S5-1) with neither file nor log: the server creates both keys, the inception and the file, and writes the recovery seed to <RIM_DATA_DIR>/server-recovery-key.txt (0600) as rim-server-recovery:1:<base64url>, logging a warning at every start while it exists ("move the server recovery key offline").
  • CLI (S5-1, beside invite_cmd.rs): rim_server server-key show, server-key rotate (a signer: server rotation; the old seed is overwritten after the entry commits), server-key recover --recovery-key-file F [--new-recovery-key]. The new seed is written to <key file>.next (0600) before its entry commits and moved over the key file after; a start that finds the log head naming the .next seed moves it into place. A running server checks the log every minute and switches to the new key, re-signing its descriptor. recover works without the key file; with --new-recovery-key it writes the new recovery key where first boot does, refusing to overwrite a file there.

Discovery document #

GET /.well-known/rim-server, unauthenticated, Cache-Control: max-age=300, Access-Control-Allow-Origin: *:

{"rim":"server-discovery","keyLog":[{"payload":"…","signature":"…"}],"descriptor":{"payload":"…","signature":"…"},
 "features":{"attachments":{"state":"enabled"},"email":{"state":"unavailable","reason":"…"},"custom_emoji":{"state":"disabled"},…},
 "registration":{"full":false}}

features is optional and unsigned: each optional feature of the instance (the names of RIM_FEATURES_DISABLED, docs/operations/features.md) with its state, enabled, disabled or unavailable, and a reason for an unavailable one. It is advisory, for clients deciding what to offer; the server enforces the switches itself, so a changed copy only changes what a client shows. Readers ignore a missing features and names they do not know. It sits beside the descriptor rather than in it because the descriptor refuses unknown fields: an earlier server would refuse a descriptor that carried it. abuseContact is in the descriptor, signed, so a copy cannot send reports elsewhere; it is left out when unset, so only a server that sets it needs peers that know the field.

registration is optional and unsigned too: full is true while the server holds as many local accounts as it accepts (RIM_LIMIT_ACCOUNTS) and refuses every signup. It is advisory, since each signup counts afresh, and sits beside the descriptor for the reason features does and because it changes with signups and purges, which would otherwise re-sign the descriptor each time. The descriptor's registration still says how to sign up; readers ignore a missing registration.

The descriptor is signed by the head server key over rim.server-descriptor.v1\0 || payload (at most 16 KiB):

{"v":2,"type":"server-descriptor","serverId":"rims1_…","keySeq":0,"version":1,"roles":["host","relay"],
 "endpoints":{"graphql":"https://host.example/api","websocket":"wss://host.example/api/ws","s2s":"https://host.example/s2s/v1"},
 "s2sVersions":[1],"mlsCipherSuites":[79],"limits":{"maxBodyBytes":8388608,"clockSkewSeconds":300,"maxDeliverItems":256},
 "registration":{"mode":"invite","powBits":null},"handleDomain":"host.example","issuedAt":"…"}
Field Rule
keySeq The log head; a descriptor signed by another key is refused
version 1 to 2³¹−1; readers keep only a higher one. Re-signed with version + 1 on any change and after every rotation
roles Non-empty subset of host, relay, in that order
endpoints One origin in v1; s2s null while server-to-server traffic is off
s2sVersions [1]; a later version keeps serving the previous one (ROADMAP.md, "Releases and updates")
mlsCipherSuites What uploadMlsKeyPackages accepts
registration mode invite, open or pow; powBits only in pow mode
handleDomain The domain of the server's handles ("Handles"): a lowercase DNS name of at most 253 bytes, labels of 1 to 63 letters, digits and hyphens, no leading or trailing hyphen, no trailing dot. Optional: a descriptor without it declares no handles, and is still valid. Placed before issuedAt
abuseContact Optional, after issuedAt: where to report abuse on the server, an email address or an https URL (RIM_ABUSE_CONTACT), 1 to 512 bytes. Left out of the payload when the operator names none, so such a descriptor is byte for byte what it was before the field existed

One well-known name is enough. Rejected: an unsigned descriptor (anyone proxying the fetch, a relay included, could change endpoints), and signing the whole document (the log is self-certifying; one verifier per statement).

Pinning a peer #

A server learns a peer's id from a request's keyid, a delegation, a card's relay URL or an invite. To pin it: fetch <origin>/.well-known/rim-server over HTTPS (5 s, 64 KiB, no redirects; origins that are or resolve to a non-public address, as "Implementation" defines it, are refused unless RIM_S2S_ALLOW_PRIVATE_ADDRESSES=true), replay the log, check the inception against the expected id, verify the descriptor (its endpoints.s2s must start with the origin), and store everything in peer_server. Refresh every 6 hours on use, on a keyid above the pinned head, and on a 401 from the peer; at most one fetch per peer per minute and 60 in total.

Fetched log Action
Equal to the pin Keep; take the descriptor if its version is higher
Extends the pin with valid rotations Accept. After a signer: server rotation the previous key stays valid 24 hours from when this server accepted the extension; after a signer: recovery rotation it is refused at once
Does not extend it (a fork) Status forked: requests either way fail 403 peer_forked, ERROR log, audit s2s.peer_forked, until rim_server peer reset <id> after an out-of-band check
A prefix of the pin Keep the pin (the peer serves an older view, say a lagging node)

blocked is an operator's decision (rim_server peer block <id>, S5-6): requests either way fail 403 peer_not_allowed from the next one, until rim_server peer unblock <id> makes the peer active again. Only an active peer is blocked and only a blocked one unblocked, so a forked peer stays forked; a server never pinned is refused with RIM_S2S_DENIED_PEERS instead. Audit s2s.peer_blocked, s2s.peer_unblocked.

A first pin keeps the key before the head but gives it no grace: the grace counts from an extension this server saw. A refetch whose inception hashes to another id (the origin now serves another server) fails and keeps the pin; only a log from the same inception can fork it.

Idle pins. An hourly job forgets an active pin that was neither fetched nor sent a request for 90 days, that nothing here refers to (a remote user's home relay, a remote user's card listing its origin, a delegation, a subscription, an outbox row, an inbound cursor, a queued envelope, a DM request, a revocation fan-out, a conversation's predecessor, a cached identity it served) and that RIM_S2S_DENIED_PEERS, RIM_HOST_ALLOWED_RELAYS and RIM_DM_PARTNERS do not name. Its row and log are deleted and its head stays in peer_server_forgotten: the seq and the exact payload of the head entry. The next pin of that id must hold that entry at that seq; each entry names the hash of the one before it, so such a log extends the forgotten one. A log that holds another entry there is pinned forked (ERROR log, audit s2s.peer_forked), and one that stops short of it is not pinned and the head stays, as a refetch keeps a pin for a prefix. Deleting the head as well would let the next contact pin any history from the same inception, such as one a server key stolen before a signer: recovery rotation can sign. forked and blocked pins are never forgotten, and rim_server peer reset deletes a pin and a forgotten head alike. Audit s2s.peer_forgotten.

Pins per origin. One origin may hold pins of several server ids: when its operator starts over with a new identity (server key and recovery key lost, or the key file moved away), the origin serves a new id and the earlier id's pin stays, since a refetch that finds another id keeps it. An origin holds at most 4 pins, whatever their status. A fifth id there is not pinned (CONFLICT from remoteServer, an unknown peer to a request) until rim_server peer reset or the idle purge removes one. A lookup by origin takes the active pin fetched last.

Handles #

A person's handle is @<username>:<domain>: their username at their home relay and the handleDomain that relay's descriptor declares, such as @kuba:rim-platform.org. A username is 3 to 32 lowercase ASCII letters, digits, _ and - (never starting r_ or deleted-) and the domain a DNS name, so neither @ nor : occurs inside either part and the form parses unambiguously. The handle points at the principal id; it is never the identity. Contacts, memberships and pins stay keyed by principal id, and a username change changes the handle only.

The domain need not be the host of the server's origin, so handles survive moving the server. A domain that is not the host delegates: https://<domain>/.well-known/rim-server serves exactly

{"delegate":"https://relay.rim-platform.org"}

(one field, an https origin without path, query or fragment) instead of a discovery document. Resolving a handle domain fetches https://<domain>/.well-known/rim-server with the pinning fetch rules above (5 s, 64 KiB, no redirects, public addresses only). A discovery document there is the server's own and must verify at https://<domain>. A delegation is followed exactly once to the named origin, whose answer must be a discovery document (a second delegation is refused). Either way the server's descriptor must declare handleDomain equal to the domain resolution started from. The binding is two-way, so neither a site nor a server can claim the other's people.

Checking a peer's domain. When a server pins a peer, and again on every refetch of the pin, it checks the handleDomain the descriptor declares: it holds when it is the host of the pinned origin (no fetch), or when the domain resolves to the same server id. The outcome is stored with the pin (peer_server.handle_domain, null when the descriptor declares none or the domain points elsewhere; audit s2s.peer_handle_domain when it changes). A check that cannot run (the domain does not answer, or the fetch limits of the pin are reached; the check counts against the overall 60 a minute and once a minute per domain) keeps the stored outcome. A stored domain counts only while the pin's current descriptor still declares it and the peer is active.

Usernames across servers. A relay's identity document and its join request carry the person's username there (below); it is outside every signed statement, the relay's own word about its own account. A host records a remote user's handle (user.home_username, user.home_handle_domain) only from a document or join presented by the relay that is the user's home_relay after the store: the username, when it is a valid lowercase username, with that relay's checked handle domain. From the home relay without a valid username or without a checked domain, the handle is cleared; from any other relay it is left as it is. A remote user without a handle has none in the API (User.handle is null), and the r_ username is never offered as one. A row that becomes a local account, or is purged, loses its home handle.

Looking a handle up on its server (@name:domain to principal id) is not part of v1.

Host keys in clients #

  • From an invite (rim-invite:1:<hostServerId>:<hostKeyHash>:<inviteToken>:<hostOrigin>): the app fetches the discovery document through its relay (remoteServer(origin)), replays the log, checks the inception hashes to hostServerId and that hostKeyHash names a key of the log followed only by signer: server rotations, then pins id and log.
  • Trust on first use for a contact's relay (the home of a DM someone else started). DM content is MLS-protected either way; the pin protects metadata events.
  • A signature at a keySeq above the pin makes the app refetch (at most once a minute) and accept only an extension. The key before the head keeps verifying 24 hours after the app accepted a signer: server rotation, never after a signer: recovery one, and a first pin gives it no grace, as for servers ("Pinning a peer"). A fork stops the app using that server: "This server's identity changed in a way RIM cannot verify".

The invite carries the host's existing invite token, not one the host signed: the server id is a hash of the host's inception, so id plus key hash already expose a substituted host, and a signature over the token would add nothing.

The S2S transport #

Signature profile #

Requests go over HTTPS (http only with RIM_S2S_ALLOW_HTTP=true) to paths under the peer's endpoints.s2s, signed per RFC 9421 under the label sig1:

Request Covered components, in order
With a body (POST) "@method" "@target-uri" "content-digest" "content-type" "rim-origin"
Without (GET) "@method" "@target-uri" "rim-origin"

Parameters, in order: created; expires (at most created + 300); nonce (16 random bytes, unpadded base64url); keyid ("<serverId>#<seq>", the signing key's log entry); alg (the key's algorithm name, "ed25519"); tag ("rim-s2s-v1").

  • Content-Digest: sha-256=:<base64 SHA-256 of the body>: (RFC 9530, padded base64); sha-256 must be present and match, other algorithms are ignored. Content-Type: application/json, except forwarded requests, which keep the client's.
  • Rim-Origin: the sender's origin, where its discovery document lives.
  • @target-uri is the absolute URI the sender used. The receiver rebuilds it from the origin of its RIM_PUBLIC_BASE_URL plus path and query, never from Host or forwarded headers, so a TLS-terminating proxy does not change it.
  • The base is RFC 9421 §2.5: "<component>": <value> lines, then "@signature-params", joined by \n, no trailing newline (A.4). Signature-Input and Signature are RFC 8941 dictionaries; other labels are ignored.

The nonce parameter is RFC 9421's own replay field and is covered by @signature-params. Rejected: a separate rim-nonce header (a second field for one purpose) and Date (second resolution; created is covered already).

Verifying a request #

In order, stopping at the first failure:

  1. A declared Content-Length at most RIM_S2S_MAX_BODY_BYTES (8 MiB; 32 MiB on /forward/) → 413 too_large.
  2. Exactly the profile's components and parameters; created ≤ now + 300, expires > now, expires − created ≤ 300 → 401 bad_signature.
  3. Peer: denied, blocked or forked → 403; an unknown id is pinned from Rim-Origin first (403 unknown_peer on failure). The host allow-list applies here ("Configuration").
  4. keyid's seq is the pinned head, or the previous key in its grace period; a higher seq refreshes the pin once. The signature verifies (verify_strict) → else 401.
  5. Only now is the body read, up to the same cap → 413 too_large; its digest matches the signed Content-Digest → else 401.
  6. Insert (peer, nonce, expires_at = created + 600 s) into s2s_nonce; a conflict is 409 replay. Expired rows are deleted every minute.
  7. Rate limits per peer → 429 with Retry-After.

Responses #

Every response from the RIM layer, errors included, is signed by the responder, covering "@status" "content-digest" "content-type" "rim-request-nonce" "@method";req "@target-uri";req plus "content-digest";req when the request had a body, with created, keyid, alg, tag. Rim-Request-Nonce echoes the request's nonce and binds the answer to it. RFC 9421 §2.4 advises against covering the request's Signature field, hence the echo. A caller treats an unsigned or badly signed response as a transport failure (retry), never as an answer, and refuses a response whose created is more than 300 s from its clock. A refusal of a request whose nonce cannot be read echoes an empty Rim-Request-Nonce; no caller can match it. While server-to-server traffic is off, /s2s/v1/… answers an unsigned 404.

Errors #

Bodies are {"error":"<code>","message":"…"}.

Status error When
400 bad_request Malformed JSON or statement
401 bad_signature Profile, clock, key, digest or signature
403 unknown_peer, peer_not_allowed, peer_forked, not_delegated, forbidden Peer not pinnable; denied or off the allow-list; forked; no delegation or card names the relay; action refused
404 not_found Unknown principal, space or conversation
409 replay, conflict Nonce seen; device request seq refused (highestSeq in the body); the action conflicts with stored state
413, 429 too_large, rate_limited Caps; Retry-After
500 internal The responder failed (its database, say); retry
503 role_disabled The endpoint belongs to a role this server does not run

A request in a method other than GET or POST fails the profile (401). A peer with status blocked gets 403 peer_not_allowed.

Ping #

GET /s2s/v1/ping → 200 {"serverId":"rims1_…","roles":["host","relay"]}, served by every role. It runs the whole request check and signs its answer, so it tests a pin and the transport both ways.

Implementation #

New crate rim_s2s (no database, no Actix): signature bases, signing and verifying this profile, Content-Digest, and the server-signed statements. Structured fields through sfv 0.15.0 (2026-06-16; RFC 8941/9651); Ed25519 through rim_identity's key encodings. Its tests check RFC 9421 appendix B.2.6 ("Signing a Request Using ed25519") and appendix A here byte for byte. Outgoing requests use reqwest with rustls behind a signing client in rim_infra_services.

Outgoing requests ignore proxy environment variables and connect only to public addresses: an IP literal is checked before the request, a name when it resolves, and the connection uses the checked addresses. Refused in IPv4: 0.0.0.0/8, 10.0.0.0/8, 100.64.0.0/10, 127.0.0.0/8, 169.254.0.0/16, 172.16.0.0/12, 192.0.0.0/24, 192.0.2.0/24, 192.168.0.0/16, 198.18.0.0/15, 198.51.100.0/24, 203.0.113.0/24 and 224.0.0.0/3 (multicast, reserved, broadcast). In IPv6 only global unicast (2000::/3) is public, less 2001::/23 (Teredo, benchmarking, ORCHID), 2001:db8::/32 and 3fff::/20; IPv4-mapped (::ffff:0:0/96), IPv4-compatible (::/96), NAT64 (64:ff9b::/96) and 6to4 (2002::/16) addresses are judged by the IPv4 address they embed, and local-use NAT64 (64:ff9b:1::/48) is refused.

Considered on crates.io, 2026-10-09: httpsig 0.0.26 (2026-07-22, MIT; Ed25519, Content-Digest, response binding, but its README says work in progress and hyper-only integration); web-bot-auth 0.7.0 (2026-04-22, Apache-2.0, Cloudflare; built for the Web Bot Auth profile, generic use undocumented); actpub-httpsig (ActivityPub-shaped). A fixed profile with one algorithm is about 400 lines against vectors, a smaller surface than any of them, and fits Actix's request types.

Remote users on a host #

Created the first time a host accepts a person from elsewhere (a join, a DM a local user starts, a delegation):

Column Value
kind, principal_id, identity_key remote; from the verified key log
username r_ + the first 30 characters after rimp1_. From S5-1 on local signups refuse the r_ prefix, so nobody squats a principal's name; existing local names are left alone
display_name The card's displayName cleaned by the display name rules of docs/api.md (invisible characters removed but those emoji and scripts need, whitespace runs made one space), cut to 64 characters, updated with each newer card; the username when nothing visible is left or the name is reserved here (RIM_RESERVED_NAMES)
password_hash, email Null (allowed: principal_id is set)
home_relay Server id of the relay that most recently presented a valid delegation for the user, else the first relay of their newest card that pins, else the relay that served their identity: one that speaks for them (7.4a) or one the host fetched it from. Null for local users
home_username, home_handle_domain The user's username at their home relay and its checked handle domain, set together ("Handles"); null while unknown and for local users

Key log, devices (with certificates and revocations) and card live in the existing key_log_entry, device_key and profile_card tables, as for an enrolled local user. A key-only signup for a principal held here as remote turns the row local and keeps its memberships. Usernames stay unique across the table; rejected: a partial unique index on local users only, since login and member lookups assume one row per name.

Remote users may not run mutations that change the account rather than a space (FORBIDDEN, not available to remote members): login, logout, signup*, enrollIdentityKey, addDeviceKey, revokeDeviceKey, rotateIdentityKey, publishProfileCard, logoutOtherSessions, password and email mutations, createServer and bot mutations. Identity changes arrive by POST /identity and POST /revocations.

updateMyProfile sets what the host stores per member and the card does not carry: the avatar (uploaded with POST /api/files/avatar on the forward path, then named by avatarUrl, which takes only the url that upload answered or an empty value), status text and bio. A displayName in it is FORBIDDEN (a remote member's display name comes from their profile card); the name changes with the next card the host receives.

Spaces hosted elsewhere: the client's path #

Device-signed requests #

A request to a space hosted elsewhere carries Rim-Device-Request (unpadded base64url of the exact payload text) and Rim-Device-Signature (the tagged signature over rim.device-request.v1\0 || payload):

{"v":2,"type":"device-request","principalId":"rimp1_…","deviceId":"<uuid>","host":"rims1_…",
 "method":"POST","path":"/api","seq":1791504000000000,"bodySha256":"<base64url>","issuedAt":"…"}
Field Rule
host The host's server id
method, path The host-relative request (POST /api, GET /api/attachments/<id>/download, POST /api/files/upload, POST /api/files/avatar, GET /api/files/<path>, GET /api/plugin-bundles/<server>/<sha256>); must equal the forwarded one
seq Below 2⁵³, greater than every seq this device used with this host; clients use max(previous + 1, Unix time in µs) and persist it
bodySha256 base64url(SHA-256(exact body bytes)); the empty body's hash for GET

The host accepts a seq it has not accepted from this device in the last 10 minutes and that is above highestSeq − 300,000,000 (5 minutes in µs), then raises highestSeq. An accepted seq is remembered for 10 minutes and, after that, until it falls below the window: forgetting it at 10 minutes would let a relay replay a device's latest request once the device went quiet. Otherwise 409 {"error":"replay","highestSeq":"<decimal>"}; the client moves its counter above it and signs once more. The window tolerates the relay reordering concurrent requests and needs no server clock. Rejected: a strict +1 counter (a crash between signing and persisting locks the device out; concurrent requests fail).

Forwarding #

The relay serves GET|POST /api/remote/<hostServerId>/<host-relative path> (a non-GraphQL transport in rim_server, in the file_handlers.rs pattern); GraphQL is POST /api/remote/rims1_…/api. It authenticates the session cookie (and CSRF for POST) as today, refuses a device request naming another principal or device than the session's or a revoked device (FORBIDDEN), and sends <host s2s>/forward<path> with the body byte for byte, the client's Content-Type, both device headers and its own signature. It returns the host's status, body, Content-Type, Rim-Host-Response, Rim-Host-Signature and Retry-After unchanged.

The host's /s2s/v1/forward/… checks the S2S signature, then the device request (a non-revoked device of a user here; host is its own id; method, path, body hash; seq), then that the relay may carry this user's traffic: it holds an active delegation of this device for a workspace here, or the user is a member of this host's direct space and the relay's origin is in their newest card (403 not_delegated otherwise). It runs the normal handler (GraphQL, attachment upload and download, avatar upload, stored-file download, plugin bundle download) as that user and device, with no session; CSRF does not apply without cookies. Per-IP limiters key on relay:<serverId>:<principalId> for forwarded requests. Forwarded GraphQL keeps the host's own /api limits, whatever the relay's are: a body past the GraphQL body caps of /api (docs/api.md, "Limits") is answered 413 {"error":"too_large"}, a batch over RIM_API_MAX_BATCH is answered 400 {"error":"batch_too_large"}, and none of either runs, and its mutation fields are charged to a RIM_RATE_MUTATIONS_PER_MIN_PER_SESSION budget of the device, so a batch past it answers RATE_LIMITED with retryAfterSeconds and nothing in it runs.

Every forwarded response carries Rim-Host-Response (base64url payload) and Rim-Host-Signature:

{"v":2,"type":"host-response","host":"rims1_…","keySeq":0,"requestSha256":"<base64url>","status":200,"bodySha256":"<base64url>"}

requestSha256 hashes the device-request payload text, so a relay cannot answer a new request with an old response. The app checks signature, pin, request hash, status and body hash; a failure counts as a relay failure ("Direct connection"). The host buffers bodies to hash them (downloads ≤ 25 MB).

Coexistence. Spaces this server hosts are used exactly as today (/api with cookie and X-CSRF-Token, workspaceEvents on /api/ws); only spaces hosted elsewhere use /api/remote/…. The request authenticator gains a second path (device request via a pinned peer) yielding the same RequestAuthResultDto with no session id; AuthActorCtx already carries the device. Rejected: one S2S endpoint per client operation (hundreds of endpoints drifting from the schema, while the decision requires writes to reach the host unchanged).

Outbox and deliver #

For each event the host appends one s2s_outbox row per receiving relay: relays holding an active delegation of a recipient, or for a direct space the relays in each remote recipient's newest card. A task per peer sends them in id order:

POST /s2s/v1/deliver
{"items":[{"id":"1234","envelope":{"payload":"…","signature":"…"},"recipients":["rimp1_…"],"deviceId":null}]}
→ 200 {"ackedThrough":"1234","refused":[{"id":"1230","reason":"unknown_principal"}]}
  • At most 256 items and 8 MiB per request; recipients are the relay's users who may see the event; deviceId targets one device (MlsWelcomeAvailable).
  • The relay stores items before answering and ignores ids at or below its received_through for the peer, so redelivery is idempotent. It refuses items for non-local principals (unknown_principal); items of a conversation it holds no invite or request for, and items naming no conversation of a workspace the recipient holds no active subscription to (not_subscribed); invites from a principal the recipient blocked (blocked) or past the request limits (limited); invites whose sender the host does not speak for (invalid_invite, see "The request inbox"); a device-targeted item for an unknown device (unknown_device); envelopes over 512 KiB, that do not verify under the delivering host's key or that name another host (invalid_envelope); and, past 2 GiB of items queued from the delivering host in a day across all recipients, any further item the relay would queue (limited; items of a workspace the recipient subscribed to are not counted). A direct space sends items naming no conversation only on e (PresenceChanged) and on the recipient's own u: stream (MemberJoined, MemberLeft, MemberRoleChanged about them): the relay queues those for a recipient who holds an accepted request for a conversation that host homes, and refuses everything else naming no conversation (w, another person's u:) without a subscription. A refusal for one recipient carries principalId. The host skips a (relay, principal) for 24 hours after unknown_principal only; the other refusals are about one conversation or item. After not_subscribed for an item of a conversation of its direct space that the principal is still a member of, the host sends that member the conversation's DmInvite again, as when they were added (from the member who added them while still a member, else from the creator), at most once a day per conversation and principal, whatever the relay lost it to: a row that expired after a long silence, or an invite written while the relay was dead and never delivered. The refused item itself is not sent again.
  • Failures back off from 1 s doubling to 5 minutes. Outbox rows live 7 days, delivered or not; a relay down longer gets nothing and its clients catch up from the change feed. A relay may pull what it missed: GET /s2s/v1/outbox?after=<id>&limit=256 → {"items":[…],"hasMore":false}.
  • Per-relay caps. A relay's backlog, its rows above what it acknowledged, holds at most 100,000 rows and 2 GiB. Delivered rows kept for the 7 days do not count. While the backlog is at either cap, an event's row for that relay is not written: the event is dropped for that relay only, counted (rim_outbox_not_queued_rows_total{reason="peer_cap"}) and logged at warn at most once a minute per relay. The write that caused the event succeeds, the host's database has it, and other relays and local members get it as usual. The writer reads each relay's backlog at most every 10 seconds and counts its own rows in between, so with several nodes a backlog can pass a cap by what the other nodes write in that time.
  • Dead relays. A relay every delivery to has failed for RIM_S2S_PEER_DEAD_AFTER_HOURS (24) since the first failure after its last success (s2s_peer_delivery.failing_since) is dead. Its backlog is kept, within the caps and the 7 days, and no new rows are written for it (reason="dead_peer"). The sender tries a dead relay once every 5 minutes, the longest backoff: with its next batch, or with an empty deliver ({"items":[]}) when nothing is left, which a relay answers like any other. The first 200 ends the failures, and rows are written for it again within 10 seconds.
  • An event a relay does not get still takes its stream's seq. When the relay is back, the next event on each stream arrives with seq > last + 1, and the app reconciles from the host as for any gap ("What the client checks"): change feed, pins, reactions, members and streamHeads, through the forward path. Not recovered: e events (no seq). A DmInvite written in that window is sent again once the relay refuses a later item of its conversation (not_subscribed).

Relay queues #

The relay stores each envelope once (relay_envelope), one relay_item per recipient user, and a cursor per device (relay_device_cursor): each device's queue is its user's items above its cursor.

  • Push: a subscription relayStream(after: ID) on the existing /api/ws yields items above after, then live ones: {"type":"RelayItem","id":"981","hostServerId":"rims1_…","workspaceId":"…","envelope":{…}}, plus notices: {"type":"DmRequestReceived","requestId":"<uuid>"}, {"type":"RevocationAcked","deviceId":"<uuid>","hostServerId":"rims1_…","ack":{"payload","signature"}} (the app checks the acknowledgement and refreshes deviceRevocationStatus) and {"type":"QueueOverflow","spaces":[{"hostServerId":"rims1_…","workspaceId":"<uuid>"}]}.
  • Pull relayItems(after, limit); ack ackRelayItems(upTo) moves the session device's cursor. A newly linked device starts at the newest item and reads history from the host's feed and the archive.
  • Retention: an item goes once every non-revoked device of its user acked it, and after RIM_RELAY_RETENTION_DAYS (30) regardless. Over the per-user byte cap the oldest go first and a QueueOverflow notice names the affected spaces. Items held by a DM request are neither counted toward that cap nor dropped for it; their own caps bound them (see "The request inbox"). The notice is pushed to the devices online and not queued (a queued item is a host-signed envelope); a device offline then sees the gap in the streams' seq. Plaintext channel events are readable by the relay while queued, as the relay decision accepts.

What the client checks #

For every RelayItem: the signature under the pinned key at keySeq (refetching on a newer seq); host is the item's; workspaceId is a space the app has from that host; the stream matches the event (c: its conversation, u: the app's principal). Then per stream:

  • seq ≤ last: duplicate, dropped. seq = last + 1: applied.
  • seq > last + 1: held up to 30 seconds or 256 events for the missing ones, then the app reconciles through host-signed responses (change feed, pins and reactions of the open conversation, members, streamHeads) and sets last to the head. Only if that fails does it show "Messages may be missing from <space>" with "Connect directly".
  • A stream's baseline is its streamHeads value when the space opens, or the first event seen. Events arriving by relay and by direct connection are deduplicated the same way.

Profile cards and contacts (7.4a) #

  • Publishing. relays[] is the person's own list, preferred first. The app signs a card (version + 1) and calls publishProfileCard on each listed relay it has an account on; each relay pushes it to every host that holds the person as remote (POST /s2s/v1/identity): the hosts it queued items or filed requests from for the person, and in S5-4 those holding their subscriptions. Device additions and revocations, identity rotations and recoveries are pushed the same way. The answer is {"applied":true|false}.
  • Identity endpoint (relays, for local users): GET /s2s/v1/principals/<principalId> → {"principalId","keyLog":[…],"devices":[{"deviceId","certificate","revocation","mlsActive"}],"card","username"}, 404 for others. username is the person's username at the relay (optional; a reader takes a document without it, and records it only as "Handles" says). devices lists at most 64 devices, leaving out those whose certificate a recovery rotation voided (keySeq before the log's last recovery entry); past 64 it keeps the unrevoked devices, then the most recently revoked. POST /s2s/v1/identity takes the same JSON; the receiver applies it only for principals it holds as remote: a log extending its copy, new devices with valid certificates, revocations, a card of higher version. A receiver ignores a listed device whose certificate a recovery voided, after checking its signature like any other; a recovery entry new to the receiver revokes every device it held for the person and ends all of the person's direct sessions and the delegations of those devices, and a revocation new to it ends that device's delegations and direct sessions, as /s2s/v1/revocations does. Live connections of the ended sessions close. The same applies to a document the receiver fetches. It applies it only from a relay that speaks for the principal: their newest stored card lists the relay's origin; the pushed card, verifying against the pushed log's head and of a higher version than the stored one, lists it; it is their home_relay and no card is stored; or it holds an active delegation of one of their devices. Any other peer gets 403 not_delegated and nothing is stored. mlsActive is outside every signed statement, the relay's own observation: a host takes it only from a relay that speaks for the principal, from one it chose to fetch from (below), or from the relay a local user named for a principal the host did not hold yet; a relay that presents a delegation or revocation for a device the host does not know is fetched from only when it speaks for the principal.
  • Fetching. remoteIdentity(principalId, relayUrl) answers local principals directly and otherwise fetches from relayUrl (pinning it), cached 24 hours. The app verifies the log against the principal id, each certificate against the log and the card against the head, as e2ee-mls-v1.md requires for leaves. principalDevices answers remote users from the stored copy, refreshed when older than an hour from the relays their newest card lists that are pinned, then their home_relay. The relay that last served or pushed the copy (servedBy) is informational and never chooses where it is refreshed from.
  • Contacts. A contact link is rim-contact:1:<principalId>:<relayUrl> (relay URL rules as a device-link endpoint: 1 to 256 bytes of printable ASCII, no ?, #, @), shown as a byte-mode QR code. The principal id authenticates everything fetched with it. Rejected: the card in the link (up to 128 KiB, too large for a QR code, stale after a relay switch). The app reads a shared workspace member's card with remoteIdentity(principalId) (the relay answers its own principals directly) to offer "Add as contact". The contact list answers open decision 9 (readable names): the app shows the card's name or the person's alias for it; aliases stay on the device. The relay keeps the list (relay_contact, at most 1,000 per user) because it filters DM requests by it. Adding someone does not let the user skip their own limits on DMs to strangers; only a contact who lists them too does ("Public relay").

The direct space #

Each relay has one server row with kind = 'direct', created at start if missing, named "Direct messages", not listed by servers, with no owner, channels, invites or plugin registry; relayInfo { serverId roles directSpaceId } gives its id. Every member is a guest, so today's guest rules already hide the member list and directory events; the conversation service lets guests create groups in a direct space and refuses channels there. Local users join on first use, remote users when a local user adds them to a conversation.

A DM or group there has conversation.server_id = the direct space, so "a DM in no workspace" belongs to its home relay's direct space and every table, event and query keyed by server_id works unchanged. Rejected: a nullable conversation.server_id (every conversation query, every event's workspace_id and the per-space subscription would change). DMs inside workspaces stay possible; the app starts new DMs in the direct space when every member has a principal id.

DMs across relays (7.4a) #

Alice's relay R_A is the home; Bob's relay is R_B. Groups work the same way.

  1. Create. Alice calls createConversation(serverId: <directSpaceId>, encrypted: true, remoteMembers: [{ principalId, relayUrls }]) on R_A. R_A fetches Bob's identity from the first relay that answers, creates or refreshes his remote user row and direct-space membership, and checks readiness from mlsActive. A pair with a DM there gets it back, as today. One entry in remoteMembers and no memberIds makes a DM, more make a group; the app names every member this way, those on R_A included. The app creates a conversation with anyone on another relay only encrypted: when a member or Alice's device is not ready it creates nothing and says who. The server enforces this too: R_A refuses such a conversation unencrypted (VALIDATION, "conversations with people on other servers are encrypted"), so relays only ever carry its ciphertext, and refuses an encrypted one when a member has no MLS-active device. A person from another relay may create one too, through the forward path, naming R_A's members the same way.
  2. Key packages. Claims for Bob's devices go to R_B: POST /s2s/v1/key-packages/claim {"principalId","devices":["<uuid>"],"conversation":{"host","conversationId","incarnation"},"claimer":{"principalId","deviceId"},"cipherSuite":79} (cipherSuite optional, the preferred suite when absent; conversation.host must be the calling peer) → {"keyPackages":[{"deviceId","keyPackage","keyPackageRef","lastResort"}]}, by today's claim rules. R_A names the claimer and R_B cannot check that name, so R_B judges the claim by Bob's tie to R_A, not by whom the claimer is: unless Bob accepted a conversation R_A homes or holds an active subscription to a workspace R_A hosts, the claimer is a stranger: last-resort packages only, 20 claims per claimer principal per day. A claimer Bob blocked is refused (403). R_A stores the packages as claimed mls_key_package rows of Bob's device rows, so submitMlsCommit's claim check runs unchanged.
  3. Invite. When a remote member is added to a conversation of the direct space (at creation or by addConversationMembers), R_A emits DmInvite on the member's u: stream, {"type":"DmInvite","workspace_id","conversation_id","from_principal_id","from_card","member_principal_ids"}, before the conversation's own events. from_* name the conversation's creator; from_card is their published card as {"payload","signature"} (a conversation with remote members needs one), and its relays tell Bob's app where to pin R_A from. The Commit that adds the member's devices then emits MlsWelcomeAvailable per added device. That is how R_B and Bob's devices learn of it; a plaintext conversation has an invite and no Commit.
  4. Traffic. Bob's devices fetch Welcomes and Commits, read the change feed, send, edit, react and mark read through /api/remote/<R_A>/api; R_A runs them as Bob's device, and its events reach Bob's devices through R_B's queue. The envelopes are exactly the message.encryption R_A stores.
  5. Sequencer. R_A alone: one Commit per epoch, the change feed's version, read states. R_B holds no conversation row. R_A keeps the conversation like any server today (Commits 90 days, Welcomes 30 days); R_B's items follow "Relay queues".

Rejected: a sequencer that moves between relays or a vote between them (state resolution between servers, which RIM does not do), and storing the conversation on both relays (two truths for epochs).

When the home is gone: unreachable directly and through the member's relay for 7 days, or absent from the creator's newest card and not answering. Any member's app may then create a successor in its own relay's direct space with the same members and predecessor: { hostServerId, conversationId }; apps show both as one timeline from the cache and archive. Of two successors the one with the smaller id is canonical (ids are UUID v7, so this is the earlier) and members leave the other. Members learn a conversation is a successor from Conversation.predecessor. The creator's app also makes successors when its person leaves the relay.

The request inbox #

R_B files a DmInvite by Bob's effective DM setting, three layers where each may only tighten the one above:

Layer Senders outside Bob's workspaces on R_B Members of a workspace R_B hosts with Bob
R_B's operator RIM_DM_INBOUND: open, requests (default), partners (the servers RIM_DM_PARTNERS lists, and R_B), none none
Each of Bob's workspaces on R_B A floor: none, requests or closed A default: direct or requests
Bob requests or none, within the floors Per workspace direct or requests

A member of a shared workspace is delivered when they are its Owner or a Moderator, Bob's contact, or when Bob's choice (else the workspace's default) for one shared workspace is direct; otherwise the invite is a request. Anyone else is refused (blocked) when the conversation's host is a server RIM_DM_INBOUND does not admit, contacts included; then a contact or a principal Bob accepted before is delivered, and otherwise the strictest of the operator's floor (none refuses senders on R_B too), the workspaces' floors and Bob's choice makes it a request or a refusal (blocked). A contact is someone Bob added, accepted, or messaged first: the home records each other member of a DM as its creator's contact.

An invite another host delivers names its sender, and R_B checks that the host speaks for them before anything else. from_card must verify against the key log of from_principal_id: the copy R_B holds (the person is its own user or a remote user it stores), else an identity it cached less than a day ago, else the identity the delivering host serves for them at GET /s2s/v1/principals/<id>. The newest card R_B then knows for them (the one it stores, the one served, or from_card) must list the host's origin; a sender who is R_B's own user may instead hold an active subscription at that host. A card that fails against a log R_B has, or a verified card that does not list the host, is refused (invalid_invite) and nothing is filed. The policy above, contacts and shared workspaces included, then judges that verified principal. When R_B holds no log for the sender and the host serves none (its RIM_DM_INBOUND may not admit R_B), the sender is unverified: whoever the invite names, it is judged as a stranger's, so it can only be a pending request or refused, never recorded as accepted or delivered directly, and the request counts against the limits below. The relay keeps no mark of this on the request: the app verifies the card against the sender's key log before it shows the name, as below, and shows an unverified sender as such. So a conversation homed on a server its creator's card does not list (created there through the forward path) reaches members on the home itself, and members on the creator's own relay while the creator holds an active subscription at the home; another relay refuses its invites when it can verify the creator, and otherwise takes them as a stranger's.

A request is a relay_dm_request row: the sender's card, the conversation, and up to 3 held items of it in at most 1 MiB, the DmInvite first (later ones dropped until accepted; the app reads them from the host). The app verifies the held DmInvite like any relay item to bind the conversation's space to its home before it reads or leaves it; ignoring or blocking keeps it with the request until the row expires. Everything held for a recipient, pending requests' items and the invites ignored requests keep, takes at most 16 MiB: past it a new DmInvite is refused (limited) and a later item dropped. Only DmRequestReceived is pushed. An invite from a contact or a principal accepted before is recorded as a row accepted at once (decided_at = created_at), keeping no card, not listed by dmRequests and not counted by the request limits, so every conversation R_B delivers for has a row and items of any other conversation are refused. Bob holds at most 5,000 accepted rows per host: past them such an invite is refused (limited). Accepting a request is never refused, and no row is evicted to make room.

An accepted row expires 400 days after the last item R_B delivered for its conversation (the expiry moves at most once a day): over a year, so a conversation whose members write once a year stays open, while one gone silent, or whose home is gone, is let go. The next item of a conversation let go is refused (not_subscribed), and the home sends its DmInvite again (see "Outbox and deliver"), which R_B files like any invite: accepted at once for a contact or a principal accepted before, a request otherwise. The row is deleted when Bob leaves the conversation or is removed from it. A home that is also Bob's relay deletes it when it removes him. Another relay deletes it on the home's MemberRemovedFromConversation naming the id the home gives Bob, which it learns from the first event of the home on Bob's own u: stream that carries user_id and the conversation (MlsWelcomeAvailable, ReadStateUpdated, NotificationDue); the event itself still reaches Bob. Until R_B learns that id the expiry alone bounds the row.

When the home and the recipient's relay are one server (Bob's relay hosts the conversation, and its creator is someone else, from another relay or not), the home files its own DmInvite for Bob through the same rule instead of delivering it; the creator's server is the home, or the home relay of a creator from another server. A DM between members of a workspace R_B hosts is filed the same way, its DmInvite naming the workspace as workspace_id. A DM the rule refuses for a member of the home is refused when it is created (FORBIDDEN). The invite and the conversation's events are held as above, and until Bob accepts, the conversation is left out of his inboxConversations, its events out of his workspaceEvents, and its notifications, mentions and unread messages out of his myNotifications, myUnreadNotificationCount, unreadCounts and email digest; ignoring keeps it out, and so does blocking its creator. Once accepted it is an ordinary conversation of the space he uses directly.

Limits: 100 pending per recipient, 20 per sender principal per day per relay (RIM_RELAY_DM_REQUESTS_PER_DAY), and 1,000 per delivering host per day whichever principals they name, 16 MiB held per recipient; past them an invite is refused (limited), and once the host is past its 1,000 an invite whose sender R_B would have to fetch is refused without the fetch. Principal ids cost nothing to mint, so for an unverified sender the per-sender limit is advisory: the per-host limit and the 100 pending per recipient are what bound a host that invents senders. reportDmRequest(id, reason) reports abuse: it files a relay_abuse_report row naming the reporter, the sender, the host and the request (audit relay.dm_request_reported), and a pending request is ignored.

Under RIM_DM_INBOUND=partners R_B answers GET /s2s/v1/principals/<id> only to the servers RIM_DM_PARTNERS lists (the S2S signature names the caller), under none to no server: 404 as for an unknown principal. POST /s2s/v1/key-packages/claim from those servers is refused with 403. A server where the principal holds an active subscription to a workspace is answered either way. Outbound, RIM_DM_OUTBOUND (allowed, partners, none) limits the servers whose people R_B's users may add to a conversation of its direct space and claim key packages from, and the relays R_B sends direct-space events to.

Joining #

  1. The invite link is read like a device-link code: whitespace removed, at most 400 characters, split at the first four : after the scheme (the origin keeps its colons). The app pins H.
  2. The challenge has keyLoginChallenge's shape (120 s, single use) and comes over S2S: POST /s2s/v1/join/challenge {"inviteToken"} → {"challengeId","nonce","expiresAt","workspaceId"}. It is a join challenge, bound to the relay that asked for it: H consumes it only in that relay's POST /s2s/v1/join, and loginWithKey, signupWithKey and enrollIdentityKey refuse it, as the join refuses a challenge from keyLoginChallenge or one issued to another relay. So the relay cannot redeem the person's proof as a session at H. The invite link carries no workspace id, and the delegation must name one, so H answers the workspace the invite names, checked as previewInviteToken checks it and not used (404 not_found for an unknown invite, 403 forbidden for one revoked, used up or expired); workspaceId is null without an invite. The device signs a login statement with audience = H's server id, so the proof is good only at H and the relay never vouches for the person. The proof keeps the login format, so what it may be used for lives with the challenge H issued; a distinct join statement naming the relay would harden this further and is not part of v1.
  3. The device signs a delegation. R sends H {"inviteToken","keyLog":[…],"devices":[{"certificate","revocation"}],"card","proof","delegation","username"}, username (optional) being the person's username at R.
  4. H verifies log, certificates, proof (claiming the join challenge it issued to R) and invite token (the rules of joinServerByInvite, bans included), creates or updates the remote user, adds the membership with the invite's role, stores devices and card, accepts the delegation, and answers {"workspaceId","userId","role","streamHeads":{"w":17,"u:rimp1_…":0}}. R records the subscription; the app loads the space through the forward path. The join carries no mlsActive, so H marks devices it did not know inactive for encryption; R pushes the full identity (POST /identity) right after the join, as it does for any host holding the person.

A current member (an earlier join, or an existing local account on H) sends inviteToken: null.

Through a public link. A workspace's public link (docs/messaging.md, "Public join link and join requests") takes the place of the invite on the same path. The link, https://<H's web domain>/join/rim_pjl_…, names H by origin only; the app pins H with remoteServer(origin), which answers H's server id.

  • The token travels in its own field, publicLinkToken, never in inviteToken: POST /s2s/v1/join/challenge {"publicLinkToken"} and POST /s2s/v1/join {…, "inviteToken": null, "publicLinkToken", "message"}, message being the optional note to the moderators. A request naming both is 400 bad_request. Both bodies refuse unknown fields, so a host without links refuses a link token (400) instead of reading it as an invite, and H never has to tell the kinds apart by content. Rejected: one inviteToken field told apart by the rim_pjl_ prefix (a client or relay that does not know links would send a link where an invite is expected, and an old host would answer it as an unknown invite).
  • H checks the link with the code of publicJoinLinkPreview and joinByPublicLink: every invalid link (unknown, switched off, replaced, its workspace gone) is 404 not_found with the same message; misses count against the presenting relay's server id (s2s:<serverId>), 20 in ten minutes answering 429 rate_limited for an hour. The relay's address is shared by all its people, while its server id is what the request's signature proves and what an operator blocks. A valid link whose allowRemote is off is 403 forbidden ("this workspace's public link does not admit accounts from other servers") and is not a miss. A blocked or denied relay gets 403 peer_not_allowed before any of this, as for every request.
  • The challenge answers workspaceId (the link's workspace), workspaceName and linkMode (direct or requests), the preview the app shows before the person chooses "Join" or "Ask to join". The link is checked, not used.
  • At the join H checks the link again before it consumes the challenge: its workspace must be the delegation's (400 bad_request otherwise). After storing the person it runs the checks of joinByPublicLink in one transaction: not a member, not banned, room under RIM_LIMIT_MEMBERS_PER_WORKSPACE. A current member is joined again as with an invite, and their delegation accepted. A local account of H presented by a relay is 400 bad_request: it uses the link at H directly.
  • direct: the person joins with the link's role and public channels, with MemberJoined "source": "public_link", the link's join count and the audit row; H accepts the delegation and answers as for an invite.
  • requests: H files a join request for the person, with the limits, message, expiry and decline wait of a local one, and records the presenting relay on it. It accepts no delegation (the person is not a member) and answers {"workspaceId","userId","role","streamHeads":{},"joinRequest":{"id","expiresAt"}}, role being the role the link gives. R records the request (relay_join_request) until expiresAt and records no subscription.
  • The decision. Accepting adds the person as an invite join does. JoinRequestDecided (accepted, declined, or cancelled by a ban) goes on the person's u: stream to the relay recorded on the request, the one outbox recipient a workspace has without a delegation. R queues an item naming no conversation for a recipient without a subscription only when it is a JoinRequestDecided on their own u: stream for a workspace where it holds their recorded request (not_subscribed otherwise), then forgets the request. The app, told accepted, joins as a current member (inviteToken: null, no link) with a fresh challenge and delegation, and R subscribes. The person cannot withdraw the request through R; it expires after 30 days. myJoinRequests on R lists only requests filed at R.

Delegation #

{"v":2,"type":"delegation","principalId":"rimp1_…","deviceId":"<uuid>","relay":"rims1_…","relayKeyHash":"…",
 "host":"rims1_…","workspaceId":"<uuid>","scope":"workspace","nonce":"<16 bytes>","issuedAt":"…","expiresAt":"…"}

Signed by the device key over rim.delegation.v1\0 || payload: "relay relay may receive this workspace's events for me and forward my device-signed requests to host until expiresAt". It never lets the relay act as the person; writes still need device signatures. nonce is 16 random bytes, unpadded base64url; the app issues delegations for exactly 24 hours from a whole second.

A host accepts it (on join or POST /s2s/v1/subscriptions) when the signature verifies under a non-revoked device of the principal (an unknown device is fetched once from the presenting relay's principals); host is its own id and relay the presenting peer; relayKeyHash names a key of that relay's log with no signer: recovery rotation after it (an ordinary rotation keeps delegations, a recovery kills them); the principal is a current, unbanned member of workspaceId; scope is workspace; expiresAt − issuedAt ≤ 24 h and expiresAt is ahead. It keeps it until min(expiresAt, accepted_at + 24 h) by its own clock, so a device clock cannot extend it. One row per (workspace, device, relay); a newer one replaces it unless the active row runs longer, so a relay replaying an older delegation cannot shorten or reset the one it holds.

Subscriptions. POST /s2s/v1/subscriptions {"delegations":[…]} (at most 64) → {"subscriptions":[{"workspaceId","status","expiresAt"}]}, one entry per delegation in order, status active or refused with a reason (invalid_delegation, bad_signature, wrong_host, wrong_relay, relay_key, expired, unknown_device, revoked_device, not_member, banned, limited); workspaceId is null for a delegation that cannot be read. renewDelegations answers these reasons and two of the relay's own, and logs the detail behind them. host_unreachable: the host could not be reached, failed, rate-limited the relay or gave an unreadable answer, and the relay keeps the subscription as it was. host_refused: the host refused the presentation as a whole, or refused a delegation for a reason outside this list. A relay's subscription for (user, workspace) lives while one of the user's devices has an active delegation there. POST /s2s/v1/subscriptions/cancel {"subscriptions":[{"workspaceId","principalId"}]} (at most 64) ends the presenting relay's delegations for them → {"cancelled":<n>}. Leaving, a kick or a ban ends the user's delegations for the workspace after MemberLeft is sent; the departed member gets that MemberLeft on their u: stream, being no member of w any more. MemberLeft may carry cause (kick, ban, workspace_deleted, account_deleted) and, for a temporary ban, until. A kick or ban's optional reason is private: it appears only on the removed member's u: stream and never on w or another member's stream. Clients may keep the reason visible until dismissed. join, join/challenge, subscriptions and subscriptions/cancel are workspace host endpoints: a server running only relay answers 503 role_disabled. presence and revocations are served by every role (a relay is the home of DMs). A relay delivers items of a workspace a user holds an active subscription to straight to the queue; the request inbox is for everything else.

Renewal. An online device signs fresh delegations when the current ones have less than 6 hours left and sends them with renewDelegations; the relay presents them. When every device has been offline 24 hours the subscription lapses, the host stops queuing for it, and on return the app renews and catches up from the change feed and streamHeads. Short delegations bound a hidden revocation, as the relay decision requires. Rejected: a delegation for the whole host (a stolen relay key would reach every workspace there), and long-lived delegations with explicit revocation only (a hidden revocation would never end).

Presence. The relay reports POST /s2s/v1/presence {"updates":[{"principalId","online"}]} (at most 64) → {"applied":<n>} to the hosts of the person's subscriptions when their first relayStream opens, and once the last has been closed for 30 s with none reopened. The host applies it in every workspace where the relay holds an active delegation of the person; a remote member's presence does not time out between reports.

Members, roles, bans, timeouts, private channels, archive state, the plugin registry and bundles, search, notifications, the change feed and MLS sequencing stay the host's, checked by the same services for remote members. Bundles and attachments come through the forward path, so the web app reads them same-origin from its relay.

The host verifies the revocation against its copy of the log (identity key, or the device itself), marks the device revoked, ends its delegations and direct sessions, raises MlsMembershipChanged where it is a group device, and acknowledges; a repeat gets the same acknowledgement (appliedAt is when the device was first revoked there). A device it does not know is fetched once from the presenting relay; one it still does not know is 404 not_found, and the relay stops sending to that host (GAVE_UP). The relay verifies each acknowledgement under the host's pinned key before recording it, and pushes {"type":"RevocationAcked","deviceId","hostServerId","ack":{"payload","signature"}} on relayStream to the person's devices online. applyRemoteRevocation is the same on the host's GraphQL, without a session and exempt from CSRF (it acts only on a fresh identity or device signature, like loginWithKey), at most 20 attempts per IP per 15 minutes (RATE_LIMITED past them). The app verifies each acknowledgement against the pinned key and its revocation's hash, and names any host it could not reach: "<host> has not confirmed; the device keeps access to <workspace> until <time>", the delegation's expiry at most. The relay stops forwarding anything the revoked device signs as soon as it commits.

Direct connection #

The fallback when the relay is unreachable; desktop only in v1 (a browser cannot hold cookies for another origin).

  • When. After 60 seconds of failed relay requests (network errors, 5xx, bad host signatures on forwarded responses), or when "messages may be missing" persists after reconciling. The app asks once per host ("Connect directly to <host>? It will see your IP address") and remembers it.
  • How. It fetches the host's discovery document directly and checks it against the pin, then calls keyLoginChallenge and loginWithKey on the host with audience = the host's server id. The host finds the remote user and device (refreshing its copy from the person's relays first, carrying on with the stored copy if none answers within 10 seconds) and issues a device-bound session valid 24 hours for a remote user. When a relay answers with a document the host refuses (it does not verify, or its key log does not extend the stored one) and no relay's is stored, the sign-in is UNAUTHENTICATED: the stored copy may predate a recovery or revocation the relay could not deliver. The app then uses the host's /api and /api/ws as a local client would, under a banner "Connected directly to <host>". The account mutations a remote user may not run are refused on that session too (FORBIDDEN).
  • Meanwhile. Events from the host's workspaceEvents carry no seq, so the app holds the host's RelayItems unapplied and unacknowledged while connected directly.
  • Back. It probes relayInfo every 60 seconds; after two successes it renews delegations, asks the host directly for the streamHeads of the streams it knows there and takes them as their baseline, runs the held items and reads relayStream on from its last item, deduplicating by (host, stream, seq), and closes the direct connections.

Switching relays #

  1. signupWithKey on the new relay R2 with the same identity: the key log, this device's certificate and a proof whose audience is R2's server id, sent directly (desktop) with a session kept outside the webview; loginWithKey instead when an earlier attempt created it.
  2. Publish a card (version + 1) with relays: [R2, R1] to both; direct-space hosts deliver to both.
  3. Sign a delegation for R2 for every subscribed workspace, including those R1 hosts (a delegation may name a local member too), and renewDelegations on R2.
  4. Drain R1's relayStream; nothing new reaches R1 that does not also reach R2.
  5. If R1 will go away, list the conversations homed in R1's direct space; once the app runs on R2 it creates their successors there (a successor is created by the app's session on its own relay), with R1's direct space as a space elsewhere.
  6. Publish relays: [R2] and call leaveRelay on R1, which cancels its subscriptions at every host and deletes the person's queue, contacts and requests there (the user row stays: it may still be a member of spaces R1 hosts).

History is on the devices and the drive, keys on the devices, spaces on their hosts: nothing is lost.

Public relay (7.4c) #

The public relay (the project's own is relay.rim-platform.org) runs the stock image with RIM_ROLE=relay. In pow mode signupWithKey takes a registration token (instance invite or workspace invite, as in invite-only mode) or proofOfWork, not both: an 8-byte nonce (unpadded base64url) such that

SHA-256("rim.pow.v1\0" || relay server id (ASCII) || "\0" || inception payload bytes || nonce)

starts with powBits zero bits (the descriptor's, from RIM_REGISTRATION_POW_BITS; 24 to start, about 16.7 million hashes on average). It binds the work to this relay and this principal; the server checks one hash before any signature; the open-signup per-IP limit applies too, and each such signup is audited as relay.registration_pow. Password signups take a token, as in invite-only mode; registrationMode answers POW. The check is rim_s2s::pow. Rejected: a server-issued puzzle (a round trip and stored state for no gain) and memory-hard functions (no WebCrypto support).

Migration of single-server deployments #

The migrations are additive and the key is created at first boot. With RIM_PUBLIC_BASE_URL unset the discovery document has endpoints.s2s null and nothing else changes. Existing accounts are local, existing workspaces hosted here; the desktop app's card already lists this server as its relay. Old invite links keep working; createInvite also answers the rim-invite:1: form when S2S is on. down migrations refuse to run while remote users, delegations or queued items exist.
