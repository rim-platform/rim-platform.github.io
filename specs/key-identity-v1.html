Key identity v1

Key identity v1version 1status: implemented, normativerim-server/docs/specs/key-identity-v1.mdcommit 332b0aa

Status: implemented, normative. A user is a key pair, the user id is stable with a signed key log, and servers are interchangeable relays. The web app may create and hold an identity, not only be a linked device (amended 2026-10-15, keys by default). This document is the contract between the server (rim_identity, KeyAuthService) and every client that signs statements.

Algorithm agility: statement format version 2 tags every key and signature with its algorithm, payload caps fit hybrid post-quantum keys, and the server indexes device keys by a hash. Version 1 statements stay valid. See "Algorithms and statement versions".

Key-only signup: signupWithKey creates an account from a key identity and an account password, with no email unless an email-bound invite gives one, so user.email is nullable. See "Key-only signup".

Account password: a local account also has a password, checked with OPAQUE and proved at every sign-in together with the device key; the recovery key resets it. See "Account password (OPAQUE)".

One kind of account (amended 2026-10-24): the accounts with a username and an Argon2 password, their email reset and the enrollment of a key on such an account are gone. Every local account signs up with a key identity and an account password.

Scope #

  • rim_identity, a dependency-light crate that verifies every signed statement below. It has no database, HTTP or GraphQL code, so the Tauri client and later the relay can reuse it.
  • Storage: key columns on the existing user row, plus key_log_entry, device_key, profile_card and key_challenge tables, and session.device_key_id.
  • KeyAuthService with GraphQL mutations to sign up with a key identity, add and revoke devices, rotate or recover the identity key, publish a profile card, and sign in with a device key and the account password through a single-use challenge.

Defined elsewhere: device linking (device-linking-v1.md), plugin manifest signing (workspace-plugins-v1.md) and remote users (server-to-server-v1.md). The recovery phrase and the key UI are client features of rim-ui.

Keys and encodings #

  • All keys today are Ed25519. Key and signature bytes are unpadded base64url (RFC 4648 §5, no =), written with an algorithm tag in front in version 2 statements (next section). Decoders are strict: padding, non-canonical trailing bits, wrong lengths, small-order ("weak") keys and non-canonical point encodings are rejected. Signatures are checked with verify_strict, so malleable signatures fail.
  • A person holds three kinds of key:
    • the identity key, which signs the key log, device certificates, revocations and the profile card. It stays off day-to-day devices where possible;
    • the recovery key, kept offline once the person saved the recovery kit (derived from the 12-word recovery phrase, see "Recovery kit"). It can replace a lost identity key;
    • one device key per device, certified by the identity key. Only device keys sign in; an account of this server also proves its password at sign-in, as an additional factor ("Account password (OPAQUE)"), and the password never signs in alone.
  • The identity key must differ from the recovery key, and a device key must differ from both.

Algorithms and statement versions #

Every payload names its format version in "v". A server accepts versions 1 and 2; any other value is refused with unsupported statement version N. Clients write version 2. Version 1 stays accepted so that statements signed before version 2 existed keep verifying, and nothing a server stores is ever re-signed.

The two versions differ only in how keys and signatures are spelled; field names, context bytes, caps and every rule below are the same.

Version 1 Version 2
Key (identityKey, recoveryKey, deviceKey) <base64url>, Ed25519 implied <algorithm>:<base64url>
signature <base64url>, Ed25519 implied <algorithm>:<base64url>
Algorithms Ed25519 only any the server implements
  • Tagged form. <algorithm> is 1 to 32 characters of a-z, 0-9 and -, followed by one : (not in the base64url alphabet, so the first colon splits). Today the only algorithm is ed25519 (32-byte key, 64-byte signature), for example ed25519:iojj3XQJ8ZX9UtstPLpdcspnCb8dlBIb83SIAbQPb1w. A version 2 key or signature without a tag, and a version 1 key or signature with one, is a VALIDATION error (identityKey is not in its canonical encoding). A well-formed name the server does not implement is refused with a message naming it (for example deviceKey names an unsupported algorithm followed by the name), so a client can tell "newer than this server" from a malformed value.
  • A signature's algorithm must be its key's. A signature tagged with one algorithm never verifies under a key of another (signature algorithm does not match the signing key).
  • One key, two spellings. A key is the same key in either version: KeyState, device uniqueness and the deviceKey must differ… checks compare algorithm and key bytes, not text. So a version 1 inception's recovery key and the same key tagged in a version 2 rotation match.
  • Mixed logs. A key log may start in version 1 and continue in version 2 (an existing identity moves to the new format, and later to a new algorithm, with an ordinary rotation signed by its current key). It never goes back: once an entry is version 2, a later version 1 entry is refused (a version 1 statement cannot follow a version 2 key log entry). Device certificates, revocations, profile cards and login proofs may be either version whatever the log's version; a version 1 statement can only carry and be checked with Ed25519 keys.
  • The principal id is derived the same way in both versions and for every algorithm: it is a hash of the inception payload bytes, so rotating to a new version or algorithm keeps it. The same keys incepted once as version 1 and once as version 2 give two different ids (the payloads differ); a client incepts once and keeps that log.
  • Canonical text. Servers store and return keys in the tagged form, whichever version carried them (DeviceKey.publicKey, user.identity_key).
  • Hashes stay SHA-256. principalId, prev and the device key hash are SHA-256, which keeps 128-bit security against quantum search; they are not tagged.

Planned algorithm (not implemented). Under the hybrid post-quantum rule, identity, recovery and device keys later move to Ed25519 + ML-DSA-44 (FIPS 204), expected under the name ed25519-mldsa44: the key and signature carry both parts (32 + 1,312 bytes of key, 64 + 2,420 bytes of signature) and a signature is valid only when both parts verify. Until a server implements it, that name is refused like any unknown algorithm. The payload caps below already fit it, including a profile card listing 32 such device keys.

Signed statements #

Every statement travels as { payload, signature }:

  • payload is the exact UTF-8 JSON text that was signed. Servers verify the signature over these bytes (they parse the payload first only to learn which key signed it), and store and return the text unchanged. Nothing is ever re-serialized, so there is no canonical JSON form: a client may order keys and space the JSON however it likes, and must keep the text it signed.
  • signature is the signature over context || payload, spelled as the payload's version requires, where context names the statement's purpose, so a signature made for one purpose never verifies as another:
Purpose Context bytes Signed by Max payload
Key log entry rim.keylog.v1\0 identity key (inception, identity rotation) or recovery key (recovery rotation) 16 KiB
Device certificate rim.device.v1\0 current identity key 16 KiB
Device revocation rim.device-revoke.v1\0 current identity key, or the revoked device itself 16 KiB
Profile card rim.profile-card.v1\0 current identity key 128 KiB
Login proof rim.login.v1\0 a device key 16 KiB
Password reset rim.password-reset.v1\0 the key log head's recovery key 16 KiB

\0 is one zero byte. The contexts end in v1 in both statement versions: they name the purpose, and the version is inside the signed payload. The caps hold for both versions and are sized for hybrid keys: a tagged Ed25519 + ML-DSA-44 key is about 1.8 KB of text (ML-DSA-87 about 3.5 KB), a rotation names two keys, and a card lists up to 32 devices (about 60 KB with ML-DSA-44, 115 KB with ML-DSA-87). Every payload has "v" (1 or 2) and a "type". Unknown fields, duplicate fields and a wrong type are rejected. The examples below are version 2; a version 1 payload is the same with "v":1 and bare keys. Timestamps are RFC 3339 and informational only: servers do not trust client clocks, so nothing depends on them.

Key log and principal id #

The key log is the person's history of identity keys. Entry 0 is the inception:

{"v":2,"type":"inception","seq":0,"identityKey":"ed25519:…","recoveryKey":"ed25519:…","createdAt":"2026-10-09T00:00:00Z"}

signed by its own identityKey. The principal id is fixed by it forever:

principalId = "rimp1_" + base64url(SHA-256("rim.principal.v1\0" || inception payload bytes))

So the id commits to both the first identity key and the recovery key, survives every rotation, and cannot be derived for keys other than those in that exact inception. The log and certificates are public, so a server additionally requires proof that the signing-up device holds its key (see "Key-only signup") before it lets an account carry a principal id.

Every later entry is a rotation:

{"v":2,"type":"rotate","principalId":"rimp1_…","seq":1,"prev":"…","identityKey":"ed25519:…","recoveryKey":"ed25519:…","signer":"identity","createdAt":"…"}
  • seq is the previous entry's seq + 1; prev is base64url(SHA-256(previous entry's payload bytes)); principalId is the log's principal id; identityKey must change. v is at least the previous entry's.
  • "signer": "identity": signed by the current identity key. The recovery key must stay the same. Existing devices stay enrolled (their certificates name an older keySeq, which is fine: a certificate is checked once, when the device is added).
  • "signer": "recovery": signed by the current recovery key. The recovery key may change. This is how a person who lost their identity key gets back in.
  • In every entry the identity key differs from the recovery key, and an entry with a field this section does not name is refused, by servers and clients alike.

Key log head pinning (clients). A client keeps, per principal, the seq and payload hash of the head of the longest log it verified. The first log it verifies for a principal pins its head; a log served later must contain the pinned entry at its seq (the same payload hash), and the pin then moves to the new head. A log that is shorter, or that holds another entry at the pinned seq, is refused: the client says the person's identity changed in a way RIM cannot verify, and treats that principal's devices as unverified.

Device certificate #

{"v":2,"type":"device","principalId":"rimp1_…","deviceId":"<uuid>","deviceKey":"ed25519:…","name":"Laptop","keySeq":0,"issuedAt":"…"}

Signed by the identity key at keySeq, which must be the head of the log when the server receives it. Clients accept a certificate at an older keySeq (devices stay enrolled across identity rotations) unless a recovery rotation follows that keySeq: a recovery voids what the lost key signed, as for plugin manifests. deviceId is chosen by the client (UUID v7 recommended). name is trimmed, 1 to 64 characters, no control characters. Per account, a deviceId and a deviceKey are each used once, revoked devices included: a revoked device comes back only with a new id and key. A key counts as used whichever version spelled it.

Device revocation #

{"v":2,"type":"device-revoke","principalId":"rimp1_…","deviceId":"<uuid>","signer":"identity","issuedAt":"…"}

"signer": "identity" (current identity key, any device) or "signer": "device" (the device being revoked signs its own retirement, so a device can sign itself out for good without the identity key). Revoking is idempotent: the first signed revocation is kept. Clients verify a revocation the server lists (by an identity key of the log, the one current when it was signed, or by the revoked device's own key) and remember a device seen revoked, so a server that later omits the revocation changes nothing on that client.

Profile card #

{"v":2,"type":"profile-card","principalId":"rimp1_…","version":3,"keySeq":0,"displayName":"Ada",
 "relays":["https://relay.example.org"],"devices":[{"deviceId":"<uuid>","deviceKey":"ed25519:…"}],"issuedAt":"…"}

What a person publishes about themselves, portable between servers. Signed by the current identity key at the current keySeq. version is 1 to 2³¹−1 and a server stores a card only if its version is greater than the stored one. displayName 1 to 80 characters; at most 8 unique http(s) relay URLs of at most 256 bytes; at most 32 devices with unique ids. The server does not check the listed devices against its device table: readers verify each device through its certificate.

Login proof #

{"v":2,"type":"login","challengeId":"<uuid>","nonce":"…","audience":"rim.example.com","principalId":"rimp1_…","deviceId":"<uuid>"}

Signed by the device key. challengeId and nonce come from keyLoginChallenge. audience is the host[:port] the client connects to (lowercase is safest; servers compare it case-insensitively), so a server that receives a proof cannot relay it to another server.

Each challenge serves one purpose. One from keyLoginChallenge is a login challenge, consumed by loginWithKey or signupWithKey. One a host issues for joining a workspace through a relay (server-to-server-v1.md §Joining) is a join challenge, bound to that relay and consumed only by its join; the two mutations refuse it, although the proof over it has the same format, so a relay never turns a person's join proof into a session.

Server rules #

Key-only signup #

signupWithKey(input: { username, displayName, keyLog, device, proof, passwordRegistration, instanceInviteToken, workspaceInviteToken }), no session needed, creates an account from a key identity and an account password ("Account password (OPAQUE)"), with no email unless an email-bound invite gives one (rule 1).

  1. The registration mode decides the token. In invite-only mode exactly one token is required, checked before the transaction and consumed inside it: an instance invite creates an account with no workspace (serverId null), a workspace invite also joins its server. In pow mode the signup gives one token or a proof-of-work. An instance invite bound to an email address gives the new account that address; the signup names no address of its own. An address an operator blocked is VALIDATION (this email cannot sign up here) and one another account holds is EMAIL_TAKEN, and either refusal leaves the invite unspent. In open mode no token may be given, and the signup counts against a per-IP limit (20 per 10 minutes). A wrong number of tokens is VALIDATION.
  2. The identity is verified: the whole log, at most 256 entries, replays from the inception; the certificate is signed by the head identity key; the proof is a login statement (same format and context as for challenge login) signed by that device's key over a fresh keyLoginChallenge, naming this log's principal id, the certificate's device id and this server's audience. The challenge is consumed. Without the proof, anyone who had seen a person's log and a device certificate (every server they use holds them) could sign that principal up elsewhere. No other account here may hold the principal id (CONFLICT). The username is 3 to 32 ASCII letters, digits, _ and -, not starting with r_ or deleted- and not reserved, stored trimmed and in lowercase, and must be free in any case (CONFLICT); displayName follows the display name rules (invisible characters removed but those emoji and scripts need, whitespace collapsed, at most 64 characters, not reserved; docs/api.md) and defaults to the username.
  3. In one transaction the server creates the user with email null or the email-bound invite's address, and principal_id and identity_key set, stores the log and the device, consumes the token (or joins the server), stores the account password with a new server share, and creates a session bound to the device, recording the device's lastUsedAt. It answers { userId, serverId, serverShare } (the share in the clear) and sets the session and CSRF cookies. Of two signups racing for one principal, the unique index refuses the second (CONFLICT). passwordRegistration that is not an OPAQUE RegistrationUpload is VALIDATION.
  4. Nothing emails an account without an email address: notification digests skip it.

logoutOtherSessions ends every session of the account but the caller's and answers how many.

Challenge login #

  1. keyLoginChallenge (no session) returns { challengeId, nonce, expiresAt }: 32 random bytes, valid for 120 seconds, single use. At most 60 challenges per IP per 5 minutes.
  2. The client signs a login proof with its device key and calls loginWithKey(proof), with passwordTicket for an account of this server. The ticket comes from passwordLoginFinish, which runs first, so the client holds the server share, and with it the keys it keeps at rest, before it signs ("Account password (OPAQUE)").
  3. The server finds the account by principalId and the device by deviceId, verifies the signature with that device's key, checks the audience against its accepted audiences, and claims the challenge atomically (a login challenge, unused, unexpired, same nonce).
  4. A local account needs a ticket. Without one, or for an account without a password record, the answer is UNAUTHENTICATED, as for a wrong proof. Someone from another server signs in with the key alone.
  5. On success it locks the user row, reads the device again (a revocation that committed in the meantime refuses the login), consumes the ticket in the same transaction as the session (it must be this account's, unexpired and unused; otherwise UNAUTHENTICATED), creates a session bound to the device, records the device's lastUsedAt, and sets the session and CSRF cookies.
  6. Every refusal is UNAUTHENTICATED with no detail, except a valid proof from a revoked device, which is FORBIDDEN so the client can tell the person to link the device again. A proof is valid here only when it passes every check of step 3: revocation is looked at after the audience and the challenge (which the attempt uses up), so an old proof, a replayed one or one made for another server never shows whether the device was revoked. Failed attempts are limited to 20 per IP per 15 minutes; successful logins do not count.

Accepted audiences come from RIM_KEY_LOGIN_AUDIENCES (comma-separated host[:port]). When it is unset, the host of RIM_PUBLIC_BASE_URL is used; when that is unset too, localhost:PORT and 127.0.0.1:PORT, but only when RIM_SERVER_HOST is localhost or a loopback address: a server bound to any other address (0.0.0.0 included) with neither variable set refuses to start, with a message naming both. The server logs the list at start-up.

keyLoginChallenge, loginWithKey and signupWithKey are exempt from the CSRF header check, because they are used without a session, and so are passwordRegistrationStart, passwordLoginStart, passwordLoginFinish, passwordResetChallenge, passwordResetStart and passwordResetFinish; loginWithKey and signupWithKey only act on a fresh signature, which a forged cross-site request cannot produce. rotateIdentityKey is exempt only when the request carries no session cookie (recovery, signed out). With a session cookie it needs the CSRF header like any other mutation, because an identity rotation is accepted on the strength of that session.

Devices #

  • addDeviceKey(certificate): signed in; the certificate must be signed by the current identity key at the current keySeq.
  • revokeDeviceKey(revocation): signed in; marks the device revoked, keeps the signed revocation, and ends every session of that device.
  • myKeyIdentity lists the log, every device (revoked ones included) and the card.

Rotation and recovery #

rotateIdentityKey(input: { entry, device }):

  • An identity rotation needs a session of that account. Devices stay enrolled. It is refused (VALIDATION, a key log may have at most 256 entries) when the log already has 256 entries, the same cap as at signup, so a log grown by identity rotations can always sign up on another server.
  • A recovery rotation works without a session (the person lost every device). It must come with a certificate for a new device under the new identity key. The server appends the entry, revokes every device and ends every session of the account, then enrolls the new device, which can sign in right away. The 256-entry cap does not stop a recovery: being locked out of the account is worse than a log too long to carry elsewhere. A log that recoveries took past 256 entries is refused by a signup on other servers. Anonymous attempts count against the same per-IP failure limit as logins, whether they succeed or not. An anonymous rotation for a principal this server does not know is UNAUTHENTICATED; other refusals carry the validation reason, so they show whether a principal is enrolled here. That is not secret: User.principalId is visible to signed-in users.
  • A rotation that does not extend the current head (wrong seq or prev) is a VALIDATION error. Two rotations racing for the same seq are serialized by the row lock below, so the second one sees the new head and fails the same way; fetch myKeyIdentity and sign again.
  • After either rotation, the server pushes the account's identity document to every host that holds the person as a remote user, as it does after a device or card change (server-to-server-v1.md, "Profile cards and contacts"). The document leaves out the devices a recovery revoked: their certificates are void, and a host revokes them when it applies the recovery entry, ending the person's direct sessions there and the delegations of those devices.

Every write that depends on the log (add, revoke, rotate, publish) runs in one transaction with the user row locked (SELECT … FOR UPDATE), so two of them for one account never interleave.

The plan called the log table key_rotation; it is key_log_entry because it also holds the inception. The device key index is on key_hash rather than on the key text, so it stays 32 bytes per row whatever the algorithm (a hybrid key's text is close to the btree row limit). Signed payloads are never rewritten. Keys live on the existing user row, so none of the tables that reference the user id move.

Malformed or unverifiable statements fail with code VALIDATION and a short reason such as signature does not verify or key log entry has seq 2, expected 1. A payload that is not JSON of the statement's shape (unknown, duplicate or missing fields, wrong types) is refused with the fixed reason statement payload is not valid; the JSON parser's own message goes to the server log only.

keyLog needs no session. The log is public (every server a person uses holds it), and a person who lost every device needs its head (seq and the hash of the last payload) to sign a recovery rotation. It answers [] for a principal no account here has (and for anything longer than 64 characters, which is not a principal id). It is not rate-limited: unlike the anonymous rotation, it checks no secret, and principal ids are 256-bit hashes that cannot be guessed, so answering whether one is enrolled here tells nothing a holder of the id does not already know.

Account password (OPAQUE) #

A local account (user.kind = 'local') has a password, a PIN or a passphrase the client chooses, which the server checks with OPAQUE (RFC 9807) and never sees. It is an additional factor: a sign-in needs a device key's login proof and the password together, and the password never signs in alone. A person from another server signs in at a host with the key alone; their password lives at their own server.

Every message travels as unpadded base64url. rim_auth/tests/vectors/opaque-v1.json holds one registration and one login made with one seeded generator (rand_chacha 0.3 ChaCha20Rng seeded with 32 bytes of 0x07, drawn by the setup, the registration start and finish, the login start, the server's login start and the login finish, in that order) for the credential id rimp1_vectortest; the client keeps a byte-identical copy and replays it to prove the same suite.

Keys and derivations #

  • E, the OPAQUE export_key (64 bytes), stays on the client. K_s, the OPAQUE session_key (64 bytes), is known to both sides after a login.
  • S, the server share: 32 random bytes per account, made when the password is first registered, kept across changes and resets, and stored sealed under the password key.
  • Transport key for what the server returns after a login: T = HKDF-SHA256(ikm = K_s, salt = "rim.opaque.transport.v1", info = <label>), 32 bytes, with <label> "server share" (and later "keep key", "session secret"). The value is AES-256-GCM sealed under T with a random 12-byte nonce and no associated data, sent as unpadded base64url of nonce ‖ ciphertext ‖ tag. At a signup or a reset there is no K_s: signupWithKey returns S in the clear, over TLS, to the account's own new session.
  • The client derives its unlock key from E and S: UK = HKDF-SHA256(ikm = E ‖ S, salt = "rim.unlock.v1", info = principal id). A rewrap a change leaves is AES-256-GCM(UK_new, nonce, UK_old, aad = "rim.uk-rewrap.v1|<principal id>"); the server stores it as opaque bytes.

The password key #

RIM_PASSWORD_KEY_FILE (default <RIM_DATA_DIR>/password-key.json, mode 0600):

{"v":1,"opaqueSetup":"<base64url, 128 bytes>","shareKey":"<base64url, 32 bytes>","createdAt":"…"}

opaqueSetup is the serialized OPAQUE ServerSetup (OPRF seed, key pair, the key that answers unknown principals). shareKey seals each server share with XChaCha20-Poly1305, a random 24-byte nonce and the user id as associated data. The server creates the file at first start and refuses to start when it is missing while passwords are stored. /readyz reports it as passwordKey. It belongs in every backup with the database: without it no password verifies and no share opens, and every account resets its password with its recovery phrase.

Registration #

  1. passwordRegistrationStart(principalId, request), no session: the OPAQUE RegistrationRequest, answered with the RegistrationResponse for the principal. CONFLICT when a local account here holds the principal; someone from another server held here may sign up and become local. At most 60 per address per 5 minutes, shared with passwordResetChallenge.
  2. The client finishes the registration and sends the RegistrationUpload as signupWithKey's passwordRegistration ("Key-only signup" rule 3).

Login and tries #

  1. passwordLoginStart(principalId, request), no session: the OPAQUE CredentialRequest. For a local account with a password the server counts a try in one statement (below), runs ServerLogin::start with the record, stores the login state for 120 seconds and answers { loginId, response }. For an unknown principal, an account of another server or one without a password it runs ServerLogin::start without a record and answers a random loginId that names nothing: the answer has the same shape, nothing is counted or stored, and no finalization verifies.
  2. passwordLoginFinish(loginId, credentialFinalization), no session, finishes it. The login state is deleted whatever the outcome; an unknown, used or expired login, or a wrong password, is UNAUTHENTICATED. A success clears the tries and answers { ticket, serverShare, rewraps }: ticket is 32 random bytes as unpadded base64url, stored as its SHA-256 hex with the account, valid for 120 seconds and once; serverShare is S sealed under T("server share") of this login; rewraps are newest first.
  3. loginWithKey(proof, passwordTicket) consumes the ticket ("Challenge login" rules 4 and 5).
  4. Tries. Every start counts as a wrong try, since each lets the caller test one guess; a finished login clears the count. Tries 1 to 3 are free. The 4th makes the next wait 1 minute, the 5th 5 minutes, the 6th 15 minutes, the 7th 1 hour, the 8th 4 hours, the 9th 12 hours. The 10th still gets an answer, and locks the password until a reset. A start during a wait is RATE_LIMITED with retryAfterSeconds; one at a locked password is PASSWORD_LOCKED. The count, the wait and the lock are per account, set in the same UPDATE that counts the try, so concurrent starts cannot pass one check. Each start also counts against the address in the key sign-in's failure budget (20 per 15 minutes) and is never refunded.

Change #

passwordChangeStart(credentialRequest, registrationRequest), signed in: counts a try and answers { loginId, credentialResponse, registrationResponse } (NOT_FOUND for an account without a password). passwordChangeFinish(loginId, credentialFinalization, registrationUpload, rewrap) verifies the current password (UNAUTHENTICATED otherwise; the try stays counted), replaces the record and clears the tries, keeps S, stores the rewrap and keeps the newest three, and ends every other session of the account. It answers { changedAt }.

Reset with the recovery key #

  1. passwordResetChallenge(principalId), no session: a challenge of purpose password_reset, 120 seconds, single use, which no login, signup or join consumes.

  2. The client signs a password-reset statement with the recovery key of its key log head:

    {"v":2,"type":"password-reset","principalId":"rimp1_…","challengeId":"<uuid>","nonce":"…","audience":"rim.example.com"}

    Version 2 only. It neither rotates the identity nor revokes a device.

  3. passwordResetStart(statement, registrationRequest), no session: the server reads the statement, finds the local account, replays its key log and checks the signature with the head's recovery key, checks the audience as for a login proof, and claims the challenge. Every refusal is UNAUTHENTICATED, with no detail: an unknown principal, an account of another server, a signature by any other key (the identity key included), a wrong audience or a used challenge. A statement that is not a password-reset statement is VALIDATION. It answers { resetId, registrationResponse }; the reset is valid for 120 seconds, once.

  4. passwordResetFinish(resetId, registrationUpload), no session: replaces the record (or stores the first one, with a new S, for an account without a password), keeps S, deletes the rewraps, clears the tries and the lock, and ends every session of the account. It answers true. Other devices' wraps of their data key no longer open, since E changed: each asks once for the recovery phrase, or starts empty.

Audit #

password_set, password_changed, password_reset, password_login_success, password_login_failure (with the count), password_locked, and key_login_failure with reason password_record_missing, password_missing or password_ticket_invalid, all with target: "audit" and ids only: never a password, E, S, K_s, a ticket, a key or an OPAQUE message.

Plugin principal ids: rimp0_ to rimp1_ #

Plugins see { principalId, displayName } (docs/specs/plugin-protocol-v1.md). Until now the client computed a provisional id, rimp0_ + base64url(SHA-256( "rim.principal.provisional.v1\0" + the lowercased account UUID)), in rim-ui/src-tauri/src/plugin_host/protocol.rs.

This PR adds User.principalId. The mapping happens once, in the client:

  1. When the signed-in user's principalId turns non-null (after the signup on this device, or on the first fetch on another device), the plugin host computes the account's old rimp0_ id the same way as before and records rimp0_… → rimp1_… in its local store.
  2. It sends running plugins rim.principal.changed with the new principal, plus the old-to-new mapping in rim.principals.remapped (plugin-protocol-v1, section 11), so a plugin can rewrite stored ids. It sends the mapping again after every handshake, so a plugin that was not running at the switch still gets it.
  3. Other people's ids map the same way when their User.principalId is first seen non-null. An account whose principalId stays null (a purged account that never had one) keeps its rimp0_ id.

The desktop client does this; the server only exposes principalId.

Clients (rim-ui) #

What the desktop app does with these statements; "Web client" below says where the web app differs. Other clients (the CLI) may choose differently, except for the recovery kit format, which every client that offers recovery must read.

  • Where keys live. Every secret goes through the app's one OS keyring helper (src-tauri/src/secret_store.rs), one entry per principal: the device key, and on the device that created the identity, the identity key and, until the person confirms they saved the recovery kit, the kit's entropy ("Recovery kit"). The identity key stays on that device until device linking can move it off; the device key alone signs in. Keys never reach the webview: it asks the Tauri side for a signed statement and sends that.
  • Key-only signup (the join pages, the only signup there is, with the page's token if it has one): the person picks a username, an optional display name, this device's name and the account password. The app creates the identity, recovery and device keys and registers the password (passwordRegistrationStart, then passwordRegistration in the signup, "Account password (OPAQUE)"). The device key, the identity key and the kit's entropy are written to the keyring before signupWithKey is sent, so a crash in between never leaves an account without its keys; the recovery key itself is never stored. There is no username and password form, no signup without a key and no enrollment of a key on an existing account. Once the signup succeeds the app shows the recovery kit ("Recovery kit"). When it fails, the app reads keyLog for the new principal: an empty log means the server refused, so the keys are removed and the draft stays in memory, letting the person retry with the same keys or discard them; a log that holds the principal means an attempt whose answer was lost created the account, so the app writes the draft's keys back if a failed attempt removed them and signs in with the device key and the password (also when the person discards the draft); with no answer the keys stay for a later sign-in. On success the keys are confirmed and linked to the returned user id, the profile card (display name, this server's URL, the active devices) is published, and the app opens the account (a workspace invite whose answer was lost opens the workspace its preview named). Unconfirmed keys whose principal has no key log on the server (a signup that never reached it) are removed when signing in with them fails.
  • Other sessions. Account settings offers "Sign out other sessions" (logoutOtherSessions) for every account, on the desktop and the web.
  • Audience. The host[:port] of the GraphQL endpoint URL as written, lowercased, the same rule the server applies to RIM_PUBLIC_BASE_URL.
  • Sign-in. On a cold start whose session cookie is gone or refused, the app signs in with the device key of the account it was last signed in to. After an explicit sign-out it waits on the sign-in screen, which offers every account this device holds a key for on this server, each signing in with the device key and the account password, besides linking this device and recovering an account. A FORBIDDEN answer says the device was revoked; the sign-in screen then offers to remove that device's keys from this computer.
  • Statement version. The app writes version 2 (tagged keys and signatures) and reads both. Keys and signatures are opaque text outside the one module that signs and verifies, so a hybrid algorithm is added there alone. A version 1 log (an identity an older client created) is extended in version 2 by its next rotation.
  • Identity rotation keeps the recovery key and every device. The new identity key is stored as pending, with the seq its rotation creates, before rotateIdentityKey is sent. A verified log whose head names it promotes it; a log that already holds that seq with another key drops it; a log that ends before it (a stale copy, or the rotation still in flight) leaves it pending, and a retry signs the same pending key again, so a rotation whose answer was lost never loses the key it put on the server.
  • Identity key backup. With the history archive set up, a device that holds the identity key keeps a copy of it in the archive, sealed under a backup key that only the recovery kit gives (HKDF-SHA256(ikm = the phrase's 16 bytes, salt = "rim.recovery-phrase.v1", info = "identity backup key"), or the same over a version 1 kit's 32-byte seed); the device keeps that backup key in its keyring record, never the phrase. It also wraps the archive key under the identity key. A linked device takes the identity key over in Settings > Security with the recovery phrase: the phrase must match the log's recoveryKey and the backed-up key the head's identityKey; nothing is signed or revoked. Format: rim-ui docs/specs/history-archive-v1.md, "Identity key backup". The backup needs the identity key as an exportable seed, so a browser-held identity is never backed up and no device can take it over with the recovery phrase ("Web client").
  • Profile card. Lists this server's URL as the one relay and the account's active devices. A device is listed only if its certificate verifies against the replayed log at its keySeq, so a server cannot add a key of its own to the card the identity key signs.

Web client #

The web app may create and hold an identity, not only be a linked device. It signs up with a key and a password (signupWithKey) as the desktop does, and follows the desktop's rules above except:

  • Keys. The identity key and the device key are WebCrypto Ed25519 keys generated with extractable: false and kept as CryptoKeys in IndexedDB, next to the account record (principal id, user id once known, server). Public keys are exported raw and tagged ed25519:. A browser without Ed25519 in WebCrypto cannot create an identity; there is no fallback to extractable keys and no account without one. In place of the signup form it shows "This browser can't create the keys an account needs. Use the desktop app or another browser." The recovery key is derived from the kit's entropy only to name it in the inception, and is not kept.
  • Storage. Before it creates keys, the client requests persistent storage (navigator.storage.persist()) and handles a refusal: it tells the person the browser may clear this site's data, which would leave the recovery kit as the only way back, and goes on only if they accept. It writes the identity key, the device key, the account record and the recovery entropy to IndexedDB before the signup mutation is sent. A failed write aborts the signup before any request, so the server never holds a principal whose keys the browser lacks.
  • A linked device is access, not recovery. Only the device holding the identity key links other devices (device-linking-v1.md), revokes them, rotates the identity key and publishes profile cards. A device linked to a browser-held identity signs in with its own device key and can do none of those, and it cannot take the identity over: a browser-held identity is never backed up ("Identity key backup" above). Its only recovery is the recovery kit, through a recovery rotation ("Rotation and recovery") that replaces the identity key and revokes every device. Moving an identity between devices is deferred.
  • Messages. A recovery gives back the account, not its messages: encrypted history comes back only from the history archive.

Recovery kit #

Shown after signup, as text the person saves, not as a gate before the request is sent. The kit saved is the whole kit, account id included. Because the inception commits to the recovery key, the kit exists before the signup is sent, so the client keeps the kit's 16 entropy bytes next to the identity key (the keyring on the desktop, IndexedDB on the web) until the person confirms they saved the kit, then deletes them; until then it can show the kit again. Those bytes are the account's recovery secret, stored temporarily: they are never logged or sent anywhere, and deleting them promises no forensic erasure. Until the person confirms, the client shows a persistent warning; the web client's reads "Save your recovery kit. Losing this browser's data can permanently remove your ability to manage this account." Clients write version 2; readers accept both versions, as a whole kit or as the bare secret alone (a 12-word phrase or a RK1- key), and tell them apart by content, not by the header line. Either way the secret is a 32-byte seed used as the Ed25519 recovery key (SigningKey::from_bytes); the key log's recoveryKey is its public key. Nothing is migrated: an identity created with a version 1 kit recovers with its RK1- key.

Version 2, the recovery phrase.

RIM recovery kit (v2)
Account id: rimp1_nz1POml8JmCMcFDECrtu60ibohPKnywhcExmOPMvTUo
Recovery phrase: word1 word2 … word12
  • Entropy: 16 random bytes from the OS.
  • Phrase: the BIP39 encoding of those bytes with the English word list: 128 bits plus a 4-bit checksum (the first 4 bits of SHA-256 of the entropy), 12 words of 11 bits each.
  • Seed: HKDF-SHA256(ikm = the 16 entropy bytes, salt = "rim.recovery-phrase.v1", info = "recovery key"), expanded to 32 bytes. It is not BIP39's PBKDF2 seed: a passphrase and 2,048 rounds add nothing to 128 random bits.
  • Reading: case, extra spaces and line breaks are ignored, and so is numbering in front of a word (1., 1), or a number on its own, as copied from a numbered list). The kit's header and account id lines and the Recovery phrase: label are skipped. A phrase that is not 12 words is refused; so is a word outside the list, with a message naming its position and the word as typed; so is a phrase whose checksum fails (most typos and swapped words).

Version 1, the recovery key.

RIM recovery kit (v1)
Account id: rimp1_nz1POml8JmCMcFDECrtu60ibohPKnywhcExmOPMvTUo
Recovery key: RK1-…   (14 groups of 4 characters)

The recovery key is RK1- and the RFC 4648 base32 (uppercase, no padding) of the 32-byte recovery seed followed by the first 3 bytes of SHA-256("rim.recovery-kit.v1\0" || seed), in groups of 4 joined by -. Readers ignore case, spaces and -, read 0 as O and 1 as I, and refuse a key whose check bytes do not match. Version 2 replaced this format for new identities; readers keep accepting it. A text holds a version 1 key when a line other than the account id's has a word starting with RK1; a phrase never does.

Recovering (signed out, every device lost): the app reads the kit, fetches keyLog for the account id, replays it, checks that the head's recoveryKey is the kit's, and signs a rotation with "signer": "recovery" that keeps the same recovery key and names a new identity key, plus a certificate for a new device at the new seq. It stores the new keys, sends rotateIdentityKey without a session, and signs in with the new device key. Every other device and session of the account is signed out by the server.

Whether a recovery landed is read from the key log, not from the error: when rotateIdentityKey fails, the app fetches keyLog again. If the log ends at its rotation it signs in; if the log answers without it, the attempt's keys are removed and any keys this device held for the account before the attempt are put back; with no answer the keys stay for the next try.

Deferred #

  • QR device linking (a new device gets its certificate from the old one through the server as a courier) is specified in device-linking-v1.md.
  • Moving an identity between devices, the identity key included. Until then a browser-held identity stays in the browser that created it and is recovered only with its recovery kit.
  • Usernames stay unique across the whole table; rows of kind remote get an r_ username (server-to-server-v1.md).
