Privacy starts
with control.

Choose who runs your workspace, where your history lives and what your tools can access. RIM connects independently operated servers, with no central RIM service required.

01 / OWNERSHIP

Run your own server.

Host a workspace on infrastructure you choose. Use your own relay, or connect through a public one. One server can do both jobs.

02 / PRIVATE CONVERSATIONS

Keys stay with your devices.

New DMs and private groups use MLS end-to-end encryption when the creator has encryption set up. Across servers, encryption is required. Devices decrypt encrypted messages; delivering servers see ciphertext.

03 / EXPLICIT ACCESS

Choose what gets access.

Review plugin permissions. Decide whether to use AI, which provider to use, and whether it may read an encrypted conversation.

Know the boundaries

Channels, including private channels, are readable by their host. Servers see metadata. External cryptographic review is pending; these are early, pre-review releases. Read the security overview ↗

How it works

One server to start.
Connect across servers.

RIM separates your connection to the network from the place a workspace runs. A relay delivers. A host runs workspaces. The same server binary can be either—or both.

Where does my account live? Where are my keys?

Your identity is based on a key pair. Your relay holds your account, profile, public device records and authentication records. Private identity and device keys stay on your devices; the recovery phrase lets you recover your identity if your devices are lost.

A workspace host keeps your membership and role in its workspace. Joining a workspace on another host doesn't move your account there. Recovering your identity and restoring old encrypted history are separate: old history needs your archive.

Keys, recovery and identity backup ↗
What happens when I send a message across servers?
  1. Your client prepares the action and signs the cross-server request with its device key.
  2. Your relay forwards the request to the server responsible for that conversation or workspace.
  3. The responsible server checks permissions, processes the action and sends signed events through members' relays. Clients verify the host's events.

Server discovery uses signed descriptors and pinned server identities. Server-to-server traffic uses HTTP Message Signatures with replay protection, over TLS.

Read the server-to-server protocol ↗
Where does end-to-end encryption happen?

In the clients. New DMs and groups are encrypted when their creator has encryption set up; local plaintext conversations can exist until upgraded. Cross-server DMs and groups require encryption. Each encrypted conversation is an MLS group, with devices as members. A sending device encrypts the content; recipient devices decrypt it. Servers order and deliver ciphertext without holding the conversation's decryption keys. DMs and groups homed on another relay are reached through your relay.

Channels are deliberately server-readable for shared history, server search and workflows. Encryption does not hide metadata such as membership and message timing. Letting a plugin or AI read decrypted content gives that tool access to it.

04 / PIPELINES

Match an event.
Explore a trigger.

Choose a workspace event, filter it by conversation or message pattern, and add a cooldown. Pipelines are an early foundation for event-driven workflows.

Today, matching events run only commands allowed without confirmation, such as searches or marking conversations read. Search results are not displayed. Posting messages, webhooks and workspace-state changes are planned.

Actions requiring confirmation are skipped. Encrypted message text cannot be matched by server filters. Posting, webhooks and state changes are on the roadmap ↗

Where do plugins run?

In your client. Sandboxed web plugins run in isolated frames in the desktop or web app, with granted capabilities and allowed network destinations. Desktop process plugins run programs on your computer with your OS account's access, including local tools and credentials.

The workspace host can distribute plugin bundles and registry entries. It doesn't run those client plugins for you. A local process isn't isolated like a sandboxed web plugin; its RIM permissions govern what the app does for it.

How do I install a plugin?

Open Settings → Plugins. Install from a bundle link, or on desktop from a local folder or Git repository. Review the source, any installation scripts and the permissions before turning it on.

A workspace can recommend plugins through its signed registry. You review and install them on your device. Registry entries pin a publisher-signed version and bundle hash; a folder, Git or ordinary link install is labeled unsigned.

Read the plugin installation guide ↗
Can a plugin read my conversations?

Sandboxed plugins read messages through the grants you approve. Reading encrypted DMs and groups requires an additional encrypted-conversation permission. Desktop process plugins also have your OS account’s access to files and credentials; RIM grants do not sandbox those programs. Once a plugin can read plaintext, its other permissions may let it send that text elsewhere. Review its author and capabilities.

Plugin settings stay on the device, scoped to the plugin and account. Secret settings are stored in the desktop vault; the web app doesn't offer secret settings.

Optional AI · Desktop

An assistant.
On your terms.

Bring an Anthropic or OpenAI API key and choose a supported model. Ask RIM's desktop agent to find information or help with a task through the same command system you use.

  1. Your permissions still apply.

    The agent sees only supported commands available to you, plus plugin commands you explicitly approve.

  2. You confirm built-in changes.

    Mutating and restricted built-in commands wait for you. Plugin commands you approve for the agent run without asking each time; dangerous ones are only proposed for you to run manually.

  3. You choose what reaches the model.

    Encrypted conversations are excluded until enabled for that conversation, with a data-sharing warning.

Desktop history · Your storage

Keep the conversation.
Choose where it lives.

The desktop keeps an encrypted local message cache for search and offline reading. Add an encrypted history archive in storage you choose, so a new device can restore the messages you've archived.

A local folder.

Keep an archive on your drive or in a folder you sync yourself. Archive files are encrypted before they are written.

Your own server.

Point the desktop archive at a compatible backup endpoint you run. This is a separate backup service, rather than a route on your RIM server.

S3-compatible storage.

Use a bucket on an S3-compatible service. The storage provider holds encrypted archive files, without the keys to read their contents.

Prefer a cloud drive? The desktop can also store the encrypted archive directly in Google Drive, Dropbox or OneDrive.

Archive ≠ live server

These are history backup and restore options. Relays and hosts still deliver live messages and run workspaces. Keep your archive passphrase and recovery material safe; an identity recovery alone doesn't restore old encrypted messages.
