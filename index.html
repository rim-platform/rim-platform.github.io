What RIM is

A communication workspace you program, and where it is heading

RIM is not a Slack, Discord or Matrix replacement. It is for people who want what those do not offer: a chat workspace they can shape with commands, keybinds, macros and plugins, running on a box they control. The closest relatives are VS Code, Raycast and Obsidian, applied to team communication.

today

What it is now

A Rust server and a Tauri desktop and web client. Chat with threads, attachments and search; a command registry with macros and pipelines; client plugins; key-based identity; MLS-encrypted DMs and groups; relays and hosts talking over a signed protocol.

direction

Where it is heading

A vanilla core that is a decentralized chat platform plus the programmable layer. Everything domain-specific lives in plugins, bots and pipelines, never in the server. Release readiness, a first-run path, hybrid post-quantum signatures and a mobile web app are next; the roadmap has the stages and the open decisions.

not

What it will not become

A platform that dictates how teams work, a race for integrations and user counts, or a product that competes on chat polish alone. It competes on being the most programmable, keyboard-efficient communication environment.

What makes it RIM

Six things no chat platform offers together

palette

Every action is a command

Fuzzy-searchable, typed, with sensitivity tiers. Plugins register into the same registry as the built-ins.

keybinds

Keyboard-first, modal if you want

Bind anything to any key, scoped by context. Three built-in profiles; export yours to a file and import someone else's. An opt-in Vim layer for moving around.

macros · pipelines

Compose your own workflows

Chain commands into one keystroke; react to events with pipelines. The workspace adapts to how you work.

plugins

Extend the app, not the channel

Panels, commands and context actions in a sandbox with capability grants. A signed workspace registry for your team.

mls

Encrypted where it matters

DMs and private groups use MLS with a hybrid post-quantum key agreement. Plugins read messages only through grants.

relays · hosts

Decentralized by design

Your identity is a key, not an account. A relay delivers; a host runs the workspace; the two talk over a signed protocol.

How it works

The design, in four layers

Everything a person or a plugin does is a command in one registry. Keybinds, macros, pipelines and the AI agent are all callers of that registry, so adding a plugin command gives every caller a new verb at once.

layer 1

Chat substrate

Workspaces, channels, groups and DMs, threads, attachments, reactions, search, notifications, moderation. Plain for channels; MLS-encrypted for DMs and private groups, with the server seeing only ciphertext.

layer 2

Command registry

Typed commands with sensitivity tiers and a confirmation gate for anything dangerous. The palette, keybinds, macros, pipelines and the agent all call it. The audit log records every run.

layer 3

Plugins

Client-side, sandboxed, with capability grants. Local plugins run as processes on the desktop; web plugins run in an isolated frame. A workspace can publish a signed registry of plugins for its members.

layer 4

Identity and servers

You are a key, with devices certified by it and a recovery phrase. A relay delivers to your devices; a host runs workspaces; servers prove themselves with signed descriptors and RFC 9421 request signatures.

One binary, two roles

A single server is its own relay and host. A public relay holds accounts and queues; workspaces live on hosts you or your team run.

Self-host

Up in ten minutes with Docker Compose

PostgreSQL, the server, the web client and Caddy with TLS on one domain. Backup, restore and a restore drill are scripts in the same folder.

# one server for a team
cp deploy/.env.example deploy/.env   # POSTGRES_PASSWORD, RIM_DOMAIN
docker compose -f deploy/compose.yml up -d --build
docker compose -f deploy/compose.yml exec rim \
  /app/rim-server invite create     # first signup link
# a public relay instead
docker compose -f deploy/compose.yml \
  -f deploy/compose.relay.yml up -d --build

# switch modules off for this instance
RIM_FEATURES_DISABLED=attachments,email

API

One GraphQL endpoint, and the HTTP around it

Everything a client does goes through POST /api; subscriptions arrive over /api/ws. The schema is published at /api/sdl with a description on every type and field, and the reference on this site is generated from it, so it cannot drift from the server.

reference

Every query, mutation and subscription

The whole schema, regenerated with every build and grouped by domain, each operation with its description, arguments and the error codes it can answer.

 contract

Talking to a server

The session cookie and the key-login challenge that issues it, the CSRF header on mutations, origins, the error codes in extensions.code, cursor pagination, serverInfo for version and feature negotiation.

Security

What we claim, and what we don't yet

Threat model

What a relay can and cannot see, what a host sees, what a stolen device yields, and what a recovery phrase recovers. Written down, with the limits.

Disclosure

Report privately through GitHub's vulnerability reporting on the repository concerned; each repository's SECURITY.md says what to include and what response to expect.
Contribute

Pull requests say what they change and why

Use whatever tools you like to write the code, including AI assistants. What we read is the pull request: it has to describe what it implements and the reason for it, in your words. A diff without that is sent back unread.

Every PR carries

What changes, for whom, and why now. What it does not do. How you tested it, with the gate output. Which spec or doc it changes, if any.

Before you start

Open an issue for anything beyond a fix, so the design is agreed first. Server features that belong to one domain are plugins, not core; the contributing guide and the roadmap say where the line is.

What the repos enforce

Formatting, lint with warnings as errors, the full test suites including the database and two-server ones, a comment style that says what code does and not its history, commits without trailers.

How the server code is laid out, and why we keep it that way

The server is three layers with a contract between each pair. A layer talks only to the one below it, and only through a trait. That is what lets us replace one piece, a repository on a different store, a service with different rules, a transport other than GraphQL, without touching the rest, and what lets every layer be tested against a mock of the one beneath. Pull requests that cut across the layers are sent back, however good the feature.

APIGraphQL resolvers and the other transports. Parses input, checks who is calling, maps errors to codes. No business rules.
rim_api · rim_server
service traits →
ServicesThe rules: permissions, validation, orchestration. Knows nothing about HTTP or SQL; sees repositories as traits.
rim_services · rim_infra_services
repository traits →
DataRepositories over PostgreSQL. Store and fetch domain models; no rules, no transport types.
rim_core · rim_infra_db

Contracts live apart from implementations

Domain models and repository traits sit in one crate, service traits with their commands, queries and DTOs in another. Implementations live in the infra crates. A caller imports the contract, never the implementation.

One wiring point

Concrete services and repositories meet in a single composition root at boot. Everything downstream holds a trait object, so swapping an implementation is a one-line change there and nowhere else.

Errors map at each boundary

A database error becomes a repository error, then a service error, then a GraphQL code. Each layer speaks its own error type, so a change in storage never leaks into the API contract.

Types stay in their layer

No Actix, GraphQL or SeaORM types in the services or the domain. Strongly typed ids everywhere. New modules are private to their crate until something outside needs them.

Tests follow the layers

Service tests mock the repositories; API tests run the schema end to end against a real database. A behaviour is pinned once, where the logic lives, with shared fixtures rather than repeated setup.

Two exceptions, both named

The composition root may import implementations, and non-GraphQL transports such as file upload may call service traits directly. Anything else that skips a layer is a bug, not a shortcut.
